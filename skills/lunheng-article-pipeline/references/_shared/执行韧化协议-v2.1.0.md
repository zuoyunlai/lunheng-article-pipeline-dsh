## 协议三大铁律（每个角色 prompt 头部必读）

### 1. 心跳信号（必须执行）
- **启动 30 秒内**：必须更新 status.md 对应行 `🔄 In Progress` + 写明「启动时间 + 当前模型」
- **每 5 分钟一次**：在 status.md 阶段行末尾追加心跳时间戳（格式：`[心跳 HH:MM] model=<model-id>`）
- **超时硬卡 8 分钟**（v2.3 已有，v2.1.0 强化）：
  - 6 分钟时：在 status.md 写 `[警告] 已耗时 6 分钟，剩 2 分钟`
  - 7 分钟时：必须产出 partial output 到草稿（哪怕不完整）
  - 8 分钟时：主控自动 kill + 标记 Failed，主控决定是否重试

### 2. 分阶段 ack（按任务时长分级）

| 任务预估时长 | ack 节点 |
|------------|----------|
| < 2 分钟 | 启动 ack 即可，无需中间 ack |
| 2-5 分钟 | 启动 + 完成二段 ack |
| 5-15 分钟（写手/审计） | 启动 + 25% + 50% + 75% + 完成 五段 ack |
| > 15 分钟 | **禁止**——必须拆任务 |

每段 ack 在 status.md 阶段行末尾追加： `[ack N% HH:MM] <一句话说进度>`。

**示例（写手 4758 字）：**
```
[ack 0% 17:35] 已读简报+大纲+10文献+17数据+3案例
[ack 25% 17:38] 完成开篇+第1节（549字）
[ack 50% 17:42] 完成第2-3节（788+592=1380字）
[ack 75% 17:46] 完成第4-5节（599+594=1193字）
[ack 100% 17:52] 完成第6-7节+参考文献（489+432+清单）
```

### 3. 模型健康度预检（v2.3 已有，v2.1.0 强化）
- **每个角色启动时**用论衡 agent `model.fallbacks` 链：
  - primary: `deepseek/deepseek-v4-pro`
  - fallback 1: `minimax-portal/MiniMax-M3`（已验证 fallback 成功 T4 实战）
  - fallback 2: `deepseek/deepseek-v4-flash`（便宜快）
  - fallback 3: `coding-plan/glm-5.3`（跨供应商最终兜底）
- **预检方法**：每个角色 session 第一次 LLM 调用前，先发一个 1-token ping（"ok"），若 30 秒内无响应则降级到下一档
- **降级日志**：在 status.md 阶段行末尾写 `[降级 HH:MM] primary→fallback1, 原因=ping超时`

## 改造要点（角色卡层面）

每个角色 prompt 头部新增段落：
```markdown
## 执行韧化协议（v2.1.0 必读，30 秒心跳 + 分阶段 ack）

1. 启动 30 秒内更新 status.md 为 🔄 In Progress，写明「启动时间 + 当前模型」
2. 按任务时长选择 ack 节奏（<2分钟/2-5分钟/5-15分钟）
3. 模型健康度预检：第一次 LLM 调用前发 ping，30秒无响应则降级 fallback
4. 超时硬卡 8 分钟：6分警告 → 7分 partial output → 8分被主控 kill
5. **禁止假装在线**：心跳 ack 必须真实反映进度，禁止编造 ack
```

## 改造要点（主控层面）

主控在 spawn 子代理时：
- 每次 spawn 后立即 watch 子代理 status.md 心跳（不再静默等待）
- 30 秒内未心跳 → 主控 console 警告，但**不**自动 kill（给子代理多一次机会）
- 5 分钟无 ack → 主控主动 ping 子代理 session（list_agents）
- 8 分钟无 ack + 无产出 → 主控 kill + 标记 Failed + 决定是否重试

## 三检索员并行监控补充（v2.1.8 必读，教训 #56 + #58）

> 背景：v2.1.8 主控一次性 spawn T1 + T2 + T6 三个独立 subagent（同一 function_calls 块内），三方并行。与传统单 spawn 不同，主控需额外监控：

- **三方并行心跳看总和**：T1+T2+T6 三个 子代理 都心跳后才视为「三方并行存活」——任一 30s 未心跳 = 该 T 心跳异常
- **三方独立超时**（v2.1.8 教训 #58）：8 分钟硬卡对每个 T **独立生效**—— T1 8 分钟未完成 ≠ T2 T6 也超；主控只 kill 超时的那个，其他不受影响
- **runtime vs 墙钟区分**（v2.1.8 教训 #58）：runtime = 模型推理 + 工具调用纯耗时；墙钟 = runtime + DSH 调度 + 子会话启动 + 文件落盘；8 分钟硬卡**指的是墙钟**（含调度延迟），runtime 通常 1-3 分钟
- **失败隔离**：T1 失败不影响 T2/T6 继续；T6 失败不影响 T1/T2；主控收到失败 ack 后标 `Failed` + T0 合并层标「案例缺角」/「文献缺角」/「数据缺角」对应降级
- **三方同步 ack 节点**：三方共享同一 Phase 1 阶段行的 status.md（避免三份独立 status 难以合并）
