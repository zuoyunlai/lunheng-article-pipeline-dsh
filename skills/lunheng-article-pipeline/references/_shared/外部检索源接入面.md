## 一、为什么做这件事

主人 2026-09-26 提问"**论衡 T1/T2/T3 能不能自动调用 firecrawl / tavily / AI4Scholar / exa / consensus / search_google_scholar 这 6 个源**"——核实后发现：

- ✅ **DSH 宿主能力面已具备**（全部工具已注册，subagent 继承主会话工具面 → 主会话配 key 后 T1/T2/T3 都能看得到）。
- ⚠️ **论衡 T1/T2/T3 卡里的默认动作没指引它们去用**——之前默认只写 `web_search` + `web_fetch`，6 源只在「自动降级路径」或「T1b 显式要求」时偶有提及。

**含义**：能力面在、指引面缺——T1/T2/T3 即便看得到 firecrawl/tavily/exa 等工具，**默认不会主动调**。本文档是**单一真源**：把 6 源可调用性、适用场景、计费语义、Key 边界、调用策略集中登记；T1/T2/T3 卡按本文档做默认动作。

> ⚠️ **本文件不改变运行期代码**（`lib/tools.js` / `lib/index.js` / `cordis.patch.yml` / `package.json` 一律不动）——它只改"agent 该做什么"。运行期抽象（论衡原生聚合工具）留给方案 2 后续推进。

## 三、关键澄清（避免重蹈「门在此却不生效」）

> **来源**：v18.18.x 教训「已修的记载只覆盖了它当时盯住的那一处」+ v18.12.x 教训「门在此却不生效」——本文档必须把这几个边界讲清楚，否则「6 源接入 = 假绿」。

### 3.1 工具面在 ≠ 指引面在

即使宿主开通了上述所有源，**T1/T2/T3 默认仍只会调 `web_search`**——除非 T1/T2/T3 卡里**写明**「请按 6 源可用性调用」。

- 本批（v18.21.2）**只在 T1/T2/T3 卡的职责段写了**「**默认学术层 + 默认网页层 + 备用层**」——这就是「指引面」。
- 不写 = T1/T2/T3 不会主动用 = 6 源接入是空话。
- **反证用例**（必做）：把 T1/T2/T3 任一卡的"接入面文档引用"那行删掉 → 测试应判红。

### 3.2 引擎降级 ≠ 必然命中

`web_search(engine=bing)` 默认走 bing，bing 成功就**不**降级。要保证某个源被命中：
- **方案 A**：改主会话 dsh 配置 `engine=firecrawl`（仅 firecrawl 适合做默认引擎的情况极少——学术检索场景 bing 更稳）；
- **方案 B**（**推荐**）：**直接调用对应 DSH 工具**（如 `search_papers` / `search_arxiv` / `web_search` + 引擎参数覆盖）——后者**可控、可观测、可计费**。

**T1/T2/T3 卡的指引采用方案 B**：默认层是 DSH 工具调用（`search_papers` + `search_arxiv` + `web_search`），不依赖降级链的偶然命中。

### 3.3 subagent 工具可见性

DSH subagent 在 spawn 时**继承主会话的全部工具面**（`docs/subsystems/core.md:499-524` 的 `composeFrom`：子代理通过「加入同一组合」继承能力）。**主会话配了 `tavily_api_key` / `firecrawl_api_key` / `exa_api_key` / `consensus_api_key` / `AI4Scholar` 积分，spawn 出去的 T1/T2/T3 也看得到**——这是 DSH 宿主行为，**论衡无法在插件层控制**。

- **诚实边界**（v18.18.x 教训）：如果主会话没配 key，**T1/T2/T3 也调不到**——不要把"工具可见"等同于"调得通"。
- **任务简报 §启用扩展检索源 的勾选项**是给主人**显式声明 key 可用性**的接口，**不勾选 = 不调**，避免主控默认调不到的源 → 静默失败。

### 3.5 Bing 偏置 + 通用性兜底（v18.21.3 现场实测新增）

> **来源**：v18.21.2 真实项目实测（`run/_v18.21.2_test/中国新能源车/`）—— T2/T3 subagent 亲遇 Bing 中文流量偏置。主人 2026-09-26「切 Bing 偏置会不会影响插件通用性」提问的反哺。

#### 3.5.1 现象

- **Bing backend 中文流量偏置严重**——英文专业查询（如 `"NEV" "China" export trade policy academic`）被污染为中文游戏 / 电商 / 通用词条
- 同一查询在 **tavily / exa**（均 **keyless**）上返回学术 PDF + 智库 + 政策库——**质量远超 Bing**
- **不限于论衡**——这是 DSH `web_search(engine=bing)` 的宿主行为，**任何宿主**遇到 Bing 都可能触发

#### 3.5.2 通用性兜底（实测已验证）

> 🧠 **关键事实**（v18.21.2 主会话实测 + DSH free-search 插件文档）：**exa / tavily / firecrawl 全部 keyless 可用**——切 Bing 不等于"必须装 key"。

| 引擎 | 本机 keyless 实测 | 其他宿主 keyless 可用性 | 推荐 |
|---|---|---|---|
| **tavily** | **OK，2 结果** | 几乎所有 DSH 部署 | **推荐主引擎**（时效性强）|
| **exa** | **OK，2 结果** | 几乎所有 DSH 部署 | 语义检索强 |
| **firecrawl** | **OK，2 结果** | 几乎所有 DSH 部署 | 反爬强 |
| **anysearch** | OK | keyless 通用兜底 | 兜底用 |
| **parallel** | OK | keyless 通用兜底 | 兜底用 |
| **keenable** | OK | keyless 通用兜底 | 兜底用 |
| bing | OK 但偏置 | 通用 | 不推荐作主引擎 |
| ddg / searxng | 本机失败 | 网络相关 | 不稳定 |

→ **任何宿主**至少 4 个 keyless 引擎可用（anysearch / parallel / keenable + 至少 1 个）；**Bing 失败时降级链必能往下走**。

#### 3.5.3 三层防护（主人 2026-09-26 显式授权）

| 层 | 改什么 | 影响通用性 | 谁负责 |
|---|---|---|---|
| **A · 文档** | 本节（§3.5）——把"Bing 偏置 + 通用性兜底"写进真源文档 | **0** | 论衡插件 |
| **B · 卡** | T1/T2/T3 卡**强约束**：主轮默认层**不开** `web_search`（学术源不够时**才**启用）| **0** | 论衡插件 |
| **C · 本机配置** | dsh 启动配置 `engine=tavily`（仅本机受益）| **仅本机** | DSH 宿主 |

**B 是关键**——把 `web_search` 从 T1/T2/T3 默认层降到备用层，**结构性**消除"主轮依赖 Bing"的同型病。

#### 3.5.5 边界声明

- **A 不影响通用性**：文档是 host-agnostic，**任何宿主**读到的都是同一份
- **B 不影响通用性**：卡的强约束是 host-agnostic（T1/T2/T3 任何宿主下都不把 web_search 放默认层）

## 四、调用策略（与 v2.5.2-dsh.7 + v2.5.2-dsh.15 三件套接入）

> **保留**：T1/T2/T3 卡已有的「**失败熔断 + 自动降级 + 边际饱和**」三件套**不动**——本批 6 源接入面**纳入**这三件套，**不另起炉灶**。

### 4.1 默认 3 源 + 备用 3 源（硬约束）

- **默认并行 3 源**（T1/T2/T3 主轮必跑）：
  - T1：`search_papers`（默认含 Semantic Scholar + PubMed）+ `search_arxiv`（预印本）+ `web_fetch`（定向抓取）——**主轮默认层不含 `web_search`**（v18.21.3 主人授权强约束：`web_search` 实测存在 Bing 中文流量偏置，结构性消除「主轮依赖 Bing」；`web_search` 仅作**候选 URL 列表生成器**，见 §3.5.3 与 `agents/01-文献检索-literature-scout.md` §源面。**2026-09-29 跨文档对账修复**：本行原写 `+ web_search`，与 01 卡的 v18.21.3 强约束互斥）
  - T2：`search_papers`（文献计量方向才有）+ `web_search` + `web_fetch`
  - T3：`web_search` + `web_fetch` + `search_papers`（学术背书用）
- **备用 3 源**（主轮**未饱和**（v2.5.2-dsh.15）才启用）：
  - T1：`search_google_scholar`（按信用点）→ `search_semantic_bulk` → `search_biorxiv` / `search_medrxiv`（按主题）
  - T2：`tavily`（如 key 配）→ `exa`（如 key 配）→ `firecrawl`（如 key 配）
  - T3：`firecrawl`（如 key 配）→ `search_semantic` → Consensus（**本批不在 T1/T2/T3 用**，留写手阶段）

### 4.2 失败熔断（源级独立）

- 同一源连续 2 次无结果 / 错误 / 429 限流 → 第 3 次**自动停止**重试
- 记录到交接报告「**已失败源清单**」（**每个源独立一份**——firecrawl 失败不等于 tavily 失败）
- 切换 query 关键词（去掉限定词、拆子主题、加同义词）→ 下一轮仍按「默认 3 源 + 备用 3 源」硬约束
- **节省**：单源 5 次重试 × ~5K cacheRead = 25K；熔断后 ≤ 2 次 = 10K（v2.5.2-dsh.7 同型）

### 4.3 自动降级（源间 / 引擎间）

- **源间降级**：`search_papers` 失败 → `search_arxiv` 失败 → `web_search`；**不是**同时跑全部后挑最好的（避免 token 浪费）
- **引擎降级**（`web_search` 内部）：bing → exa → tavily → keenable → firecrawl → parallel → ddg → searxng → anysearch（free-search 插件默认序）
- **彻底失败**：5 次切换 query + 2 次备用源都未命中 → 标「该子主题 Permanent Gap」，交接报告交接给 T0 主控，主控在 Phase 2 启动时显式标「文献缺角 → 缺角论点降级为观点」

### 4.4 边际饱和 + 首轮软预算（v2.5.2-dsh.15；**保持**）

- **首轮软预算 ≤40 步**（T1 Phase 1.5 补检索另受 ≤30 步铁律约束）——6 源接入**不增预算**
- **边际饱和即停**：连续 2 轮检索（每轮 ≥3 次 query/URL）新增有效卡片数 = 0 → 判定该子主题饱和
- **饱和 → 启用备用 3 源**（本批新增：饱和判停后**才**启用 `search_google_scholar` 等备用源——避免默认层浪费 token）
- **饱和 ≠ 缺口**：饱和段照实记「已检到饱和，未检索到 X 类证据」；**不得**因饱和补占位卡
- **交接报告必报一行**：`检索预算：已用 N 步 ｜ 饱和判定：<子主题>=饱和/未饱和 ｜ 已用源：<6 源中实际命中的>`——**新增「已用源」字段**让 T7 审计能机械判定「T1 是否真的调到了接入面源」

### 4.5 成本控制

- `search_google_scholar` **不在 T1 默认层**——饱和后才启用，且**主控在任务简报勾选**才算授权
- `auto_cite`（已接入，**不在本批接入面内**）——T5 写手后补标注阶段；详见 `auto_cite-integration.md`
- **跑满一次主轮最高成本** ≈ 50-150 信用点（Google Scholar）+ 0-30 信用点（其他）—— 主控须在任务简报 §启用扩展检索源 显式声明
- **T2 重试预算的成本口径（v18.35.0 自 02 卡迁入）**：单源 5 次重试（每次 ~5K 上下文）≈ 25K cacheRead → 熔断后 ≤2 次 ≈ 10K（**口径 = 单源重试的上下文预算；模型估算，无实测样本**）。本机实测（`node scripts/token-budget.mjs --roles`）：**T2 共 4 会话、聚合 cacheRead 1.44M**（含首轮停滞/重跑冗余）。**旧版 02 卡引用的单个 18.9M 数字已无法复验**（该会话投影不在本机缓存中），故不再引用，改以聚合口径为准——**迁移时原样保留这条自我更正**，避免它随卡片瘦身一起消失。
- **检索式批量纪律（2026-09-29 外部借鉴 context-mode，B3）**：同一轮的多条检索式应**批量提交**（一次多查询），**不得**用 N 次近似重复的单查询代替一次多查询。**且「饱和停」判据针对「新增」而非「次数」**——判据是「连续 2 轮无新增卡」，不是「调用了几次」；两者混同会同时导致**过早停**（把次数当饱和）与**空转**（次数没到就不敢停）。
  > **依据与边界**：context-mode 的 flood-guard 防的正是「用几十次独立小检索代替一次批量检索」把上下文刷爆（`src/search/flood-guard.ts:4-8`），其工具层纪律为「NEVER make multiple separate calls — put all queries in one array」。**本处只借行为纪律，不引入任何限流机制**——论衡无工具拦截层，运行时限流会误伤正当的多轮补检（见 `DSH-集成方案.md` §六 自我限制）。
