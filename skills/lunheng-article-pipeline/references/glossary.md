## 一、核心角色（9 个独立角色 T1-T9，互不可替代；T0 = 主控身份，兼任 T8 执行者）

> **v2.5.2-dsh.8 角色语义定案（主人指令）**：**9 个角色 T1-T9（文献/数据/案例/分析/写作/批判/审计/终检/审稿）各自独立、不可相互替代**，每个都有独立角色卡（`references/agents/01~09`）；**T8 终检是独立角色**，执行者由主控担任（**主控 = T0 调度 + T8 终检执行双重身份**），T8 不 spawn 子代理；**T9 审稿可选但默认选中，学术论文必选**。
> **历史（v2.3.0 重构 + v2.4.0 加 T9，教训 #116）**：原 8 角色 → v2.3.0 角色编号重构（T6 案例检索→T3、批判→T6、审计→T7、终检→T8）+ v2.4.0 新增 T9 同行评审。编号 = 流水线 Phase 顺序：T1-T3 检索 / T4-T5 加工 / T6-T9 防御。

### T0 - 主控（Coordinator，= T8 终检执行者）
- **职责**：流程编排 + 任务派发 + 质量把关 + 人机交互 + **以 T8 身份亲完成终检**（v2.5.2-dsh.8：主控 = T0 + T8 双重身份；T8 仍是独立角色，只是执行者由主控担任，不 spawn 子代理）
- **不做**：不替代其他 8 个子代理角色执行具体工作（T1-T7/T9 必须 spawn 独立子代理，唯一例外 T8 由主控亲执行）
- **关键协议**：Phase 0 同意关卡 / spawn-yield 模式 / 完成验证铁律
- **T8 终检职责**：M 门 23 项复核 + 证据包自动生成 + AI 使用声明 + 交付物完整性 + 引用闭环 → `final/定稿.md` + `final/证据包/` + `final/交付说明.md`（详见 [`agents/08-终检-finalizer.md`](agents/08-终检-finalizer.md)）

### T1 - 文献侦查（Literature Scout）
- **职责**：已发布学术文献 / 政策文件 / 统计年鉴检索
- **输出**：`[Lxx]` 文献卡
- **并行模式**：T1 ∥ T2 ∥ **T3** 独立运行（v2.3.0 改 T6→T3）

### T2 - 数据检索（Data Scout）
- **职责**：已发布统计数据 / 行业报告 / 新闻数据检索
- **输出**：`[Dxx]` 数据卡
- **铁律**（v2.1.8）：只产数据卡，不产案例卡
- **并行模式**：T1 ∥ T2 ∥ **T3** 独立运行

### T3 - 案例检索（Case Scout，v2.3.0 重命名原 T6→T3）
- **职责**：案例/事件/人物/企业案例检索
- **输出**：`[Cxx]` 案例卡
- **0 条空卡协议**：0 条场景输出 `[C-空]`
- **并行模式**：T1 ∥ T2 ∥ T3 独立运行（v2.1.8 + v2.3.0 重命名）
- **任何量级必 spawn**：含 cases = 0 也走空卡协议

### T4 - 分析（Analyst，v2.3.0 改 T3→T4）
- **职责**：论点拆解 + 论证结构设计 + 大纲编写
- **输入**：T1 + T2 + T3 全部完成后触发（v2.3.0 改 T6→T3）
- **输出**：`analysis/分析大纲.md`

### T5 - 写手（Writer，v2.3.0 改 T4→T5）
- **职责**：正文撰写 + 修订执行
- **铁律**：禁做清单 10 项（AI 去味）
- **独立性**：修订轮必须重新 spawn，不能主控代执行
- **输出**：`drafts/初稿-vN.md` + `drafts/修订说明-vN.md`（修订轮）+ **`analysis/素材加载清单.md`**（v2.5.2-dsh.17：每轮覆盖写「## 已加载」= 实际读过的编号；正文引用须 ⊆ 它，机检 M-Form-11）

### T6 - 批判伙伴（Critical Companion，v2.3.0 重命名原 T8→T6）
- **职责**：批判性审查（非对抗性，从反方攻击论证）
- **触发**：T5 写手 v2（含主人洞察）完成后、T7 审计前（v2.3.0 改 T8→T5/T8→T7）
- **触发阶段**：**Phase 3.6**（v2.3.0 引入的独立节点）
- **输出**：`analysis/批判报告-vN.md`
- **定位**（v2.2.2）：不是 adversarial，是 critical companion
- **攻击对象**：v2（含主人洞察），不是 v1

> **v2.3.0 关键标识**：本角色在 §四 三检索员段 + §十一 主控 vs 子代理段 + 派发话术段均有 **T6 批判** / Phase 3.6 / T6 独立早期攻击 等显式标注。

### T7 - 审计（Auditor，v2.3.0 改 T5→T7）
- **职责**：质量审计（G0-G14，v2.4.0 加 G14）+ 修订任务书
- **输出**：`audits/审计报告-vN.md`
- **双完整性门**：T2.5（数据卡完整性）+ T7.5（引用完整性，v2.3.0 编号重构后定名 T7.5）

### T9 - 同行评审（Peer Reviewer，v2.4.0 新增，v2.5.2-dsh.8 语义定案）
- **职责**：论文投稿前的预演审稿（**可选但默认选中**——v2.5.2-dsh.8 主人指令：默认选中，**学术论文必选**；非学术文章主人 Phase 0 可取消）
- **触发阶段**：**Phase 4.5**（终稿前 + T6 批判伙伴 + G14 检测器并行）
- **输出**：`audits/审稿报告-v[N].md`
- **6 维度评分**：原创性 / 方法论 / 证据强度 / 论证结构 / 写作质量 / 引文规范（每维度 1-5 分，总分 30）
- **判定**：26-30 accept / 21-25 minor revision / 16-20 major revision / <16 reject
- **与 T6/T7 的边界**：T6 攻击论证强度（不评分）/ T7 核验形式/事实（不评分）/ **T9 评分**（不做形式核验）
- **开关**（v2.5.2-dsh.8 定案）：默认选中；**学术论文 = 必选不可关**；行业分析/商业评论/公众号默认选中，主人 Phase 0 可取消（v2.4.6 旧口径「公众号默认关闭」废止——主人指令明确 T9 默认选中）
- **借鉴**：academic-paper-reviewer（第三方同类插件，v2.4.0 论衡哲学化）
- **不替代真实审稿**：仅 pre-submission 模拟，论文投稿后还需真实审稿人审稿

### T8 - 终检（独立角色，主控亲执行）

> ✅ **v2.5.2-dsh.8 语义修正（主人指令，取代下方旧澄清）**：T8 终检是**独立角色**（有独立角色卡 [`agents/08-终检-finalizer.md`](agents/08-终检-finalizer.md)），**不可由 T5/T6/T7 兼任替代**；执行者由主控担任（主控 = T0 + T8 双重身份），T8 **不 spawn 子代理**——「角色独立」与「执行者 = 主控」不矛盾：独立性指职责边界不可替代，执行者指由谁完成。

- **职责**：M 门 23 项复核 + 终检必查 15 项 + 证据包自动生成 + 交付物完整性 + AI 使用声明填实

## 二、三层防御体系

### M 门（形式合规门）
- **性质**：机械化、零人工判断、可自动化
- **算法**：Python 伪代码 + Bash 验证命令
- **执行模型**（v2.2.12 澄清，v2.5.2-dsh.4 审计修订）：
  - ✅ **主控 LLM 推理判定**：主控用 `read` 读取算法文档，按伪代码**推理**判定
  - ✅ **白名单脚本机械判定**：M-Form 1-11 + M-Exist 1-10 + M-Integrity-1（共 22 项）走 `scripts/m-gate-check.mjs`（零 LLM，可复现 exit code）
  - ❌ **不执行任意 shell**：算法中的 `grep`/`diff`/`sha256sum`/`wc` 等命令示例仅供人类手动复核，agent 优先用白名单脚本/read 推理
- **覆盖范围**：23 项检查（M-Form 11 项 + M-Exist 10 项 + M-Integrity 2 项）
- **单一真源**：`references/_shared/M-Gate-Algorithm.md`

### F 模式（失败模式清单）
- **性质**：面向用户的叙事层，解释"为什么要这么做"
- **覆盖范围**：F1-F9（v2.2.2）
  - F1：幻觉引用（引用真实但用错语境 / 完全捏造）
  - F2：幻觉数据（数字真实但过期 / 完全捏造）
  - F3：早期框架锁定（分析大纲先入为主）
  - F4：论证自洽陷阱（论据与论点逻辑脱节）
  - F5：拼凑式章节断裂（章节无过渡 / 过度对称）
  - F6：过度防御口吻（破坏客观分析视角）
  - F7：主人风格模仿失真（主人洞察当作者声音）
  - F8：数据信任失败（来源混入 / 转引未标注 / 信任级别遗漏）
  - F9：论证强度不足（论据单一 / 因果倒置 / 反方走过场）
- **单一真源**：`references/_shared/failure-modes.md`

### G 清单（质量审计清单）

  - G0：覆盖度检查（防选题漂移）
  - G0.5：视角一致性（v2.3 新增，防第一人称经历）

  - G2.5：案例核验（v2.2 新增，多源交叉）
  - G3：逻辑核验（论点-论据-因果）
  - G4：结构与格式（文末四节完整性）
  - G5：学术规范（查重 / AI 痕迹）
  - G6：论据类型自标（v2.3 新增）
  - G7：原创性审计（先行者差异点）

## 三、数据信任级别（v2.2.1 核心机制）

### 🟢 Level 1：已发布公开数据（最高信任）
- **定义**：通过正规渠道发布的官方/学术数据
- **示例**：
  - 官方统计年鉴（国家统计局）
  - 学术论文中的研究数据（已发表）
  - 行业协会公开报告（中国汽车工业协会）
- **验证要求**：来源 URL 可核验（已发布数据，G1/G2 核验）
- **引用形式**：内联引用 `(来源，年份)` 或编号引用 `[Dxx]`

### 🟡 Level 2：主人投喂数据（中信任）
- **定义**：主人提供的一手数据、内部资料、专家访谈记录
- **示例**：
  - 主人提供的企业内部销售数据
  - 主人进行的问卷调查结果
  - 主人的实地考察笔记
- **验证要求**：主人确认记录（主人投喂数据）
- **引用形式**：标注 `[主人提供]` 或 `[内部数据]`

### 🔴 Level 3：二手转引（低信任，严格限制）
- **定义**：从新闻报道、自媒体、二手资料转引的数据
- **限制条件**（v2.2.1 铁律）：
  1. 必须回溯到一次文献（新闻/报告必须引出原始来源）
  2. 顶部标注 `[二手转引]` 警告
  3. **T7** 审计 G12 专项检查（v2.3.0 改 T5→T7）
- **禁止场景**：核心论据、统计数据、精确数字

### 基线引用 [D-基-xx-xx] 格式（v2.3.7 论文三实战升级，P1-2）

- **背景**：论衡 v2.3.7 论文三实战中 T2 数据检索员产出 6 条基线数据（资金/阈值/案例/其他），命名为 `[D-基-R-01]` `[D-基-T-01]` `[D-基-C-01]` `[D-基-E-01]` 等。但 T5 写手传递时可能简化成"基线一致"或具体数字，导致基线编号格式丢失，影响证据可追溯性。v2.3.7 升级后**基线数据编号格式正式规范化**。
- **格式定义**：`[D-基-{类别}-{序号}]`
  - `D-基`：基线数据前缀（区别于普通数据卡 `[Dxx]`）
  - `{类别}`：单字符类别码
    - `R` = Resource（资源/资金/成本）
    - `T` = Threshold（阈值/拐点/临界值）
    - `C` = Case（案例事件）
    - `E` = Evidence（其他证据）
  - `{序号}`：两位数序号（01-99），项目内唯一
- **示例**：
  - `[D-基-R-01]` = 资金基线第 1 条（如"开模打样成本"）
  - `[D-基-T-01]` = 阈值基线第 1 条（如"60% 一致性阈值"）
  - `[D-基-C-01]` = 案例基线第 1 条（如"某家居品牌原创失败事件"）
  - `[D-基-E-01]` = 其他证据基线第 1 条（如"10.6% 市场增速"）
- **数据卡模板要求**：T2 数据检索员产出基线时，必须按上述格式在数据卡 entry 顶部标 `**基线编号**：[D-基-R-01]` 字段。
- **写手传递要求**：写手 v1/v2/v3/v4/v5 引用基线数据时，**必须保留完整 `[D-基-xx-xx]` 格式**，不允许简化成"基线一致"或裸数字。M-Form-6 + M-Exist-3 双格式检查会拦截丢失基线编号的引用。
- **任务简报要求**：§四 数据基线段必填基线编号清单（如"资金基线：[D-基-R-01]；阈值基线：[D-基-T-01]"），写手 v1 看清单引用。
- **T7 审计检查**：G12 数据信任一致性 + 基线编号双格式检查——丢失编号 = P1 必补。

### 修订回环 ≤2 轮降级（v2.2.0，v2.3.1 定义细化 + v2.5.2-dsh.4 双轨制定案，教训 #64 + #120）
**规则（双轨制，v2.3.7-dsh.8 语义定案）**：
- **A 轨 = 审计打回轮（硬约束 ≤2 轮）**：T7 审计打回 → T5 修订 → T7 复核为 1 轮；第 2 轮打回 → T5 再修订 → T7 再复核；第 3 轮 → Acknowledged Limitations 模式（自动降级为人工介入）
- **B 轨 = 主控触发轮（不限额，不计入 2 轮预算）**：主人深度洞察（Phase 3.5）/ T6 批判反馈 / T9 审稿建议 / G14 检测修订 —— 这些是**质量增益轮**，与审计打回独立计数；同一轮修订可合并消化多条反馈（如 G14 与 T6 并行产出 → 合并为一份 T5 修订清单）
- **T8 小幅修补权限（v2.3.1 新增）**：≤字数 5% / AI 披露修正 / 元叙事清理 / P1-D 事实错误 → T8 亲修；结构性 P1-A/B/C + P0 → T5 独立写手（审计打回轮必须 spawn 独立写手）
- **P1 分级（v2.3.1 新增）**：P1-A/B/C（论证补强/结构缺失/反方缺失）→ T5 重启；P1-D（引用格式/元数据/漏引/拼写）→ T8 亲修

- 防止无限循环（教训 #64）

## 五、工具能力边界（DSH：v2.5.2-dsh.0 前置声明）

- **shell 使用（v2.5.2-dsh.4 审计修订）**：论衡**不是零 exec**——主控按需执行随包 **9 个** `scripts/*.mjs` + 有限验证命令（ls/stat/wc/cp/diff/Get-FileHash 等）；算法文档中的 `grep`/`diff`/`sha256sum`/`wc` 等示例命令是给人类主人手动复核的参考，agent 优先用白名单脚本与 read 工具（版本基线发布版中的「（检查）」占位符同样按此处理）
- **主流程**：LLM 推理 + 文件读写 + Web 检索 + 白名单脚本；除白名单外默认不执行任意 shell 命令（经主人同意除外）

### 第 1 层：Git（真源版本控制）
- **Commit**：（维护由开发者完成，使用者无需 git 操作）
- **Tag**：（维护由开发者完成，使用者无需 git 操作）
- **Push**：（维护由开发者完成，使用者无需 git 操作）

### 第 2 层：技能文档（18 文件版本号同步）
- `SKILL.md` frontmatter `version: X.Y.Z`（版本号单一真源）
  > **契约定位（v18.0.0 对齐官方）**：DSH 官方的 skill frontmatter 契约只定义 **`name`（必填，kebab-case）/ `description`（必填）/ `whenToUse`（可选路由指引）/ `disable-model-invocation` / `user-invocable`** 五个键；**`version` 不在官方契约内**——它落入 `metadata: Record<string, unknown>`（provider-specific metadata），实测 `dsh-skill-filesystem` 会**原样保留、不警告、不拒绝**。
  > 因此：① 本技能把 `version` 当版本号单一真源**是允许的自定义用法**，但**不得假定任何其他 DSH 组件会读取它**（模型目录更不会）；② 下游工具要读版本号，应显式从 `metadata` 取，或改用 `package.json#version`（后者才是 npm/DSH 通用的版本真源）；③ 若未来官方 frontmatter 引入同名的 `version` 键，须复核本技能用法是否冲突。

## 九、外部服务声明（v2.1.2）

### 🌐 涉及的外部服务
1. **Web 检索 provider**（DSH 配置的 web_search / web_fetch 提供方，可能含 Google/Bing）

> **内置功能（零外发）**：**数据图表 SVG + 封面 SVG 矢量风**由主控用 `write` 工具本地手写矢量图，**零外发，不依赖任何外部服务**（符合「零 exec」哲学）。仅主人勾选「启用封面生成」并配图像 MCP 时才外发（可选默认关闭）。

### 🔒 数据流方向
- **向外发送**：
  - 检索关键词（web_search / web_search）
  - 目标 URL（web_fetch / web_fetch）
  - 图像生成 prompt（图像 MCP，默认关闭，需主人同意）
  - **大模型推理全文**：文献卡/数据卡/案例卡/草稿/大纲/正文全文发送给当前模型 provider
- **不发送**：原始文献内容 / 主人投喂数据 / 中间产物（除非主人显式同意外发；大模型推理全文属上列外发项）

### 🛡️ 主人拒绝外部服务时的备选方案
1. **Web 检索**：主人手动提供文献/数据 PDF
2. **封面生成**：

## 十一、关键术语

### 主控 vs 子代理
- **主控**：T0，流程编排者，不替代子代理执行具体工作（除 T8 终检——主控 = T0 调度 + T8 终检执行双重身份）
- **子代理**：**T1-T9**，专项任务执行者（v2.5.2-dsh.8 语义定案：9 个独立角色各有独立子代理身份，**唯一例外 T8 终检由主控亲执行不 spawn**——T1-T7 + T9 必须 spawn 独立子代理，不可由主控代做）

### spawn vs yield
- **spawn**：主控通过 `subagent` 创建子代理
- **yield**：主控通过 `等完成通知` 挂起等待子代理完成

### 真源 vs 副本
- **真源**：论衡 skill 目录 `references/`（本 skill 的流水线真源）
- **副本**：发布渠道 ZIP / GitHub 仓库

### 蒸馏 vs 压缩
- **蒸馏**（Distillation）：从日记忆提炼长期记忆（有损压缩）
- **压缩**（Compact）：减少重复内容（无损压缩）

## 十二、本技能自用术语与文档约定（v18.0.0 新增）

> **为什么单列这一节**：DSH 官方对仓库文档的要求是「用直接、具体的术语，**不用隐喻**；**不保留审查历史**；一事实一处」（见官方 `AGENTS.md` §Type safety and documentation）。本技能**刻意偏离**了后两条，此节把偏离**显式声明**，以免后续维护者（或官方规范审阅）误以为是疏漏。

### 12.1 自用术语（**非通用术语**，仅在论衡语境内有定义）

| 术语 | 在本技能中的确切含义 | 不是 |
|---|---|---|
| **承重墙 / 承重证据** | 支撑力最强的**单条**证据（每论点标一条 `承重证据 top1`）；同一证据被 ≥3 个论点标为承重即**超载** | 不是建筑隐喻，也不是「重点段落」的泛称 |
| **三角验证** | 论点必须能映射到 **`[Lxx]`（文献）+ `[Dxx]`（数据）+ `[Cxx]`（案例）** 三类证据（涉事件者必须有案例） | 不是「多方求证」的泛称，是**三类证据编号的硬约束** |
| **M 门** | `M-Form 11 + M-Exist 10 + M-Integrity 2 = 23 项`形式合规门，由 `scripts/m-gate-check.mjs` 机械判定 + T8 LLM 复核 | 不是「质量评分」 |
| **G 清单 / G0-G14** | 审计员逐项执行的 **15 主项 + 3 子项**检查（覆盖度 / 引用核验 / 溯源 / 逻辑 / 格式 / 原创性 / 时效 / 信任级别 / AI 披露 / 中文 AI 痕迹） | 不是「评分维度」 |
| **F 模式 / F1-F9** | **失败模式**清单（幻觉引用 / 幻觉数据 / 早期框架锁定 / 论证自洽陷阱 / 拼凑式断裂 / 过度防御 / 风格失真 / 数据信任失败 / 论证强度不足） | 不是「功能编号」 |
| **闸门（T2.5 / T7.5）** | 主控在两个阶段边界执行的**完整性检查点**（不绕过即不派下一阶段） | 不是 DSH 的 approval 机制 |
| **回环 / 修订轮次** | 审计打回 → 写手修订 → 复核，**A 轨 ≤2 轮**硬约束；主控触发轮（T6/T9/G14/主人洞察）为 **B 轨**不限额 | 不是「迭代次数」 |
| **卡级 / 修卡** | 素材卡（文献/数据/案例）层面的字段缺失与修补（属 T7 建议，非正文缺陷） | —— |
| **筛选器 vs 判别器** | 脚本 = **筛子**（可能误报/漏报），T7/T8 = **判别器**（逐项复核裁定）；实测约 45% 的 M 门项需人工修正 | 不是「自动化程度」之分 |

### 12.2 文档约定（与官方规范的刻意偏离）

| 项 | 官方规范 | 本技能做法 | 理由与代价 |
|---|---|---|---|
| **隐喻** | 「Do not use metaphors」 | 使用上表自用术语（在 12.1 统一定义） | **理由**：中文写作场景下这些术语已成为团队内稳定黑话，且与英文术语（gate / audit / failure mode）无一对一直译；**代价**：新人需先读本节 |
