- 反哺报告**默认只产出**，**不自动修改任何角色卡**（`references/agents/*.md`，即本 skill 目录下的角色卡）
- 主控会话结束时不调用 `edit` / `write` 工具 commit 反哺规则到角色卡
- **任何对角色卡的修改必须经主人人工 review 后手动 merge**，主控在交付说明里列出「建议 merge 的反哺规则」清单，等主人点头
- 反哺报告本身（`audits/反哺报告-vN.md`）作为知识保留，但角色卡修改路径已封死

### ⚠️ 提议写法：稿件侧优先（v18.11.0 新增，实测教训）

**每条提议必须同时给出「稿件侧修法」与「工具侧修法」两个选项，默认稿件侧优先。**

- **稿件侧修法**：改产物（初稿 / 素材卡 / 交付说明 / 大纲）使其合规——**默认选项**
- **工具侧修法**：改 `scripts/**` 或 `references/**`——**例外**，仅当能证明下列三者之一：
  1. **守规模棱两可**（两份真源互相矛盾，如「承重」既是 M-Form-8 分析术语又是 M-Form-5 禁词）
  2. **实现与规范不一致**（文档这么写、脚本那么做）
  3. **覆盖盲区**（脚本 best-effort 解析误判、正则漏网导致的**假阳性**）

**改工具前必跑回归**：在真源仓库执行 `node --test "tests/**/*.test.mjs"`——**红了即回滚该条**，并把驳回理由写进反哺报告。

> **为什么加这条（实测教训，2026-09-24）**：某项目按反哺报告 v1+v2 落地 18 条提议时，**4 条被回归测试当场驳回**
> （F-1' 删「承重墙」出 M-Form-5 词表 / F-2 头部声明对账降档 / F-6 索引段编号并入全卡集合 / F-7 硬孤儿阈值 10→15）。
> 共同句式是「**某论文触发了这项门 → 说明门太严 → 放宽它**」，但真因拆解后**4 个「门太严」全是「稿件不合规」**：
> 沿用流水线话术、索引表缺方括号、孤儿是真的。其中 F-6 最危险——并入后 `idxIds ≡ bodyIds`，
> 「索引缺条」检查**不是放宽而是彻底关停**。
>
> **判据一句话：门的严格度不是问题，产物的合规度才是。**

## 交接报告（F8 补完，与其他 6 角色卡对齐）

**审计员交付审计报告 + 反哺报告时，必须按以下六要素交付**（与所有角色一致）：
1. **做了什么**：审计范围（覆盖几节/几轮）+ 反哺报告沉淀了几条建议
2. **产物在哪**：`audits/审计报告-vN.md` + `audits/反哺报告-vN.md`（两个文件，主控一并收）
3. **怎么验证**：审计报告里的 G0-G14 检查项是否全覆盖 + 反哺规则是否可执行
4. **已知问题**：审计没覆盖的盲区（如本轮没抽到的引用、未做的三角验证维度）
5. **下一步**：建议主控「接受 / 要求 T5 修订 / 升级主人决定」（注：v18.8.0 聚合）
6. **状态机更新**：status.md 对应行已置为 Review/Done；如有失败写明原因

**审计员特异职责**：交接报告必须明确审计结论——**通过 / 修订 ≤2 轮 / 升级主人决定**三档之一。审计员不下「接受」决定，主控才下。
