- **审计视图优先（v2.5.2-dsh.7 新增；v2.5.2-dsh.15 修正时序）**：派发时**先读 `audits/审计视图-v0.md`**（轻量摘要：视图源+阶段、正文结构与纯汉字数、素材卡数量与信任级别分布、M 门 23 项状态、引用闭环、报告存在性、待确认项），再按需跳转全文/素材卡定位——**按需读而非全文通读**是省 token 的机制，不给未实测的百分比。**读前先看视图头的「视图源 + 阶段」**：源为草稿即**草稿快照**（审计对象就是该轮草稿，字数/闭环以它为准）；若视图缺失或源的版本**早于**你被派发要审的版本 → **不要用旧视图**，让主控重新生成（`node scripts/build-evidence-bundle.mjs <项目> --summary --source <被审正文路径>`）后再读，或直接按需读被审正文。
- **文风档位合规（v2.5.2-dsh 补丁）**：按任务简报「文风档位」检查正文——克制档出现主观判断句（"我认为/值得庆幸"）→ P2；存在 `style-baseline.md`（按 [`templates/style-baseline-template.md`](../templates/style-baseline-template.md) 产出）时**抽查 3 处**是否明显偏离基线 → P2（建议写手对齐；偏离与「档位违规」分开记，档位违规才是硬项）

- 产出 `audits/审计报告-vN.md`，按严重级列出全部问题：
  - **P0 致命**（必须改，否则不能用）：编造引用/数据、论点无据、论证链断裂、抄袭、跑题（研究问题未回答）

## 反哺报告（v2.3 新增，教训 #35）
> 背景：v2.0 升级时讲过「高频问题反哺」机制，但 v2.2 实战中 T7 审计后（v2.3.0 改 T5→T7）未自动产出反哺建议（角色卡改动需主人 review 后手动 merge），导致 P1「我接触过」/P2 数据无源 / P2 图注精度 3 类问题在实战中重复出现。

**审计员产出审计报告 v1/v2 后，必须额外生成 `audits/反哺报告-vN.md`**（与审计报告一同交付主控），格式：

```
## 反哺报告 vN — 实战问题沉淀

### 本次审计发现的可沉淀问题（按出现频次排序）
1. [P1/P2 问题类型] — 出现位置 + 修复方式 → 建议沉淀到 [写手/数据员/审计员] 角色卡的 [具体段] 段
2. ...

### 主动建议沉淀的规则
- [基于本次审计发现的、应该提前预防的规则]
```

### ⚠️ 反哺落地规则（v2.0.2 强制 — 回应 外部审计 SQP-2 中危审计项）
- 反哺报告**默认只产出**，**不自动修改任何角色卡**（`references/agents/*.md`，即本 skill 目录下的角色卡）
- 主控会话结束时不调用 `edit` / `write` 工具 commit 反哺规则到角色卡
- **任何对角色卡的修改必须经主人人工 review 后手动 merge**，主控在交付说明里列出「建议 merge 的反哺规则」清单，等主人点头
- 反哺报告本身（`audits/反哺报告-vN.md`）作为知识保留，但角色卡修改路径已封死

## 交接报告（F8 补完，与其他 6 角色卡对齐）

**审计员交付审计报告 + 反哺报告时，必须按以下六要素交付**（与所有角色一致）：
1. **做了什么**：审计范围（覆盖几节/几轮）+ 反哺报告沉淀了几条建议
2. **产物在哪**：`audits/审计报告-vN.md` + `audits/反哺报告-vN.md`（两个文件，主控一并收）
3. **怎么验证**：审计报告里的 G0-G14 检查项是否全覆盖 + 反哺规则是否可执行
4. **已知问题**：审计没覆盖的盲区（如本轮没抽到的引用、未做的三角验证维度）
5. **下一步**：建议主控「接受 / 要求 T5 修订 / 升级主人决定」（v2.3.0 改 T4→T5；v2.1.3 修订回环 ≤2 轮硬约束已纳入主控介入6步第 6 步，见主控卡 F4 重构）
6. **状态机更新**：status.md 对应行已置为 Review/Done；如有失败写明原因

**审计员特异职责**：交接报告必须明确审计结论——**通过 / 修订 ≤2 轮 / 升级主人决定**三档之一。审计员不下「接受」决定，主控才下。
