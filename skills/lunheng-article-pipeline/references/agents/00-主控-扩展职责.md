## 二、status.md 并发写控制（v2.3.7 升级）

**status.md 主控独占写**：实战中主控 edit status.md 失败 2 次（子代理改了 status.md 内容），主控和子代理并发写有 race condition。**v2.3.7 升级后协议**：
- **主控独占写**：`status.md` 只能由主控（主 agent）写入，子代理**不得直接 `write`/`edit`** status.md——子代理通过阶段文件（如 `drafts/<role>-status.json`）或交接报告通知通知主控更新，主控收到信号后独占写入 status.md
- **子代理标识状态**：子代理在产物路径写**自己的阶段文件**（如 `drafts/<role>-status.json`），主控轮询阶段文件后更新到主 status.md
- **修改状态补锁**（可选）：如主控需频繁修改 status.md，在脚本中加 `flock status-md.lock` 文件锁防并发
- **edit 后必复核（v2.5.2-dsh.0 反哺，教训：论艺术中的丑实战 status.md 重复行）**：主控每次 edit status.md 后，**必 grep 复核**——① 无重复的阶段行（如「T7.5 完整性门」出现两行）；② old_string 是否覆盖干净（edit 失败多因 markdown 表格对齐空格漂移）。**edit 用整行替换而非段落替换**（old_string 精确到单个表格行的完整文本），避免相邻行被误伤。出现重复行 → 立即合并修复，不带到下一阶段。

### 闸门公共动作：刷新审计视图（v2.5.2-dsh.15 新增，token 优化落地）

两道闸门 + Phase 2 / 3.6 / 4.5 / 5 **派发前**，主控先跑一次：

```
node scripts/build-evidence-bundle.mjs <run/项目> --summary
```

生成/刷新 `audits/审计视图-v0.md`（源三级回退：`--source` ＞ `final/定稿.md` ＞ `drafts/` 最高版本正文；三者皆无则出「素材阶段视图」），并把该路径写进派发话术的「读」清单（见 `references/dispatch-cards.md` 顶部的派发前置）。

- **为什么是主控的闸门动作**（旧版缺陷，v2.5.2-dsh.15 修）：视图源曾**写死 `final/定稿.md`**，而定稿 Phase 5 才产出——T6(3.6)/T7(4)/T9(4.5) 全部在定稿**之前**运行，于是「文档要求先读、实际读不到」，该优化只对 T8 自己成立。视图生成因此必须是**闸门动作**，不是终检专属动作。
- **「源须 = 被审版本」**：源版本 ≠ 被审版本时视图具误导性——显式 `--source <被审正文路径>` 重新生成后再派发，**不得让子代理拿旧视图审新稿**。
- **播报口径**：闸门播报里写明「审计视图已刷新：源=<路径>（阶段）」，主人可核（对应「闸门留机械证据」）。
- **不重复生成**：同一阶段多次派发同一版本对象时复用现有视图；仅在**对象版本变化**时刷新（避免为省 token 反而多花）。

## 十三、主控进度播报协议（v2.2.10 汇报粒度，DSH 三播报补丁，防主人干等）

主控是**唯一直接对主人说话**的角色。运行中**不许闷头等子代理**——每个关键动作都要「播报」给主人，让主人一眼看出「在跑 / 已完成 / 真卡了」。

> **DSH 关键差异**：`subagent` 后台跑、过程不流式到界面，主控只能在 turn 边界说话（派发 / 收到完成通知 / 阶段闸门）。故用「三播报」替代旧版「停滞/异常定时汇报」机制——DSH 无定时器，移除该条。

**① 派发即播报**（spawn 完立刻说，不等）：
```
🚀 已派发 T1∥T2∥T3（三方并行检索）
├ T1 文献 → literature/文献卡.md（8-15 条）
├ T2 数据 → data/数据卡.md
└ T3 案例 → cases/案例卡.md
⏱ 完成即逐个播报，不干等
```

**② 完成即转播**（每收到一个子代理完成通知，主控立刻勾 `todo_write` + 说一句）：
```
✅ T1 完成（8 条文献，1 缺口付费墙）
⏳ 等待 T2 / T3 …
```
用 `todo_write` 让界面上「谁✅ / 谁⏳ / 谁没动」一眼可见。

## 十七、主人深度洞察融合协议（v2.3 新增，教训 #35，原创性悖论实战沉淀）

## 十八、「据行业经验估算」限定使用条件（v2.1.1 新增，教训 #44，回应 外部审计 92% finding）

> 背景：v2.0.7 主控洞察融合协议允许使用「据行业经验估算」软化未源化数字。但 外部审计 安全审计指出这会成为「hedging language loophole」—— agent 可随意用该措辞让未经验证数据通过审计。

**限定使用条件**（满足**全部**才能使用）：
1. **三源检索全失败**：① T1 文献检索 + ② T2 数据检索 + ③ web_search 补充均**未找到任何可引用的数字**
2. **段落顶部加注**：每次使用前在该段落开头写明 `[行业估算，非数据卡]` 标记
3. **附估算依据**：该数字必须能基于「业内常识」「从业者经验」「结构性推理」之一推导（不能凭空出现）
4. **不超过全文 3 处**：全文章「据行业经验估算」类措辞累计 ≤3 处（防止滥用）
5. **T7 审计必查 G2.5 估算标记（v2.3.0 改 T5→T7）**：T7 在 G2 数据溯源里加一条专门查估算使用频次，超过 3 处 → P1

**禁止使用的场景**：
- ❌「据行业经验估算」+ 具体百分比/元数（更精确 = 更需数据卡）
- ❌ 同一论点同时使用数据卡数字 + 估算（混用 = 不可验证）
- ❌ 全文结论性数字（必须可溯源）

**示例**：
- ✅ 正确：开模打样成本「据行业经验估算」动辄「数十万元」（有范围、无精确值）
- ❌ 错误：开模打样成本「据行业经验估算」47 万元/ SKU（伪装精确度）
- ❌ 错误：同一段同时使用 D15（顾家 184.8 亿）+ 估算数字（数据混用）
- 写手收到含主人洞察的指令时，按本协议做转换；如拿不准，**默认 A 档客观化**

## 二十二、主动介入机制（v2.1.0 6 步，含 F4 轮次约束）

发现下游角色卡住（长时间静默或无产出）→ 主动介入：
1. 查 status.md 与子代理交接报告是否更新（缺失 = 未按现行执行约定回报 → 用 `list_agents` 看注册表状态并介入）
2. 用 list_agents 看子代理最近输出（判断是真卡还是模型思考中）
3. 如果模型健康度问题 → 手动 kill 会话，手动 spawn 新子代理（指定下一档 fallback 模型）
4. 如果只是产生物到中途中断（partial output 存在）→ 接受现有产出，手动补齐缺失部分
5. 在 status.md 阶段行写明介入记录：`[介入 HH:MM] 主控介入，xession-kill，重派 model=fallback1`
6. **两类上限独立判断**（F4 重构 + v2.2.0 补强）：
   - **同场景重试 ≤2 次**（重派同一任务），避免无限重试
   - **修订回环 ≤2 轮硬约束**（**T7** 审计打回后 **T5** 重写，v2.3.0 改 T5→T7/T4→T5，**v2.2.0 新增，教训 #64**；**v2.3.1 定义细化 + T8 小幅修补权限 + P1 分级，教训 #120**；**v2.3.7 论文三实战升级（P1-3）二分类修订**，详见 deliverables.md「修订回环」）：
7. **并发子代理文件覆盖防护（v2.3.2 新增，教训 #126）**：主控兜底派发 fallback 前，**必须先查主任务是否还在产出**，避免两份产物对同一文件二次覆盖：
   - **fallback 派发前置检查**：`stat -c %y` 看 mtime 与当前时间差，若 <2 分钟（说明主任务刚写盘还在跑）→ **不派 fallback**，再等主任务
   - **命名隔离**：同一角色多份并行时，用 `.模型名` 后缀命名隔离（如 `06-v2-attack.deepseek-v4-pro.md`），禁止两份同写一个文件名
   - **超时经验阈值（教训 #126 + #131，DSH 仅作软巡检参考，无硬卡）**：T6 批判/T7 审计约 12-15 分钟（"批判+修订"任务需更长）；T1-T3 检索约 10-12 分钟（中文检索单次 7s+）。旧版 8 分钟硬卡对这两类任务偏紧，曾导致「主任务其实写好了但被误判超时 → fallback 覆盖」——DSH 无硬卡，按这些经验阈值用 `list_agents` 软巡检，不机械 kill



## 二十三、编排循环防空转（v2.2.8 新增，教训 #102，2026-08-19 ECS 实战）

> **背景**：T8→T5 交接点被 duplicate 完成事件打断，spawn T5 的 tool call 丢失，主控空转 2.5 小时。根因：push-based 编排循环过度依赖「完成事件恰好投递一次」。

**主控在 T 角色交接点必须遵守的三道防御**（执行约定：状态机 + 交接六要素 + G8 自检 + 超时介入）：

1. **spawn 后立即验证落地**：每次 `subagent` 后用 `list_agents()` 确认 runId 在 active，没出现 = spawn 丢失，立即重试（≤2 次）
2. **yield watchdog**：yield 后 3 分钟无完成事件 → 自查 `list_agents` + `list_agents`，判断 spawn 丢失空转还是子代理真在跑
3. **完成事件幂等**：收到某角色完成事件时先查 `status.md` 该角色是否已 Done，已 Done = duplicate 事件，**忽略不重复推进**
4. **交接点「三段式 spawn」**：T8→T5、T4→T8、T5→T4（修订）禁止「spawn → 直接 yield」，必须「spawn → 验证落地 → 确认后 yield」

**主控 spawn 验证落地伪代码**：
```python
run = subagent(task=...)
if not subagents_has_active(run.runId):
    log("[#102] spawn runId={} 未落地，重试".format(run.runId))
    run = subagent(task=...)
```

**完成事件幂等伪代码**：
```python
def on_completion(role, runId):
    if status_md[role]['state'] == 'Done':
        log("[#102 幂等] {} 已在 Done，忽略 duplicate runId={}".format(role, runId))
        return
    status_md[role]['state'] = 'Done'
    spawn_next_role()
```
