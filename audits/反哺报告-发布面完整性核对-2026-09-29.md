# 反哺报告 — 发布面完整性核对（2026-09-29 · v18.56.0 发布后）

> **性质**：主人提问「**以前全部发布了吗？**」→ 本报告把该问题**转成四个可机械对账的面**并逐一对齐。**结论不是「是」**：查出 **4 类缺口**，其中 1 类无解释、3 类已定位成因。
> **方法**：只读核对，不依赖任何「扫 git log」的启发式（见 §五 的方法教训）。**全程未改动任何机制文件。**
> **机检边界**：`audits/**` → ⑨ 词预算不覆盖、⑪ 裸行号引用豁免、⑦b 本机路径须为 0 处（本文件已按此写）。

## §一、结论摘要

| # | 缺口类型 | 数量 | 具体 |
|---|---|---|---|
| **A** | **npm 上不存在**，但 tag 与 `package.json` 都指向它 | **2** | `18.2.9`（2026-09-21）、`2.3.7-dsh.5`（2026-08-22） |
| **B** | **错 tag**（tag 名 ≠ 它指向提交的 `package.json` 版本） | **1** | `v18.7.0` → 实际 `package.json` = `18.6.2` |
| **C** | **无 GitHub Release**（npm 有、tag 有） | **19** | 早期 dsh 线 11 个（`2.1.8-dsh.1/.2` + `2.5.2-dsh.9`–`.17`）＋ `18.10.0` ＋ `18.48.0`–`18.54.0` 共 7 个 |
| **D** | **CHANGELOG 有段落但从未发布**（无 tag、无 npm） | **8** | `17.0.0`、`18.0.5`、`18.6.3`（**3 段文档内已明写未发布**）＋ `18.2.2`、`18.2.7`、`18.7.2`、`18.7.3`、`2.5.2-dsh.6`（**5 段未写**） |

**反过来也要说清（同等重要）**：npm 上**每一个版本都有 tag**（反向差集为空）——即**不存在「发了但没打 tag」的版本**；也不存在「tag 指向 master 历史之外的提交」（130 个 tag 全在 `HEAD` 祖先链上）。

## §二、四个面的对账数据（全部实跑）

| 面 | 数量 | 口径 |
|---|---|---|
| git tag | **130** | `git tag -l`；逐 tag `git merge-base --is-ancestor <tag> HEAD` → 全部在内 |
| tag → 版本映射（去重） | **129** | 逐 tag 读 `git show <tag>:package.json` 的 `version`（**权威口径**，不扫 log） |
| npm 已发布版本 | **127** | `npm view lunheng-article-pipeline versions --json` |
| GitHub Release | **110** | `gh release list --limit 300` ＋ 抽查 `gh api .../releases/tags/<tag>` 交叉验证 |

**推导**：129 个「被 tag 声明过的版本」− 127 个已发布 = **2 个未发布**（= A）；130 个 tag − 129 个版本 = **1 个重复/错指**（= B）。

> **口径为什么用「tag→版本映射」而不是「扫 CHANGELOG 版本号」**：CHANGELOG 里 `2.5.2` 这类段号重复出现（历史 `-dsh.N` 段的父号），直接抓版本号会得到重复项；而 tag 是**发布意图的机械载体**，逐 tag 读它指向提交的 `package.json` 得到的映射**一一对应、可复核**。

## §三、逐类成因（**已定位**的三类）

### A（2 个 npm 缺失）——**成因不可判定，如实声明**

两个 tag 都指向 `package.json` 就是该版本的提交，说明**当时确实把版本切好了、tag 也打了**。但 npm 上不存在，且 **npm 不提供「某版本是否曾被发布又撤回」的历史**——故无法从本机判定它是：

- ① 当时 `npm publish` 失败后被跳过（**不追发**）；还是
- ② 曾发布、后经 `npm unpublish` 撤回（**72h 窗口内可撤**）。

**旁证（仅作倾向，不作结论）**：`2.3.7-dsh.5` 在 npm 上呈**洞穴状空缺**——`.1/.2/.3/.4` 有、`.5` 无、`.6/.7/.8` 有。单点空缺更像「该次发布失败后未补」，而非「事后整批撤回」。

### B（错 tag）——**成因已定位：tag 打在了错误的提交上**

`v18.7.0` 指向提交 `4e263b3`（标题 `fix: 词预算抬限 5 文件预冲 v18.6.3 +1 KB`），该提交 `package.json` = **18.6.2**。

而 CHANGELOG 的 `## 18.7.0` 段自述「**合并到 v18.7.0 单版**」——即 18.7.0 是**计划中**的一个大合并版，实际发布时成了 `18.7.1`（`18.7.1` 在 npm 上、有 tag）。**18.7.0 从未作为版本存在。**

**这条不是纯记账问题**：`publish.yml` 里有一条守卫「`git tag` 与 `package.json version` 不一致 → 拒绝发布（防版本超前误发）」。若该 tag 被重新推送触发 CI，会**直接撞这条守卫**。

### C（19 个无 Release）——**两个不同的成因，都不是「忘了」**

| 子集 | 成因 |
|---|---|
| 早期 dsh 线 11 个 ＋ `18.10.0` | **当时尚无自动创建 Release 的步骤**——该能力是 2026-09-21 的提交（自述原文：「**自动创建 GitHub Release（此前一直是手工补，漏补即停更）**」）才加进 `publish.yml` 的。在此之前靠手工补，漏了就永久没有。`18.10.0` 另有一条独立成因：那次是**因 EOTP 走 NPM_TOKEN 手工发布**的（本地发布不建 Release）。 |
| **`18.48.0`–`18.54.0` 共 7 个** | **`publish` 作业连续 7 次失败，而 `release` 作业依赖它成功**（`needs: publish`）→ 被跳过 → Release 从未创建。失败原因（实测日志）：`npm error code E409 … Cannot publish over previously staged version "<ver>"`。 |

> **E409 的机制**（本仓已有记载）：`npm publish` 在**鉴权/收尾步骤失败时也会先把 tarball 放进暂存区**；其后任何重试都会撞 `E409 Cannot publish over previously staged version`，须先 `npm unpublish` 再发。
> **但 npm 上这 7 个版本都是在的** → 说明它们最终经**本地手工路径**完成发布，而 CI 那一次（或其后重试）**停在 E409**。**后果仅限「Release 缺失」**，不影响 npm 安装。
> **该簇已自愈**：`v18.55.0` 起 publish 作业恢复 success（18.56.0 亦 success）。

### D（8 段从未发布）——**3 段已写明、5 段没写（真实文档缺口）**

| 版本 | 文档是否已说明 | 说明原文 / 缺口 |
|---|---|---|
| `17.0.0` | ✅ 已写 | 标题即写「**（未单独发布 —— 内容随 18.0.0 首发）**」，且 `## 18.0.0` 段复述「17.0.0 从未单独发布…随本版首发」 |
| `18.0.5` | ✅ 已写 | 「⚠️ **本版未单独发布到 npm**（`18.0.5` 不是一个已发布的版本）——它的全部内容包含在 `18.1.0` 里，随 18.1.0 首发」 |
| `18.6.3` | ✅ 已写 | 标题即写「**18.6.3 — 计划中（未发布）**」 |
| `18.2.2` | ❌ **未写** | 标题只有日期；该编号在版本序列里被跳过（`18.2.1` → `18.2.3`） |
| `18.2.7` | ❌ **未写** | 同上（`18.2.6` → `18.2.8`） |
| `18.7.2` | ❌ **未写** | 同上（`18.7.1` → `18.8.0`） |
| `18.7.3` | ❌ **未写** | 同上 |
| `2.5.2-dsh.6` | ❌ **未写** | 同上（`dsh.5` → `dsh.7`） |

**这 5 段是真实的文档缺口**：读者在 CHANGELOG 里看到 `## 18.7.2 — 2026-09-23` 这样带日期的段落，**会认为存在 18.7.2 这个版本**，而 `npm i lunheng-article-pipeline@18.7.2` 会 **404**。
**共同形态**：段落写在发布之前（内容工作进行中先占段号），落地时编号被跳过、内容并进下一版，但**段首没有补一句「未单独发布」**——前 3 段是补了的，后 5 段没补。

> **可迁移判据**：**「计划中/未发布」的段号不是记账问题，是安装指令问题**——CHANGELOG 是用户找可用版本的入口之一，一段带日期的「## X.Y.Z」在读者眼里等价于「X.Y.Z 可安装」。**凡写未来段号，必须同段落写清它与最终交付版本的关系**（本仓已有 3 个正确先例可照抄）。

## §五、方法教训（**本报告最该被记住的一条**）

**我第一版用「扫 `git log -p -- package.json` 抓 `+ "version"` 行」来推「哪些版本被切过」，结果被自己的交叉验证推翻**：该扫描给出「曾切 127 个版本」，而 npm 上有 5 个版本（`18.12.2`/`18.12.3`/`18.13.0`/`18.14.0`/`18.15.0`）**在扫描结果里完全不存在**——可它们的 tag 提交的 `package.json` 明明就是那些版本。

**改用不依赖 log 扫描的权威口径后**（逐 tag `git show <tag>:package.json` 读版本），**同一个问题立刻得到自洽的三方数字**（130 tag / 129 版本 / 127 npm），且反向差集为空。

> **可迁移判据（与 §一 的普查教训同族，但触发点不同）**：
> **① 凡「扫描日志/差异文本来重建一个集合」的推导，都必须有一个不含扫描的独立口径做交叉验证**——否则扫描漏项会被当成「历史上的确没有」。
> **② 一个集合类结论（「全部都在」/「一共 N 个」）只有在两个独立口径给出同一数字时才可信**；只要出现一个反例（本例 5 个），该口径即整体作废，不得局部修补后继续用。
> **③ 本例最省事的独立口径 = 读**制品本身**（tag 指向的 `package.json`），而不是读**制品的变更历史**——前者是状态，后者是过程，状态不会被日志扫描的方式漏掉。
