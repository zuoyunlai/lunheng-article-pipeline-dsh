# 反哺报告 — `parseTargetCandidates()` 在**粗体 + 千分位 + 区间**写法上的两处失效

> 版本：v1（2026-10-16）｜产出者：T0 主控｜**性质：只出判据与证据，未改任何机制文件**
> **发现场景**：本项目（`run/ai-era-tech-ethics`）Phase 4 派发前刷新审计视图（`build-evidence-bundle.mjs --summary`）时，视图打出
> ```
> ⚠️ 正文区 5921 汉字 > 目标上限 880 × 1.2 = 1056（视图内已打显著标记）
> ```
> 而本项目目标是 **6,000 字** —— 「目标上限 880」荒谬，遂逐层回真源。

---

## 一、结论（先读这段）

**`_lib/target-chars.mjs` 的两个导出函数在同一句话上给出不同的数**：

| 函数 | 本项目简报原文上的返回 | 谁在用 |
|---|---|---|
| `parseTargetChars()`（单值） | **`{"value":6000, "raw":"6,000 字（纯中文字符数，口径 A）**，区"}`** ✅ **正确** | —— |
| **`parseTargetCandidates()`（候选）** | **`{"candidates":[880]}`** ❌ **错** | **`build-evidence-bundle.mjs`（审计视图）L551「取候选最大值」** |

⇒ **审计视图据此判定「超限」并打显著标记**。该项目实际 5,921 字（在 5,880–6,120 内），**视图给出的是一个假超限**；而审计视图是 **T7/T8 判字数归属 G8 的读数来源** ⇒ **可致错误 P0/P1**。

---

## 二、复现（探针原样，可照抄）

```js
const m = await import('<技能根>/scripts/_lib/target-chars.mjs')
const cases = [
 ['现状',         '- **目标篇幅**：**6,000 字（纯中文字符数，口径 A）**，区间 **5,880–6,120**（±2%）'],
 ['A 去掉区间',   '- **目标篇幅**：**6,000 字（纯中文字符数，口径 A）**'],
 ['C 区间无千分位','- **目标篇幅**：**6,000 字（纯中文字符数，口径 A）**，区间 **5880 至 6120**（±2%）'],
]
for (const [n, t] of cases) console.log(n, m.parseTargetCandidates(t).candidates, m.parseTargetChars(t).value)
```

**实测输出（逐字）**：

```
现状（基线）                 候选=[880]        单值=6000
A 去掉区间                   候选=[]           单值=6000
B 区间另起一行               候选=[]           单值=6000
C 区间写「至」不用千分位        候选=[5880,6120]  单值=6000
D 区间前置                   候选=[]           单值=6000
```

## 三、两处失效（**同一根因的两张脸**）

| # | 症状 | 触发写法 | 后果 | 严重度 |
|---|---|---|---|---|
| ① | **抓错数** | 粗体 + 千分位 + **含千分位区间**（`**6,000 字**，区间 **5,880–6,120**`） | 候选 = `[880]` ⇒ **假超限**（视图显著标记 → T7/T8 误判） | **P1**（可致错误判级） |
| ② | **静默跳过** | 粗体 + 千分位，**无区间**（`**6,000 字**`） | 候选 = `[]` ⇒ 视图退化为「未解析到目标字数，跳过 G8 字数硬阈判定」 | **P1**（**正是 v18.12.3 立项要修的那一类**——「闸门在最需要它的档位上静默失效」） |

**根因（判断，未读实现细节）**：`parseTargetCandidates()` 与 `parseTargetChars()` **共用 `LINE_RE`**（行匹配没问题，两函数都命中了同一行），但**候选提取的数字正则没有处理 `**` 包裹与 `,` 千分位** ⇒ 粗体形态下 `6,000` 抓不到（②），而一旦同一窗口里还有别的数字碎片（`5,880` 的 `880`）就抓那个（①）。

**佐证（同模块的历史）**：该模块头注释（L4–L10）明确记载 v18.12.3 的立项理由就是**「四类完全合法的写法都返回 null」**（含 `目标篇幅：12,000 字` 的**千分位**形态，以及**粗体**形态的 v18.23.0 EFF-1 修复）。⇒ **修的是 `parseTargetChars` 那条路径，姊妹函数 `parseTargetCandidates` 未同步**——与本仓「同一事实两处实现必然漂」的既有判据同型。

---

## 四、影响面（为什么值得单列一条）

1. **不是本项目独有**：任何把目标字数写成 **`**目标篇幅**：**N,NNN 字`**（`任务简报-template.md` 的**推荐粗体写法**）的项目，其**审计视图**都会走 ② 或 ①。
2. **症状②尤其危险**：它不是报错而是**静默跳过**——视图上只显示「未解析到目标字数」，读的人**不会察觉** G8 字数硬阈判定被跳过了（这正是 v18.12.3 的原始病灶）。
3. **在本项目上已实际误导**：视图已打出假超限标记；而**本项目是 `policy` 档真试跑**（一次被当作验证用的跑），假读数会直接进 T7 的读数面。
