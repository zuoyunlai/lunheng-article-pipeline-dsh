## §七、不写出来会丢的边界（**写给将来的主人**）

1. **A 路径 vs B 路径的独立性**：A 是「**接口层**」，B 是「**流程层**」——**互不可见**。试点报告必须分别看（A 看 schema 是否能用、B 看断点是否可触发）——**不能用一个试点同时验证两个路径**。
2. **主人显式开 B 门 的语义**：**B门=on = 5 个断点都开**（不是 5 个开关）——简化主控 Phase 0 简报字段；如未来要「**只开断点 1 + 断点 3**」则加 `B门=on;B1=on;B3=on;B2=off;B4=off;B5=off`——**本报告不预设**。
3. **bridge_payload 的存在理由**（v18.56.0 引入）：这是「**主控 → 子代理**」的单边传递（不是交接 JSON 的「**子代理 → 主控**」）；交接 JSON（LLMG-1）是「**子代理 → 主控**」的对侧——**两者拼起来才是完整的结构化交接**。本报告 LLMG-1 不动 `bridge_payload` 的现定义（属于主子消息契约，与 LLMG-1 的子主契约**互不干扰**）。
5. **修机制文件的风险**（`AGENTS.md §机制文件写保护`）：本报告 LLMG-1~10 全部要动 `references/**` / `AGENTS.md` / `scripts/**` —— **必须主人显式授权后才进入执行场**。本报告成文时**零改动**（实测）；落地路径**严格按** AGENTS.md 例外条款（改前备份 / 改中 `edit` 精确匹配 / 改后四门全绿 / 改后 `docs/` 前呼）。
6. **本报告与 v18.78.0「刻意设计不变量」的关系**：v18.78.0 已登记四处机制为「**知道它为什么这样设计**」——本报告 LLMG-1~10 不与这四处冲突（**已实测核对**）：① 不动 **M 门 25 项 = 24 机检 + 1 人工**；② 不动 **handoff-check.mjs 的退出码契约 20/21/22**；③ 不动 **args.bridge_payload 的主子契约**；④ 不动 **LUNHENG_*.mjs 的写盘打白**。
