## P0/P1 优先问题

### P1-1：`/lunheng-status` 末级文件软链接能越出 run 围栏

位置：[commands.js](../lib/commands.js) 第 97-104 行；项目目录过滤位于第 30-49 行。

围栏验证了 `run/<项目>` 目录，但随后直接读取 `status.md`、`进展-主人版.md`；叶文件本身未做 realpath containment。临时目录复现：`run/demo/status.md` symlink 指向 run 外文件后，命令成功返回外部文件标记内容。无参数“最近项目”分支同样读取叶文件。

影响：有文件系统访问权限的调用方可以让状态命令读出 run/ 之外内容。修复建议：对每个待读叶文件执行 realpath 并限制在已验证项目目录内；处理链接替换竞态，必要时使用 no-follow/open 后核验。

### P1-2：四个原生工具的相对路径按宿主 cwd 解析，而不是会话工作区

位置：[tools.js](../lib/tools.js) 第 55-60、223-225、288-290、357-362 行；伦理工具注册及参数处理见第 444 行起。

子进程 `spawn()` 未传 `cwd`，伦理脱敏工具直接读取相对路径；工具执行接口没有使用 `exec.agent.session.header.cwd`。临时夹具令宿主 cwd 与会话 cwd 不同，会话目录存在 `paper.md`：`lunheng_char_count({file:'paper.md'})` 报文件不存在；伦理工具同样失败。若宿主 cwd 恰有同名文件，则可能对错文件给门结果或脱敏结果。

影响：桌面/多工作区环境中相对路径功能不可靠，并有对错稿作判断的完整性风险。修复建议：统一从调用执行上下文取会话 cwd，先 resolve 所有相对输入，再把 cwd 显式传给子进程和文件读取模块；补不同 cwd 的集成测试。

### P1-3：H2 opt-in 改写会覆盖下游监听器已替换的 content

位置：[index.js](../lib/index.js) 第 368、381-407、474-478 行。

仅当 `hookRewriteContent=true`：H2 先 `await next()`，但之后仍以原始 `result.content` 构造脱敏数组，并设置 `decision.content`。探针中 `next()` 将内容换成 `DOWNSTREAM_SAFE_REPLACEMENT`，最终 H2 输出却是原始文本的脱敏版本，下游删改被覆盖。

影响：与后续监听器的过滤/删减结果冲突，覆盖安全处理；默认值关闭，所以不是默认态泄露。修复建议：已有 `decision.content` 时以其为输入，或保守地不覆盖它；增加多个 post-execute 监听器组合回归测试。

### P1-4：M 门 `ERROR` 可经 T8 裁定变成 exit 0

位置：[m-gate-check.mjs](../skills/lunheng-article-pipeline/scripts/m-gate-check.mjs) 第 418-480、802-860 行。

机械判定明确规定 `severity: ERROR` → exit 70，表示门内错误、未对内容作结论。但 `--adjudicate` 仅禁止四类硬红线；ERROR 被排除于红线集合。临时夹具显示：机械报告含两条 ERROR、机械 `script_exit_raw=70`，但给 `true_p0=0/true_p1=0` 与满足关键词的 review 后仍写入裁定 `exit=0` 并以进程 0 退出。

影响：系统未能完成检查时可以被表示成通过。修复建议：任何 ERROR/exit70 必须无条件拒绝裁定，先修复执行错误并重跑；单独测试 ERROR 加 adjudicate 的组合。

### P1-5：证据包构建标记拒收源，但 M-Exist-2 不消费该标记

位置：[build-evidence-bundle.mjs](../skills/lunheng-article-pipeline/scripts/build-evidence-bundle.mjs) 第 230-245、385-405 行；[mexist-gates.mjs](../skills/lunheng-article-pipeline/scripts/_lib/mgate-gates/mexist-gates.mjs) 第 1532-1643 行。

构建脚本将 0 字节或大小不符的源记入 `manifest.zeroByteSrcs` / `manifest.sizeMismatch`，但在有其他合法文件时仍可成功。M-Exist-2 复算 `files`、空文件与哈希，却不检查上述拒收源字段。独立临时夹具确认：manifest 有拒收源记录，门仍可 `pass=true`（其他条件正常）。

影响：构建器明示未完整收录的证据源可能不阻止“证据包完整”结论。修复建议：定义拒收源的规范处理：生成阶段非零退出或由 M-Exist-2 判 P1/P0；在 manifest schema 和行为测试里钉住。

### P1-6：破坏性写入保护用 realpath 字符串比较，硬链接可绕过

位置：[destructive-write.mjs](../skills/lunheng-article-pipeline/scripts/_lib/destructive-write.mjs) 第 35-61、231-239 行。

`sameFile()` 通过路径 resolve/realpath 后比较字符串。硬链接拥有不同路径和 realpath，但指向同一文件记录。临时 `fs.linkSync()` 探针证实 `sameFile(original, alias) === false`。因此 `writeReport` 等依赖 `sameFile()` 的源文件保护可能接受硬链接别名作为输出路径。

影响：在支持硬链接的文件系统上，覆盖别名会覆盖受保护源文件。修复建议：同设备时比较 `stat.dev` + `stat.ino`（平台可用性须明确），必要时拒绝硬链接输出；加入硬链接用例。

### P1-7：确认模板允许 Phase 0 预授权，但交接门在回执账本存在时只认可逐门 ask_user_question 回执

位置：[主人确认-template.md](../skills/lunheng-article-pipeline/references/templates/主人确认-template.md) 第 137-149 行；[handoff-check.mjs](../skills/lunheng-article-pipeline/scripts/handoff-check.mjs) 第 742-768、833-859 行。

模板允许主人在 Phase 0 显式预授权，后续满足三条件时不等主人现场回复，并要求在 §6 写“Phase 0 预授权”。但若项目已有 `gate-receipts.jsonl`，机械门要求每道确认单有 gate 相符的 `ask_user_question` 回执，没有预授权回执分支。

影响：合规预授权仍会被判 exit 21，逼迫伪造现场问答或删除回执账本。修复建议：新增可验证的 Phase 0 预授权回执类型与作用范围，或收窄模板承诺；不要通过删除账本绕过。

### P1-8：质量评分把门脚本 ERROR/exit70 当成普通 N/A

位置：[quality-score.mjs](../skills/lunheng-article-pipeline/scripts/quality-score.mjs) 第 169-188 行（评分门调用与结果接纳）；测试见 [quality-score.test.mjs](../tests/quality-score.test.mjs)。

M 门在可解析的内部 ERROR 场景会 stdout 输出完整 JSON、进程 exit70。评分器仅检验 `j && j.total > 0`，不验证子进程状态、`j.exit===70` 或 `severity: ERROR`，因而继续以 `pass/total` 计分，不将总分标为无效。

影响：评分可能看起来有效，实则关键检查未成功运行。修复建议：记录执行状态并将 ERROR/70 作为评分 `invalid`（不是 N/A）；增加“有 JSON 但 exit70”的测试。其他门也应统一检查退出状态。

### P1-9：轮次上限可由主人在确认单变更，但机械账本仍固定 2/1/2

位置：[主人确认-template.md](../skills/lunheng-article-pipeline/references/templates/主人确认-template.md) 第 98-112 行；[round-ledger.mjs](../skills/lunheng-article-pipeline/scripts/_lib/round-ledger.mjs) 第 27-28、68-76 行；[handoff-check.mjs](../skills/lunheng-article-pipeline/scripts/handoff-check.mjs) 第 814-831 行。

模板称主人可在 §6 将 A/B 轨上限变更且即刻生效；账本解析与 handoff-check 却固定采用 `ROUND_CAPS={A:2,B:1,G:2}`，不解析已授权的新额度。

影响：主人明示授权的额外轮次仍会被机械判硬失败。修复建议：把变更写入具备项目范围、时间/回合范围的结构化授权记录并让门消费；或删除模板中的“即生效”承诺。

### P1-10：裁定所称的“证伪四件套”目前只做关键词存在性检测

位置：[m-gate-check.mjs](../skills/lunheng-article-pipeline/scripts/m-gate-check.mjs) 第 817-843 行。

四项校验是 `逐条`、`真阳性`、`规范`、`复核|独立` 的正则命中数，要求 3/4；不检查是否有逐条编号、扫描结果、具体规范冲突或独立复核来源。任意 review 文本包含这些关键词即可让非红线机械失败被裁定为 0。

影响：结构化证据门退化为可轻易满足的词语门。修复建议：裁定输入改为结构化字段并核验引用与本次失败 gate/编号对应；“独立复核”需要真实可寻址来源。未能自动证明的部分明确改为人工审批，不宣传为机械验证。

## P2 问题

### P2-1：H2 地名哨兵与用户原文私用区字符碰撞时静默篡改

位置：[ethics-sanitize.js](../lib/ethics-sanitize.js) 第 259-261、313-320 行。

地名替换使用私用区哨兵编号。原文若已含将被本轮映射占用的同一哨兵（探针 `\uE0000\uE000` 加词表地名“杭州”），恢复时会把原始字符误当内部哨兵并替换成地名占位符；未产生 reviewFlags。

影响：脱敏工具会无声破坏非个人信息文本。修复建议：选取输入中不存在的哨兵前缀，或使用分段映射避免哨兵串进入文本；对实际映射编号碰撞测试。

### P2-2：伦理脱敏 `maxChars` 接受小数导致分页不前进

位置：[ethics-sanitize.js](../lib/ethics-sanitize.js) 第 183-190、327-330 行；对应工具参数定义位于 [tools.js](../lib/tools.js) 第 405-406、468-478 行。

工具 schema 接受 number。传 `maxChars:0.5` 时内部 `slice(0, 0.5)` 得到空字符串，`nextOffset` 仍与当前 offset 相同，同时 `truncated=true`；调用方按分页续读会陷入无进展循环。

影响：参数边界造成分页卡死，而非数据泄露。修复建议：要求整数且 ≥1；返回 `hasMore` 时断言 `nextOffset > textOffset`。
