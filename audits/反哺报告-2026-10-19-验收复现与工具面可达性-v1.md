### 2.1 【A-1 · P1】已发布 19.19.0 的 `sessionLog` / `sessionRoot` 工具面不可达（**复现成立**）

→ Error: INVALID_ARGS：sessionRoot 只能指向会话工作区或系统临时目录之内，收到 C:/Users/<user>/.dsh/sessions/--E-HERNESS--。

**证据 3（脚本层对照 ⇒ 堵点在工具面，不在脚本）**：

node scripts/handoff-check.mjs --project ../../../_accept/liteproj --role T8 \

### 2.2 【A-2 · P2】`--help:73` 的「默认 `$DSH_HOME/sessions`」与实现矛盾（**复现成立，两版都有**）

**事实**：

- `scripts/handoff-check.mjs:73`（19.19.0 与 19.19.1 **逐字相同**）：
  `--session-root <目录>  配合 --session-log 传「会话 id」时用（默认 $DSH_HOME/sessions）。`
- 实现 `:209-211`：id 形态且**未给** `--session-root` → `exit 10`；`:202-204` 注释明说**刻意不做** `DSH_HOME` 兜底（防跨宿主假红）。
- 已装 19.19.0 的**工具参数描述**同样写着「默认 `$DSH_HOME/sessions`」（`lib/tools.js:506`）；源码 19.19.1 已改对（`:535`「传会话 id 时必须一并给 … 无它 → exit 10」）。
- **无任何测试断言这句文案**：`tests/` 与 `skills/*/tests/` 内 grep「默认 $DSH_HOME/sessions」零命中 ⇒ 该句可以长期漂移而全绿。

**为什么仍是 P2 而不是 P1**：脚本行为本身是**对的**（刻意无默认，理由充分）；错的是文案。但这条文案正好在 19.19.0 里**误导**主控把 `--session-root` 当可省，与 A-1 叠加后就成了「文档说可选、实现要必给、围栏还拒」的三重错位。

**动议 A-2**：`:73` 改为「传会话 id 时**必给**；脚本不做默认，无它即 exit 10（防跨宿主假红）」；顺手核 `SKILL.md`/`operations-capability.md` 余下的「默认」表述。**建议同时加一条文案断言**（正则断言 `--help` 不再出现「默认 $DSH_HOME/sessions」），否则下次还会漂。

### 2.3 【A-3 · P2】`lunheng_char_count` 丢弃 `scopeSource`（**复现成立**）

**事实**：

- 脚本 `scripts/count-chars.mjs:287` 与 `:320` 产出 `scopeSource`（`bodyStartSource` / `full`）。
- 工具 `lib/tools.js` 的 `output.schema` 为 `additionalProperties: false`，`properties` 只有 `hanChars` / `scope` / `exit` / `degraded` / `degradedReason` / `sections` / `truncated` ⇒ **`scopeSource` 被静默丢弃**；`render` 也只呈现 `scope`。
- 注：`m_gate` 的 `advisories` / `unchecked` / `hardRedLineHits` 属**同族问题**，已在 19.19.1 修掉（`lib/tools.js:317` 注释即记此事）——`char_count` 是**漏网的第四个**。

**为什么是 P2**：`scope` 标签自身已携带同义信息（起点来源），故**不产生误导结论**，成本是信息面收窄 + 与脚本契约不一致（同一脚本，脚本层有、工具层无）。

**动议 A-3**（二选一，不要两边都做）：
- 方案 1：schema 补 `scopeSource: { type: 'string' }`，`render` 首行尾附来源（与 `m_gate` 的处理对齐）；
- 方案 2：维持丢弃，但在工具描述与 `TOOL_FACE_FLAG_GAPS` 旁**显式登记**「`scopeSource` 刻意不透出，`scope` 已含同义信息」——避免下一个人把它当缺陷重报。

### 2.4 【A-4 · 流程】仓库 19.19.1 ≠ 已发布/已装 19.19.0（**成立**）

**事实**：

- 真源 `package.json` = **19.19.1**，HEAD = `3f581365`，`git describe --tags` = `v19.19.0-3-g3f581365`；
- 已装 profile = **19.19.0**，`lib/tools.js` 与 tag `v19.19.0` **逐字节相同**；
- ⇒ 验收/测试**跑的是旧产物**，源码已绿的项在产物侧可能是红的（A-1 就是实例）。

**这不是代码缺陷，是发版流程缺一道核对**。原验收报告已给出「`loaded == onDisk`」这一半结论，本报告补上另一半：**`onDisk == git HEAD` 也必须成立**，否则「验收通过」说的是上一版。

**动议 A-4**：发版链增加**三向同版**核对（一条命令即可，建议进 `scripts/` 或发版清单）：

```
package.json.version == git describe --tags 的基线（tag+3 提交时须显式承认「未发版」）
npm latest == package.json.version
profile 已装 == package.json.version   # loaded == onDisk == HEAD
```

`no-write-check` 之外单列，因为它是**发布序列**的门，不是写盘门。

### 2.5 【A-5 · 修正】原报告两处措辞/定性订正

1. **「只能退回 `pwsh`」→ 不成立为「唯一」**。工具报错自带的处方是「材料摄取」：把会话文件拷进 `run/<项目>/materials/` 再调用，围栏内可行。故正确表述是「**无直连通路**；材料摄取可绕行，但绕行本身是主控侧拷贝，独立核对层的价值取决于主人是否接受该拷贝」。§2.1 定性按此修正，定级不变。
2. **A-3 的「信息面收窄」保留 P2，但补一句**：`scope` 标签已含同义信息，**不得**把本条升格为「口径失真」——与 `degraded` 语义无关。
