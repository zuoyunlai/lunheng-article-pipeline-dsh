## 二、③ 两处缺陷的修复（实测夹具 = `run/xingbie` 的 56 张数据卡）

### 2.1 缺陷①：效应量候选的**静默退化**

- **病灶**：旧版效应量分支只有**二分**——`rct`/`队列研究`/`case-control` → OR/RR/RD；**其余一切** → MD/SMD/r。于是「**studyType 没识别出来**」与「**已知是横断面**」落进**同一支**。实测：56/56 卡 `studyType` 全为 `null`、**每张卡都拿到同一组通用候选**，而脚本照常 `exit 0` ⇒ 下游会读成「已识别出可算的效应量」。**「碰运气」量化**：该正则在 `xingbie` 的 56 张卡里命中 **0**，在 `E3-ai-content-farm-A/B`、`ai-cad-cam-impact` 里命中 1–2 ⇒ **同一脚本在不同项目上输出不可比**。
- **修法**：拆**三支**——① 二分类设计 → OR/RR + RD；② **已知**非二分类 → MD/SMD/r（**仍给候选**，因为「已识别」≠「未识别」）；③ **未识别** → `candidates: []` + `degraded: true` + `degradedReason`。并把 **`effectSizeSummary.degraded` 抬到顶层**（单卡标记容易被略过）。
- **实测改后**：`effectSizeSummary = {total: 56, identified: 0, degraded: 56}`、首卡 `candidates=[]`、**0/56 卡**再拿到那组误导候选。

### 2.2 缺陷②：PRISMA 把**数据点当研究**

- **病灶**：四阶段计数**一律等于卡数**（实测各 56），而 PRISMA 数的是「**研究**」⇒ 读者读成「56 项研究入选」。**流程看起来完整**，比「输出为空」更危险。而数据卡契约**不含「研究标识」** ⇒ 脚本**无法**归并。
- **修法（改的是**声明**，不是数字）**：`prismaFlow.unit` 明文「records = 数据卡（数据点）——**不是研究数**」；`studyCount: null` + `studyCountReason`。
  **反向钉**：`identification.identified` **仍等于卡数**——**不许用「把数字改小」消除歧义**，那是**伪造而非修复**（该反钉已入回归网）。
- **同批**：`meta.inputFaceCaveats` 四条（输入面不匹配 / 两条后果 / **责任点 = T4·主控须核对 `degraded` 与 `unit`**）。
