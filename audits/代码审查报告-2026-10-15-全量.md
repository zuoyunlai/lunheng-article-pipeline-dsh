## 一、P1（真实缺陷，有条件触发，建议本迭代修）

### P1-1 `pool-extract` 重用计数非幂等：同一项目重复抽取会虚增 `reuseCount`

**位置**：`skills/lunheng-article-pipeline/scripts/pool-extract.mjs:161-166`

```js
if (index.has(k)) {
  const hit = index.get(k)
  hit.reuseCount = (hit.reuseCount || 0) + 1          // ← 无「是否同一项目」判定
  hit.reusedBy = hit.reusedBy || []
  if (!hit.reusedBy.includes(projectName)) hit.reusedBy.push(projectName)   // ← 这一行有去重
  reused++
}
```

**事实**：`reuseCount` 在**每一次命中去重键**时无条件 `+1`；而 `reusedBy` 用 `includes()` 去重。两者判据不一致 → **同一项目反复抽取，`reusedBy` 只有 1 项，`reuseCount` 却线性增长**。

**复现（已验证，实跑）**：

```
同一项目、卡片一字未改，连跑 3 次 pool-extract：
  第 1 次 → 新增 1 条 / 复用 0 条
  第 2 次 → 新增 0 条 / 复用 1 条
  第 3 次 → 新增 0 条 / 复用 1 条

literature.json → { reuseCount: 2, reusedBy: ["proj"] }      ← 1 个项目却记 2 次复用
manifest.json   → { reuseCountTotal: 2 }                      ← 虚增已进入汇总产
```

**为什么真实触发**：`references/pipeline-readme.md:252` 把 `pool-extract.mjs` 排为 **Phase 5 终检**的标准动作。Phase 5 后一旦发生 T5 修订轮 / 重跑交付，该动作会**再次执行**；据本仓自己的记录，单个项目正文演进 3 次并不罕见（见 `refresh-gates.mjs:9` 的实测记录「终检期正文演进 3 次」）→ `reuseCount` 直接虚增 3 倍。

**影响面**：`pool-report.mjs:57-58, 104` 把该值作为「累计复用 X 次 / 最高复用」输出，并提供给主控与主人阅读。**数据未丢，但持久化的统计量已失真且不可自愈**（`reusedBy` 无法反推正确计数）。

**建议**：把 `reuseCount` 的递增绑定到「新项目入 `reusedBy`」这一唯一事实：

```js
if (index.has(k)) {
  const hit = index.get(k)
  hit.reusedBy = hit.reusedBy || []
  if (!hit.reusedBy.includes(projectName)) {   // 只有在「首次由本项目复用」时才计数
    hit.reusedBy.push(projectName)
    hit.reuseCount = (hit.reuseCount || 0) + 1
  }
  reused++
}
```

并补一条幂等用例（本仓已有 `tests/` 惯例，落到 `tests/scripts/pool-extract.test.mjs`）。

**严重度**：P1 ｜ **已验证**

### P1-2 `pool-query` 骨架重建会写出一份「与池内容矛盾」的 manifest，且不自愈

**位置**：`skills/lunheng-article-pipeline/scripts/pool-query.mjs:41-59`

```js
function ensureSkeleton() {
  if (existsSync(join(poolDir, 'manifest.json'))) return false   // ← 判据只看 manifest 在不在
  ...
  for (const f of Object.values(POOL_FILES)) {
    const p = join(poolDir, f)
    if (!existsSync(p)) writeFileSync(p, JSON.stringify({ version: 1, entries: [] }, ...))  // ← 不覆盖已有池数据（对）
  }
  writeFileSync(mf, JSON.stringify({ totalEntries: 0, byType: {...0}, reuseCountTotal: 0, ... }))  // ← 但计数恒写 0（错）
}
```

**事实**：判据是「`manifest.json` 是否存在」，而**写入的计数恒为 0**，与四个池文件的实际内容无关。于是只要 `manifest.json` 缺失、而池文件有数据，就会生成一份**自称 0 条、实际非 0 条**的 manifest。

**复现（已验证，实跑）**：

```
池内实有 1 条文献 → 删掉 manifest.json → 跑 pool-query <工作区根>
  stdout: "✅ 已创建空素材池骨架（0 条）"          ← 紧接着又打印「命中 1/1 条」，同一进程内即自相矛盾
  manifest.json: { totalEntries: 0, byType:{L:0,...}, reuseCountTotal: 0 }
  pool-report 同刻读到: "总条目: 1 (L=1 D=0 C=0 DB=0)"   ← 两个工具各说各话
```

**为什么不自愈**：全仓只有 `pool-extract.mjs:191-213 updateManifest()` 会重算这些字段（且算法正确），而 `pool-extract` 只在 Phase 5 跑。**在下次从任意项目跑 `pool-extract` 之前，manifest 一直是错的**；若主人只跑 `pool-query`/`pool-report`（这正是 `素材池.md` 给主人的读面路径），就会持续读到 0。

**修法（二选一）**：
- **优选**：`ensureSkeleton()` 改为**复用 `pool-extract` 的 `updateManifest()` 逻辑**（抽出到 `_lib/`，两处同一实现）；`pool-query` 只负责建目录与空池文件，manifest 一律由「重算」产生。
- 次选：`ensureSkeleton` 不再写 `totalEntries/byType/byChannel/reuseCountTotal`，或写 `derived: true` + `stale: true` 标记，并让 `pool-report` 优先信池文件（它已经这么做了——**问题只在 manifest 这一份冗余副本**）。

**顺带**：这正是本仓自己立的判据「**同一事实两处实现必然漂**」的又一实例——`totalEntries` 这类**派生量**被当成了独立持久状态。

**严重度**：P1 ｜ **已验证**

### P1-3 素材池与修订账本是唯一绕过写盘安全网的持久状态（非原子、无回滚点、读-改-写无保护）

**位置**：

| 文件 | 行 | 行为 |
|---|---|---|
| `scripts/_lib/round-ledger.mjs` | `190` | `writeFileSync(p, readFileSync(p,'utf8').replace(/\n*$/,'\n') + line)` |
| `scripts/_lib/round-ledger.mjs` | `187` | `writeFileSync(p, LEDGER_HEADER + line)` |
| `scripts/pool-extract.mjs` | `182`, `213` | `writeFileSync(poolFile, …)` / `writeFileSync(mf, …)` |
| `scripts/pool-query.mjs` | `47`, `51` | `writeFileSync(...)` × 2 |
| `scripts/pool-report.mjs` | `98` | `writeFileSync(join(poolDir,'index.md'), …)` |
| `scripts/build-evidence-bundle.mjs` | `811`, `881` | `writeFileSync(summaryPath, …)` × 2 |

**事实**：本仓 `_lib/destructive-write.mjs` 提供了三条硬保证——**同文件守卫 + 时间戳 `.bak` 回滚点 + temp-rename 原子写**——并明确要求「**报告类写盘一律经 `writeReport`**」（`count-chars.mjs:244` 原文）。上述 8 处**都是持久化的交付/状态产物，却全部是裸 `writeFileSync`**，因此：

1. **无原子性**：写入中途被 kill（超时 / Ctrl-C / 断电）→ 目标文件半写损坏，且**无 `.bak` 可回滚**；
2. **`round-ledger.appendLedgerRow` 是典型的读-改-写**（`:190`）：两次写入交叠即**丢失更新**（后写者基于陈旧快照覆盖），而账本承载的是**轮次额度**这种「判据输入」（`parseLedger` 的 `over` 直接喂给 `handoff-check.mjs:888` 与 `apply-revision-cycle.mjs:71`）；
3. **无 `.bak`**：这四类产物一旦写坏，**没有任何自动回滚点**。

**边界（如实，不夸大）**：我**没有**找到当前版本里真的并发调用 `appendLedgerRow` 的调用方（唯一调用点 = `apply-revision-cycle.mjs:276`，单进程顺序执行），素材池同理。故**当前更现实的风险是「半写损坏 + 无回滚点」**（1、3 两条），而非并发丢失更新（2）——**后者是设计缺陷、未必已发生**。

**建议**：把这 8 处改为 `writeWithSafety(..., { inPlace: true })`（账本与池文件都属「本就允许在原位反复重写」的形态，与 `writeReport` 的既定用法一致）。这一步**零行为变更**、只加原子性与回滚点，成本 ≈ 8 行。

**严重度**：P1 ｜ **已验证（裸写事实与缺失保证）／疑似（并发丢失更新是否已发生，需人工复核）**

### P1-4 盲评件契约的「**首节**」要求写在帮助文本与用例名里，但代码只判「**存在**」

**位置**：`skills/lunheng-article-pipeline/scripts/handoff-check.mjs:281-284`

```js
// ③ 「已读范围」为首节且非空                       ← 注释自称「为首节」
const mRead = /^##\s*已读范围/m.exec(text)          ← 但正则只是「任意位置有一个 ## 已读范围 行」
if (!mRead) { hard.push({ check:'BR-A4', ..., detail:'缺首节「## 已读范围」…' }) }
```

**同一处声明出现在三个地方**：

- `handoff-check.mjs:74`（`--help`）：「六维名逐字 + 每维 x/5 + 总评分 = 六维之和 + **首节**「已读范围」非空 + 禁忌面（自述层）」
- `handoff-check.mjs:281`（注释）：「「已读范围」**为首节**且非空」
- `tests/blind-review.test.mjs:8`（用例文件头）：「…/ **首节**「已读范围」非空 / 禁忌面自述」
  —— 而该文件 `:78-84` 的 B4 用例只测「**删掉**该节 → 硬 21」，**没有任何用例把该节放到非首位**。

**复现（已验证，实跑）**：把 `## 已读范围` 前面插入另一个 `##` 节后再跑：

```
正常盲评件（首节=已读范围）      → exit 22（仅 BR-A6 匿名声明软提示）
已读范围 不是首节（前置另一 ##） → exit 22，hardCount: 0，hard: []      ← 与正常件**不可区分**
缺已读范围                       → exit 21，hard: [BR-A4]              ← 只有「完全没有」才拦
```

**为什么这不只是措辞问题**：该门的自述理由是「盲评的**全部效力**建立在『读的是什么』可核对之上」（`:284`）。「写在最前、读完即记」与「写在末尾、事后追补」在**审计意义上不同**——门既然把「首节」写进了契约，就应判它；否则应把三处措辞统一降为「须含」。

**建议**（改判据或改措辞，任选其一，**但必须两边同改**）：

```js
// 取「第一个 h2」而不是「任意 h2」
const firstH2 = /^##\s*(.+?)\s*$/m.exec(text)
const mRead = /^##\s*已读范围\s*$/m.exec(text)
if (!firstH2 || firstH2.index !== mRead?.index) { /* 判硬 21：已读范围必须是首个二级节 */ }
```

改判据时请同步补一条**反向用例**（首节非「已读范围」→ 硬 21），否则同类漂移会再犯。

**严重度**：P1（契约未实现 + 无测试钉住）｜ **已验证**

### P2-1 `refresh-gates` 把**字面量**当「源文件路径」传进同文件守卫 → 守卫恒不生效

**位置**：`scripts/refresh-gates.mjs:209`

```js
if (!dryRun) writeWithSafety(abs, text, { source: 'refresh-gates.mjs' });   // ← source 是文件名，不是路径
```

**事实**：`writeWithSafety(p, text, { source })` 的契约是「`source` = **本次运行读过的源文件路径**」，内部执行 `assertNotSameFile(source, p)`（`destructive-write.mjs:205`）。传入字面量 `'refresh-gates.mjs'` 会被 `resolve()` 成 `<cwd>/refresh-gates.mjs`——**该文件不存在**，`sameFile` 对不存在的路径在 `pathKey` 不同后 `stat` 失败即返回 `false`（`:69-71`）→ **守卫永远放行**。

**当前实际影响**：**无**——该脚本的刷新目标是 `audits/闸门记录-T2.5.md`、`audits/闸门记录-T7.5.md`、`final/交付说明.md`（`:6` 与 `:89-90`），**不可能等于源正文** `final/定稿.md` / `drafts/初稿-vN.md`，所以「守卫不生效」今天不会被触发。

**为什么仍要报**：这是**语义误用**——把「人读的标签」写进了「机器判据的槽位」。它有两个真实代价：① 读代码的人会以为这里有源文件保护；② 一旦将来有人把某个交付件的路径加进刷新目标，保护会**静默失效**。建议传 `src.abs`（源正文真路径），或删掉该参数并显式注释「本脚本的刷新目标与源正文不相交」。

**严重度**：P2 ｜ **已验证（守卫不生效）／当前无可触发路径（如实）**

**为什么值得单独成条**：这三个脚本**同时**满足三个条件——① 被 `SKILL.md:49` 白名单正式登记为「随包脚本」；② 被 `pipeline-readme.md:252` 排进 **Phase 0.5（查池）与 Phase 5（回写）的标准动作**；③ 由 `pool-extract`/`pool-query` **直接写盘**（P1-3）。**零测试 + 直接写盘 + 标准流程动作**三者叠加，是本次 P1-1/P1-2 能长期潜伏的结构性原因。且 `readJson` 里两处都写着「容忍 BOM」（`pool-extract.mjs:56`、`pool-query.mjs:38`）——说明作者遇到过真实输入问题，却没有把它固化成用例。

### P2-7 测试超时口径两处不一致（180s vs 240s）

**位置**：`package.json:76-77` = `--test-timeout=180000`；`scripts/no-write-check.mjs:88` = `--test-timeout=240000`

**事实**：`no-write-check` 是**发布前固定动作**、且它包的就是「全量套」（`:88` 注释自称）。两处超时不同意味着：**CI/本地按 `pnpm test` 判定的「通过」，与发布前 `no-write-check` 判定的「通过」不是同一个判据**——一个 180 s 内必须完成的用例，在 `no-write-check` 里可以跑到 240 s。对**计时敏感或偶发变慢**的用例（本仓有大量 `spawnSync` 子进程用例），这会造成「本地红 / 发布前绿」或反之。

**修法**：抽一个真源（如 `package.json` 的 `dsh.testTimeoutMs` 或直接统一为 240000），两处引用同一值。

**严重度**：P2 ｜ **已验证**

### P2-8 `--blind-review` 只对文件做「存在 + 0 字节」判定，不校验**扩展名 / 扩展名与内容形态**

**位置**：`handoff-check.mjs:258-261`

**事实**：给定任意**非空**文件（含 `.txt`、`.json`、二进制），该模式都会进入契约解析并可能判 0/22。这是**窄判据**而非缺陷（六维正则自然会失败），故仅登记为**输入面收窄建议**：可加一条「非 `.md` 后缀 → notes 提示」，避免把明显非盲评件的路径当真运行。

**严重度**：P2（低）｜ **疑似（未构造二进制样例复现，需人工复核）**
