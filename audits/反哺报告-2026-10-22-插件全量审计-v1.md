## 二、本次审计发现的可沉淀问题（按问题族排序）

### 1. 证据与读面边界没有统一收口（P1-1、P2-4、P2-5、P2-9）

这是最高频、也最需要沉淀到主控和审计角色卡的一类问题：**目录已经过围栏，不等于所有固定文件读取、证据缺失和测试入口也经过同一围栏。**

1. **P1-1（原 A01）面板固定文件读取可穿透目录链接**  
   [面板快照实现](<E:/HERNESS/lunheng-article-pipeline-dsh/lib/panel.mjs#L397-L417>)直接读取状态、日志和运行报告；[HTTP 快照路由](<E:/HERNESS/lunheng-article-pipeline-dsh/lib/panel.mjs#L1005-L1012>)直接返回结果。离线夹具把 `final` 链到项目外目录后，响应状态为 200，返回了 `OUTSIDE_PROJECT_SENTINEL`。这是已复现的结构化越界泄露。

2. **P2-4（原 A07）缺少回执账本时，现代项目可能退回更弱检查**  
   [交接门实现](<E:/HERNESS/lunheng-article-pipeline-dsh/skills/lunheng-article-pipeline/scripts/handoff-check.mjs#L961-L974>)对历史项目保留兼容；[账本缺失分支](<E:/HERNESS/lunheng-article-pipeline-dsh/skills/lunheng-article-pipeline/scripts/handoff-check.mjs#L1203-L1209>)只写 notes。探针显示：账本存在但不相容时 exit 21、A7 四项硬失败；移走账本后 A7 为空、exit 22。尚未证明整体 exit 0 绕过，但已证明删除证据会降低检查强度。

3. **P2-5（原 A08）host install smoke 未先检查 dump 状态**  
   `host-install-smoke` 只核对输出文本，未把 `dump.status` / `dump.error` 作为先决条件；若进程先输出目标行再非零退出，可能假绿。此项由源码控制流确认，未进行真实安装复现。

4. **P2-9（原 A12）默认测试入口隐含真实安装行为**  
   `tests/host-install-smoke.test.mjs` 在 PATH 发现 `dsh` 时会调用临时 profile 安装脚本。该路径会执行 `dsh plugin add`，可能联网；本机因 `dsh` 不在 PATH 而跳过。安装测试应和离线单元套件明确分层，不能让“test”名称掩盖副作用。

**沉淀方向**：主控必须把“输入材料、读面、安装、联网、历史项目”分成可见状态；审计员必须检查固定文件入口，而不是只看目录遍历入口；缺证据不得自动获得更高可信度。

### 2. 跨阶段状态与发行契约依赖非持久变量（P1-2、P1-3、P2-8）

1. **P1-2（原 A03）`latest` 硬断言 step 使用了前一 step 的 `VER`**  
   [发布 workflow 硬断言](<E:/HERNESS/lunheng-article-pipeline-dsh/.github/workflows/publish.yml#L222-L231>)启用 `set -u` 后引用未定义变量；离线 shell + npm stub 复现 `VER: unbound variable`。发生在 publish 之后，可能出现包已经发布但 job 失败、后续 Release 不运行。

2. **P1-3（原 A04）tag 发布不等待同 SHA 的完整 CI 成功**  
   CI 对 `v*` tag 的触发和发布 workflow 的门集合不一致；发布 workflow 的祖先关系检查不能证明 CI 已绿。CI 专属的 drift、冻结安装和 host contract 门没有作为同 SHA 的发布前置条件。该项由 workflow 配置和门集合探针确认，未触发真实发布。

3. **P2-8（原 A11）维护政策与实际 workflow 漂移**  
   `CONTRIBUTING.md` 仍描述 latest 永不自动前移，而当前 workflow 已尝试 OIDC / token 兜底；link-check 头注释也落后于实现范围。当前 link-check 本身为 123 个 Markdown、1558 个引用实例、broken 为空，故问题是语义维护漂移，不是当前断链。

**沉淀方向**：凡跨 step、跨 agent、跨轮次使用的值，都必须进入显式输出、账本或 artifact；shell 局部变量不能作为交接；发行前置条件必须引用同一 SHA 的可验证 check，而不是复制一份相似命令。

### 3. 机检候选被误当成事实，且错误集合操作不保持单调性（P2-1、P2-2、P2-3）

1. **P2-2（原 A05）事实门把正常时序变化判成 P0**  
   [M-Fact-1](<E:/HERNESS/lunheng-article-pipeline-dsh/skills/lunheng-article-pipeline/scripts/_lib/mgate-gates/mfact-gate.mjs#L124-L158>)按数字前短标签聚合，丢失年份、主体和口径。输入“2020 年覆盖率 60% / 2025 年覆盖率 80%”被判为摘要核心冲突 P0。未证明是同一时点、同一主体、同一口径时，不应直接硬失败。

2. **P2-3（原 A06）异单位命中会取消同单位冲突检查**  
   `units.size > 1` 后整组跳过。原本 60% / 80% 的同单位冲突，加入另一条不同单位记录后整体变成通过。错误处理不满足“添加无关观察不得抹掉已有发现”的单调性。

3. **P2-6（原 A09）受管数字只检查第一次匹配**  
   `derive-facts` 对同类声明使用首个 `.exec`；前文正确、后文 999 的矛盾仍可能 `issues=[]`。该项已由离线探针复现。

**沉淀方向**：正则和短标签只能生成候选；硬等级必须由上下文、来源和人工或更强的结构化字段确认。错误集合应满足单调性：新增无关命中不能让既有错误消失，删除证据不能让验证状态变好。

### 4. 测试绿灯与实际行为承诺没有完全对齐（P2-1、P2-5、P2-7、P3-1）

1. **P2-1（原 A02）面板把 exit 22 计入 `handoffs.ok`，却未单独统计 exit 0**  
   [面板状态解析](<E:/HERNESS/lunheng-article-pipeline-dsh/lib/panel.mjs#L533-L534>)把“仅软提示”与“已通过”混在成功视图中。论衡规则明确 22 不等于已验收；面板可能把未完成的交接显示得过于乐观。

2. **P2-5（原 A08）host smoke 的异常状态覆盖不足**  
   同时属于边界问题和测试证据问题：当前测试只覆盖成功路径，没有“含目标行但 exit 1 / timeout / dump.error”负向样本。

3. **P2-7（原 A10）宽断言、吞异常和静默 return 弱化了测试证据**  
   `e2e-pipeline-chain` 允许与注释不一致的返回码；部分测试把未知异常当成环境限制或直接 return，使测试通过强度高于其实际证明范围。不是全套测试无效，而是行为承诺没有全部被精确断言。

4. **P3-1（原 A13）CI 四平台重复跑完整套测试**  
   每个平台先跑包装器再裸跑同套测试，形成四个平台八次重复。它源于历史防止包装器吞退出码的补丁，暂不视为功能缺陷；但增加维护成本，并扩大 workflow 分叉面。

**沉淀方向**：测试应优先执行实际控制流；静态字符串钉只证明“文本存在”；`skip` 必须说明原因，未知异常不得自动降级为 pass；`22 / 0 / 20 / 21` 必须在 UI、报告和测试中保持同一语义。

## 四、主动建议沉淀的规则

以下规则是建议写入角色卡、维护者文档或回归测试的草案，不是已经生效的机制。每条同时给出“产物 / 运行侧补偿”与“工具 / 机制侧修法”；按插件规则，默认先考虑产物侧补偿，只有满足“规范与实现不一致”或“覆盖盲区”时才建议改工具。

### R-01 统一读写原语与物理围栏

- **建议沉淀位置**：T0 主控扩展职责、T7 审计员；维护者文档的面板安全边界。
- **规则草案**：所有项目内固定文件读取、目录枚举、快照和下载都必须经过同一条“会话工作区 → 项目目录 → realpath 物理包含”判定；目录遍历守卫不能代替固定文件读取守卫。
- **产物 / 运行侧修法（默认）**：运行项目不把状态、报告或 token 产物放在工作区外；在交付前记录项目根、每个证据目录 realpath 和 `manifest.json` 绑定关系；发现链接或 junction 时标记未验证，不把面板读数作为独立证据。
- **工具 / 机制侧修法（本项建议采用）**：抽取受控 `readProjectFile()`，让 `lightSnapshot`、`/file`、`/snapshot`、`/events` 共用；固定文件逐个检查 `lstat` / `realpath`；越界返回拒绝而不返回部分快照。理由：这是已复现的实现覆盖盲区，不能只把风险转嫁给文章产物。
- **验收**：普通文件通过；项目内叶链接、祖先 junction、断链、外部目标分别有 HTTP 负向用例；越界响应不包含 sentinel。

### R-02 跨 step / 跨 agent 状态必须持久化

- **建议沉淀位置**：T0 主控扩展职责、维护者发布文档。
- **规则草案**：任何后续步骤使用的版本号、项目代号、输入 hash、门状态，都必须来自明确的 output、artifact 或日志；不得依赖前一 shell 的局部变量或模型记忆。
- **产物 / 运行侧修法（默认）**：在发布和交接摘要中重复写入版本号、提交 SHA、门状态；对每次重试保留 attempt 编号和输入快照。
- **工具 / 机制侧修法（本项必须）**：`publish.yml` 的硬断言 step 自行计算 `VER` 或读取 job output；增加 shell stub 行为测试，覆盖当前版本、补推旧 tag、registry 失败和 `set -u`。
- **验收**：单独执行该 step 时无未定义变量；当前版本能比对；旧 tag 不因防回退策略错误失败；npm 查询失败时按声明的失败等级呈现。

### R-03 发布只认同 SHA 的完整门结果

- **建议沉淀位置**：维护者文档、发布 workflow；T0 发行前检查清单。
- **规则草案**：tag 发布的前置条件必须是同一 commit SHA 的要求 checks 全部成功；祖先关系只能证明来源，不能代替 CI 结论。
- **产物 / 运行侧修法（默认）**：发布单记录 commit SHA、check-run 名、结论和查询时间；未取到 check 结果时标记 `unverified`，不标绿。
- **工具 / 机制侧修法（本项必须）**：使用可复用 workflow 或显式查询同 SHA required checks；将 drift、frozen-lockfile、host-contract 纳入统一发布门，避免复制两套清单。
- **验收**：同 SHA 的任一专属门失败、进行中、缺失或超时，publish 均不启动；所有 required checks 成功后才允许 publish。

### R-04 正则只产候选，硬等级需要上下文

- **建议沉淀位置**：T7 审计员、T8 终检；事实门说明。
- **规则草案**：数字短标签命中不等于同一事实。硬 P0/P1 前至少保留时间、主体、范围、单位和来源；缺任一关键限定时出候选交语义复核，不因“摘要 / 结论”位置自动升级。
- **产物 / 运行侧修法（默认）**：写作侧对同一指标使用统一字段：指标名、观察期、主体、口径、单位、来源卡；跨年、跨群体、跨地区比较必须在句中显式标注。
- **工具 / 机制侧修法（本项建议采用）**：M-Fact-1 按结构化上下文或 `key + time + subject + unit` 分组；上下文不足时 severity 降为候选 / P2，交 T7/T8；补正常变化负对照。理由：当前实现已证明会产生硬门假阳性。
- **验收**：正常跨年增长、地区比较、群体比较不判冲突；真正同口径冲突仍能发现；摘要核心冲突必须能追溯到四要素。

### R-05 检查结果满足单调性

- **建议沉淀位置**：T7 审计员、T8 终检、测试维护者。
- **规则草案**：新增无关观察不得消除既有错误；删除证据不得提高验证状态；未知不得落为通过。
- **产物 / 运行侧修法（默认）**：在审计报告中分别列“已发现”“未执行”“无法比较”“缺输入”，不把未执行写成无问题。
- **工具 / 机制侧修法（本项建议采用）**：事实门按 `key + unit` 分桶，不因异单位整组 `continue`；`derive-facts` 用 `matchAll` 检查全部声明；状态机显式区分 `pass / fail / skipped / unverified / legacy`。
- **验收**：对任一阳性夹具添加无关行，既有 failure 集合不减少；删除证据后的状态不优于删除前；后续数字矛盾和逆序矛盾均被发现。

### R-06 缺证据不能通过删除获得更宽松结果

- **建议沉淀位置**：T0 主控扩展职责、T8 终检、交接报告模板。
- **规则草案**：历史项目兼容必须由显式 schema / createdWith / migration 状态决定；不能用“文件不存在”推断它是旧项目。
- **产物 / 运行侧修法（默认）**：新项目在 Phase 0 固定 schema 版本；缺账本、缺会话日志、缺证据包时写 `unverified` 与处置动作，不自行填补主人原话。
- **工具 / 机制侧修法（本项建议采用）**：给项目目录写入不可变的创建版本或交付协议版本；现代项目缺 `gate-receipts.jsonl` 判硬；存量项目只标 legacy/unverified，不回头重判历史 run。
- **验收**：同一现代项目删除账本后不得从硬失败变成仅提示；历史项目仍不被强制重跑；报告明确区分 legacy 与 current。

### R-07 测试命令必须显式声明副作用等级

- **建议沉淀位置**：维护者文档、CI workflow、T0 审计启动清单。
- **规则草案**：默认测试必须离线、无安装、无发布；安装 / 网络 / 真实 Host 启动测试单独命名并显式 opt-in。
- **产物 / 运行侧修法（默认）**：审计报告先记录命令副作用和 skip 原因，再报告测试数量；禁止把 integration skip 写成真实安装通过。
- **工具 / 机制侧修法（本项建议采用）**：拆分 `unit`、`offline-integration`、`host-install`；host-install 只在专用 CI job 或显式变量下执行；先判 `status/error/exit/signal/timeout` 再核输出文本。
- **验收**：无 `dsh` 时明确 skip；有 `dsh` 时默认单元套件不触发 `plugin add`；含目标行但非零 / 超时的 dump 一律失败。

### R-08 行为承诺优先用执行测试，静态钉只做补充

- **建议沉淀位置**：维护者文档与测试规范。
- **规则草案**：源码字符串钉只能证明实现文本存在，不得证明 shell 控制流、异常分支或外部契约已经生效。
- **产物 / 运行侧修法（默认）**：报告中把“源码确认”“行为复现”“未测”分栏，不能把静态绿色写成行为绿色。
- **工具 / 机制侧修法（本项建议采用）**：workflow 使用 stub npm / fake check API / 临时 profile 做离线控制流测试；宽断言只保留在兼容性测试中并写清理由；未知异常抛出，环境限制使用显式 `skip`。
- **验收**：`latest`、404、断网、认证失败、旧 tag、新版本竞态均有可执行样例；异常不被 catch 成“环境限制”通过。

### R-09 文档政策只能有一个当前权威面

- **建议沉淀位置**：维护者文档、CHANGELOG / ADR 索引。
- **规则草案**：历史事故说明和当前操作政策分离；当前政策只保留一个权威入口，其余只留链接和版本背景。
- **产物 / 运行侧修法（默认）**：每次发布记录当前策略、例外和人工动作；审计报告引用当前权威文件而不是旧注释。
- **工具 / 机制侧修法**：清理 `CONTRIBUTING` 与 workflow 的冲突叙述；让 link-check 头注释从 scope 常量派生，或改成不陈述易漂移的固定数字。
- **验收**：latest 策略、link-check 扫描范围、CI 门集合分别只有一个当前事实源；历史说明不再以现在时态给操作指令。

## 九、结论

本轮反哺的核心不是“再增加一条提示词”，而是把以下四条不变量转成可验证机制：

1. **边界不变量**：所有读面都必须走同一物理路径围栏；
2. **证据不变量**：删除、缺失或未核验的证据不得改善状态；
3. **状态不变量**：跨 step / agent / round 的值必须持久化并绑定版本、SHA 和 attempt；
4. **判定不变量**：候选、软提示、未执行、legacy 与通过必须保持可区分，正则不得替代上下文判断。

这些规则能直接减少论衡流水线中“自述完成但无法复盘”“门绿但控制流未验证”“缺证据反而更容易通过”“正常事实变化被硬门打回”四类重复事故。报告交付即完成本轮反哺产出；任何机制合并均留给主人 review，不在本轮自动执行。
