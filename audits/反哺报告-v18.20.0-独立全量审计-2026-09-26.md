## §二、问题清单

### P1-① lunheng-commands 子技能版本漂移：1.0.0 vs 1.0.1（「已修却只修了一半」）

**现象**（三处漂移，两处随包）：
| 文件 | 现值 | 应为 | 是否随包 |
|---|---|---|---|
| `skills/lunheng-commands/SKILL.md` | `version: "1.0.1"` ✓ | 1.0.1 | 是 |
| `skills/lunheng-commands/references/command-routing.md` | `v1.0.1` ✓ | 1.0.1 | 是 |
| `skills/lunheng-commands/README.md:1` | `# lunheng-commands v1.0.0` ❌ | v1.0.1 | **是（npm pack 实测在包内）** |
| `skills/lunheng-commands/package.json:3` | `"version": "1.0.0"` ❌ | 1.0.1 | 否（`!skills/lunheng-commands/package.json` 排除） |

**根因**：v18.7.1 把 lunheng-commands 从独立包**嵌入**论衡 bundle 时，升了 SKILL.md / command-routing.md / route-command.mjs 三处版本，**漏了 package.json 与 README.md 两处**。v18.7.1 全量审计报告（`audits/全量审计报告-v18.7.1.md:40`）**已把「子技能版本 1.0.0/1.0.1 漂移」列为中等问题**，但 v18.7.2 修订方案（`docs/审计与修订记录/论衡插件-修订方案-v18.7.2.md:64`）的同步点清单里**同样漏了这两处**——「已修」记载只覆盖了当时盯住的那一处，漂移存活到 v18.20.0。

**为何门没抓**：consistency-check 规则① 只对账**主包**版本（package.json 主包 ↔ SKILL.md frontmatter ↔ 版本头 ↔ 仓库级文档），**不覆盖子技能自己的 1.0.x 版本**；`skills/lunheng-commands/package.json` 是 JSON，不在 .md 扫描面内。

**修法**：把 `README.md` 标题、`package.json` version 两处升到 `1.0.1`（各 1 行，用 edit 精确匹配）。**验收判据**：`grep -rn "1\.0\.0" skills/lunheng-commands/` 仅剩 CHANGELOG 历史留痕语境。

### P1-② lunheng-commands 声称「11 个命令」却只枚举 10（漏 `-stats`）

**现象**：真源 `route-command.mjs` 的 `COMMANDS` 表 = 11 个（`-draft/-resume/-cite/-audit/-journal/-ppt/-history/-rollback/-status/-stats/-help` + `-h` 别名）。但：
- `skills/lunheng-commands/README.md` 代码块只列 10 条，**缺 `/lunheng -stats`**；
- `skills/lunheng-commands/package.json` description「提供 11 个…」后枚举也只 10 个，**缺 `-stats`**。

对照：`SKILL.md` description 枚举正确（含 `-stats`）✓。

**为何门没抓（真盲区）**：consistency-check 规则㉕（命令数口径）只核对「**N 个**」这个**数字字面量**是否等于真源数（`N 个 /lunheng 命令` → N ≠ 11 → P1）。README.md 写的是「11 个」（数字正确），故通过；**它从不核对枚举清单本身**。`-stats` 是 v18.5.0 就存在、v18.7.1 才补回斜杠包装的真实功能，README 缺它 = 用户读随包文档发现不了这个命令。

**修法**：① 两处枚举补 `-stats`；② **（治本）** 扩展规则㉕——从「核数字」升级到「核枚举」：解析 README 代码块 / package.json description 里的 `-xxx` 清单，与 `route-command.mjs` 的 `COMMANDS` keys **双向对账**（多列/少列都报 P1）。见 §四优化方向。

### P2-① dsh-plugin-guide 本地 0.3.10 vs pin 0.3.16（本地门 ≠ CI 门）

**现象**：`plugin-surface-check.mjs` 输出 `CLI 版本：0.3.10（pin = dsh-plugin-guide@0.3.16）` + 显式警告「⚠ 实际 CLI 版本 0.3.10 与 pin 0.3.16 不一致」。原因：`CLI_SPEC` pin 已抬到 0.3.16（v18.2.9），但本机 `~/.dsh/profiles/desktop/node_modules/dsh-plugin-guide` 仍是 0.3.10，零下载路径**优先命中旧装**。

**影响**：本地跑门用 0.3.10 语义、CI（无本地 profile，走 dlx）用 0.3.16 语义——**「本地全绿 CI 红」或反向的漂移风险持续存在**（仓库记忆里反复踩过「本地假绿、CI 才红」）。代码注释已如实声明此漂移，属「已知但未处置」。

**修法**：把本机 profile 的 dsh-plugin-guide 升到 0.3.16（或 `DSH_PLUGIN_DEV_SPEC=dsh-plugin-guide@0.3.16` 强制 dlx 命中 pin），消除本地/CI 版本差。

### P2-② 词预算触顶（AGENTS.md 仅余 41 B）

**现象**（repo-hygiene 规则⑨ 读数）：
- `skills/lunheng-article-pipeline/AGENTS.md` = 21463 B / 上限 21504 B / **余量 41 B**；
- `references/_shared/规范-机械门对照表.md` = 35699 B / 上限 35840 B / 余量 141 B。

**影响**：AGENTS.md 余量 41 B 意味着**连一个汉字都加不进去**——任何后续机制文档增长都必须在同一次提交里显式抬棘轮上限（规则⑨ 已设此约束，抬升需写明理由）。这是棘轮机制**在正常运作**，但同时也提示文档规模已逼近「必须主动瘦身而非被动抬升」的拐点。

**修法**：不抬上限，改做一次**注解聚合/精简**（AGENTS.md 卡头已有「注解聚合」机制，可把历史分层注解进一步收敛），把余量拉回 >1 KB 安全线。

### P3-② README.md（英文）对 11 命令的松散描述与真实命令集不符

## §四、进一步优化方向

1. **规则㉕ 升级为「枚举对账」**：把「N 个」数字核对扩展为「解析文档里的 `-xxx` 命令清单 ↔ `COMMANDS` keys 双向对账」。一举消灭 P1-② 这类「数字对、清单漏」盲区，且天然覆盖 README 代码块与 package.json description。
2. **子技能版本纳入一致性门**：规则① 现只对账主包 18.x 版本；新增对 `skills/lunheng-commands/` 三件套（SKILL.md / README.md / package.json）自身版本（1.0.x）的交叉核对，防「子技能漂移」复发（正是 P1-① 的形态）。
3. **lunheng-commands 去双重身份**：它既是「内嵌子技能」又残留「独立 npm 包」形态（package.json + peerDep + 独立 1.0.x 版本号）。建议二选一明确语义——① 彻底去包化（删 package.json，版本跟随父包 18.x）；② 或保留但把版本 bump 纳入主发版级联（bump-version.mjs 同步升 1.0.x）。当前「两头都不归」是漂移温床。
4. **AGENTS.md 主动瘦身**：词预算触顶，优先走注解聚合而非棘轮抬升（见 P2-②）。
5. **本机 dsh-plugin-guide 升级到 pin**：消除本地/CI 门版本差（见 P2-①）。
