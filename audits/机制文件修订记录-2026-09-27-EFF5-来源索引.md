## 二、设计决定：为什么是「每线一个分片」而不是「三线共写一个 sources.json」

报告原文写「新增 `run/<项目>/sources.json`（模板）」。**落地时改成三线分片 + 主控合并**，理由是本仓已记载的**并发写**判据：
三个子代理（T1/T2/T3）**并发**写同一文件必然互相覆盖——这正是 `status.md`（**主控独占写**）/ `agents-log.md`（**子代理各自追加**）当初分离的同一原因（教训：T1/T2 与主控并发写冲突）。
故：

- `sources/{T1,T2,T3}.jsonl` —— append-only、**每线独占**（与 `agents-log.md` 同形）；
- `sources.json` —— **只有主控**在 Phase 2.5 跑 `--merge` 生成（与 `status.md` 同形）。

**这不是偏离报告意图**：报告要的是「三线共享一份来源索引」，分片 + 合并给出的正是共享视图，且不引入并发覆盖这一新缺陷。

## 三、两条边界（刻意，写进模板与脚本头）

1. **它不是门**：`--check` 只校验**行是否合法**、只**统计**跨线重复——**重复是收益来源，只报不判错**；「该不该抓某个源」由各线自行判断。
2. **缺分片 / 空分片不判错**（= 该线尚未登记）——与 M-Exist-10/11「缺输入记 **N/A 且未检**」同一口径（本会话第四次沿用该口径）。

## 四、连带修复（本批自抓）

**⑧d 的既定形状**：新脚本头部我把退出码写成「`0` 成功｜`1` …」，而 ⑧d 解析器要求 **`N = 语义`** 形式 → 报「解析出 0 个码」。**已按门的形状把头部展开为四行**。
**判据**：门有既定形状要求时**按门的形状写**，不为了让自己的自由格式通过而改门。

## 五、已知缺陷（如实登记，下一批处理）

**`_lib/script-surface.mjs` 写盘词表漏 `writeReport`**：`writeReport`（原子写 + `.bak`）**会落盘**，但词表只收 `writeFileSync` / `writeWithSafety` / `appendFileSync` / `copyFileSync` / `renameSync` / `rmSync` / `unlinkSync` → **只用 `writeReport` 的脚本被 ⑧c 算作「只读」**：实测涉及 `cite-coverage-check` / `journal-fit` / `structure-check` / `methodology-check` / `quality-score`（它因 `rmSync` 被算写盘，`writeReport` 只是次要）/ 本批 `sources-index`。
