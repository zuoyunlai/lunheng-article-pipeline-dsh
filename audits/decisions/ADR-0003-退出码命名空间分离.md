# ADR-0003 — 退出码按「命名空间」分立：M 门 `0/1/2/3` 与交接门 `20/21/22` 刻意不共用

> **状态为「回填」**：本决策由 v18.0.2 统一退出码、v18.6.0 交接门、v18.12.0 收口三批合成，当时未以 ADR 形式登记。本件于 2026-09-29 按证据回填。

- **Status**：`Accepted（回填，2026-09-29 登记）`
- **Date**：2026-09-29（登记日；含 v18.0.2 / v18.6.0 / v18.12.0 三层）
- **Version**：v18.12.0（最后一层：把全仓「用法/参数错记 1」的最后三处收口到 10）
- **Supersedes**：`exit 1` 兼表「内容失败」与「用法/参数错」；交接门复用 M 门 `1/2/3`
- **Evidence**：`scripts/_lib/exit-guard.mjs:3-9`（v18.0.2 统一显式分支为 10，但**未捕获异常仍走 Node 默认 `exit 1`**，而 1 的语义是「P1 内容失败」）／`:17-18`（`EXIT_USAGE = 10`、`EXIT_INTERNAL = 70`）／`:9`（「两者都不与 0/1/2/3 的 M 门语义混用」）／`AGENTS.md`「闸门留机械证据」「阶段闸门」两条

---

## Context

**事故（两次，同型）**：

1. **未捕获异常撞上内容判定码**：v18.0.2 把**显式分支**里的路径错统一为 `10`，但脚本抛出的**未捕获异常**仍走 Node 默认 `exit 1`——而 `1` 在 M 门语义里是「**P1 内容失败**」。于是 `count-chars <目录>`、`m-gate-check <目录> <目录>` 这类**用法错**被读成**内容失败**，进而误触发修订轮。`exit-guard.mjs:3-4` 记录了这一缺口。
2. **交接门若复用 M 门码会重演同一误判**：交接门（`handoff-check.mjs`）的失败形态是「产物缺失 / 结构不合 / 仅软提示」——与 M 门的「P0/P1/P2 内容判定」**是完全不同的语义**。若复用 `1/2/3`，读者会把「产物没落盘」读成「论文内容有 P1」。

**根因重析**：`0/1/2` 这套通用惯例**只有一个失败维度**（成败），而论衡的失败有**至少三个正交维度**——① 内容判定（P0/P1/P2）② 用法/参数/路径错误 ③ 基础设施/脚本缺陷。用一维编码表达三维语义，**必然撞码**；而脚本的消费者（主控、CI、子代理）**只读码不读文本**，所以撞码不会被文本提示兜住。

**一条可操作的判据（本决策的副产品）**：

> **只要脚本不做内容判定，它的 `1` 就一定是撞码。** —— 它的 `1` 不可能是「P1 内容失败」，所以必然是误用。

## Decision

**退出码按命名空间分立，不同语义绝不共用同一个数**：

| 码 | 命名空间 | 语义 |
|---|---|---|
| `0` | M 门 | 通过 |
| `1` | M 门 | **P1 内容失败** |
| `2` | M 门 | **P0 内容失败** |
| `3` | M 门 | 仅 P2/soft/SKIP（**须人工复核，不得当通过**） |
| `4` | 工具专用 | `model-routing.mjs`：需人工决定（**不与 M 门语义共用**） |
| `10` | 通用用法 | **参数 / 路径 / 用法错**——所有脚本一律用 10，包含闸门脚本 |
| `20` `21` `22` | **交接门专用** | `20` 产物缺失或 0 字节（重派）／`21` 结构·版本·成对·回报段不合（续接补交）／`22` 仅软提示（人工复核放行） |
| `30` `40` | 专用 | 各自登记 |
| `70` | 通用内部 | `EX_SOFTWARE`：脚本缺陷——**与任何内容判定码都不撞** |

**具体三条**：

1. **交接门 `20/21/22` 与 M 门 `1/2/3` 刻意分离**——判据是「复用会重演『`exit 10` 被读成 P1』事故」。
2. **不做内容判定的脚本，其「用法/参数错」一律 `10`**（v18.12.0 把该族最后三处 `token-budget` / `token-cost` / `model-routing` 收口）。
3. **异常兜底**：`exit-guard` 把未捕获异常收敛到 `10`（fs 类）或 `70`（其余），**幂等安装**。

## Regression-proof anchor

1. **行为测**：`tests/handoff-check.test.mjs`（11 处，交接门三码）+ `tests/scripts.test.mjs`（56 处）+ `tests/argv-strictness.test.mjs`（13 处）+ `tests/exit-resolution.test.mjs`（2 处）——覆盖「未知参数 → 10」「用完模式仍 exit 10」等。
2. **源码钉**：`repo-hygiene-check` **规则 ⑧** 静态解析全部随包脚本的 `process.exit` / `exitCode` 两种写法并核对**退出码契约表**；**规则 ⑧b** 核「代码侧码 ↔ §8 配额 ↔ §8 表格」**三方一致**；**规则 ⑧d** 核脚本头部自述码 ⊆ 自身契约行。
   > 本决策是本地**少数已具备源码钉的决策**——⑧/⑧b/⑧d 即其锚点，可作为 ADR-0001「源码钉」要求的一个现成范例。

## Consequences

### Positive

- **误判链被切断**：用法错（10）不再被读成内容失败（1），交接门失败不再被读成 P0/P1。
- 主控与 CI 可以**只看码**做分支，不需要解析人读文本。
- 新增脚本「属于哪个命名空间」有明确归属问题可问——**迫使作者想清楚自己的失败维度**。

### Negative

- **【明确认赔】** 退出码**偏离通用惯例**（`10/20/21/22/70` 不是 POSIX/CLI 常见约定），**必须查表**才能读懂；新手第一次看到 `exit 21` 不会知道那是「交接报告结构不合」。我们接受——**语义明确性优于惯例一致性**，且 `AGENTS.md` 与 `exit-guard.mjs` 头部都登记了表。
- 命名空间一多，**新增码的分配成为协调动作**（须在 `§8 配额` 与契约表两处登记，规则 ⑧b 会机械核）——增加了一点流程成本。
- `4` 的存在（`model-routing` 需人工决定）**刻意不与 M 门共用**，因此「4」在不同脚本里**不是同一个意思**——这是命名空间分立的代价，须靠「码属于哪个命名空间」来消歧。

### Neutral

- 退出码表同时登记在 `AGENTS.md`、`exit-guard.mjs:3-9`、`docs/troubleshooting.md §8` 三处——**由规则 ⑧b 的机械对账约束**，不构成「同一事实两处维护」的风险。

## Alternatives considered

- **全部用 `0/1/2`（通用惯例）** — 驳回。理由：只有一个失败维度，**无法区分「内容失败」与「用法错」**——这正是事故 1 的成因；且 `1` 已被 M 门占用为 P1，无位可分。
- **交接门复用 M 门 `1/2/3`** — 驳回。理由：语义完全不同（产物缺失 vs 内容 P1）；实测已发生过「`exit 10` 被读成 P1」的误判，复用即重演。
- **用 `stderr` 文本区分而非退出码** — 驳回。理由：**脚本的消费者读码不读文本**——CI 分支、主控状态机、子代理判断都基于码。
- **每个脚本自定义码** — 驳回。理由：跨脚本无法对账；规则 ⑧b 的「三方一致」正是为防这种散乱。
- **统一码 + 结构化 JSON 输出**（把语义放进 stdout JSON） — 部分采纳但**不足以替代**：本包确有 JSON 输出（如 `M-Gate-Report.json`），但**失败时脚本可能连 JSON 都写不出来**（路径错、脚本缺陷），此时**码是唯一还活着的信道**。

## Contract for consumers

- 新增脚本时先问：**我做内容判定吗？** 不做 → 你的「用法/参数错」**必须**是 `10`，**不得**用 `1`。
- 申请新码须在 `§8 配额` 与契约表**两处**登记（规则 ⑧b 会核三方一致）。
- **不得**让两个命名空间共用同一个数，即使「语义相近」。
- 若要推翻，开新 ADR 并标 `Supersedes: ADR-0003`。
