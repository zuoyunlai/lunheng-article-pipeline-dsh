## 〇、为什么另立一份，而不并进「刻意设计不变量」

`decision-2026-10-04-刻意设计不变量.md` 记的是**「别改坏这些机制」**（对象 = 机制的设计）。
**本记录记的是「改之前先查这几件事」**（对象 = **改动者的动作**）。

两者体例相同（`decision-*.md` 六字段头）、住所相同（`audits/decisions/`），**但回答的问题不同**——混在一份里会让「改动前该做什么」淹没在机制说明中。

> **判据**：**「知道什么不该改」与「知道改之前该查什么」是两件事。** 前者是知识，后者是流程；**知识不会在你要动手的那一刻自动出现，流程才会。**

## 二、前置检查清单（**改动机制文件前逐项过**）

> **用法**：不是"记住"，是**在动手前把下面几项各跑一条命令**。本批实证：**执行了清单的那两轮（21/22）首跑即绿；没执行的那几轮全部被门抓。**

### A. 若**新建文件** → 查路径登记面

```sh
# 新文件里有没有本机绝对路径？有则必须在 LOCAL_PATH_BASELINE 登记（并写明理由）
grep -nE '[A-Za-z]:\\\\|/Users/|/home/' <新文件>
```
**实证**：第 7 轮。**主动规避的例子**：第 20 轮新建 `decision-*.md` 时**刻意 0 处绝对路径**，未触发。

### B. 若**改动已有文档的行数** → 查行号断言

```sh
# 有没有测试或文档断言该文件的行号？
grep -rn "<文件名>:[0-9]" tests/ skills/
```
**实证**：第 11 / 15 轮**同一道门撞了两次**。第二次（第 15 轮）我在记录里写了判据**仍未执行**；
第 21 / 22 轮**执行了**（改前先量、改中同步）→ **首跑即绿**。

### C. 若**改 `scripts/` 的能力面**（新增写盘 / 子进程 / mkdir）→ 查 `SECURITY.md` 的执行面声明

```sh
grep -n "写内容\|子进程\|只读" SECURITY.md      # ⑧c 会双向对账
node scripts/repo-hygiene-check.mjs
```
**实证**：第 12 轮（给 `count-chars.mjs` 加 `--report`）。

### D. 若**增补任何 ≥12 KB 的 .md** → 查**两件事**（不同）

| 问题 | 看什么 |
|---|---|
| ① **它在不在棘轮表内？** | 现状 |
| ② **本次增补会不会把它推过 12 KB？** | **增量** |

**实证**：第 23 轮。我**只查了 ①**（答：不在表内）就动手，**②** 使文件从 11,483 → 12,677 B **跨线** → 门红。
> **判据**：**这两个问题是独立的——① 看现状，② 看增量。** 只查 ① 会漏掉"把一个下线文件推上线"这一整类。

### E. 若**增补任何已在棘轮表内的 .md** → 同批抬上限并写明理由

```sh
grep -n "<文件名>':" scripts/repo-hygiene-check.mjs    # 取上限与理由字段
```
**公式（定案 ①）**：`新上限 = 实测 + 1.5 KB，向上取整到整 KB`。
**实证**：第 15（F-16）/ 21（F-22）/ 23（F-5 首次登记）轮。

### F. 若**用 pwsh 写回文本** → **停下来，改用 `edit` 工具**

- **实证 1（第 16 轮）**：`-replace` 的替换串写了 `\`n`（pwsh 应为 `` `n ``）→ **转义符当字面量写进文件**。
- **实证 2（第 17 轮）**：`Set-Content -Encoding utf8` → **注入 UTF-8 BOM** → `consistency-check` P1。
> **判据**：**`edit` 管写，pwsh 管跑。** pwsh 写文本满是隐式转换（编码 / BOM / 转义 / 换行）。

### G. 若在**块注释 / HTML 注释 / 任何"用标记包裹"的结构里举例** → **不得写出其终止标记**

| 结构 | 终止符 | 正确写法 |
|---|---|---|
| JS 块注释 `/* … */` | `*/` | 例子里写 `run/<项目>/…`，**不写** `run/*/…` |
| HTML 注释 `<!-- … -->` | `-->` | 例子里写 `<!-- -- >` |
| 尖括号占位符 `<…>` | `>` | 说明文字**先剥行内代码**再判定 |

**实证**：**同一结构 3 次** —— F-3（`-->` 写在 HTML 注释里，状态机提前结束）／F-11（`<…>` 写在被检文本里，占位符检查误伤）／第 27 轮（`*/` 写在块注释里，**语法错误、脚本不可加载**）。
> **判据**：**凡「用标记包裹一段内容」的结构，绝不能在内容里写出它的终止标记——哪怕只是举例。举例时必须破坏该序列。**
> **⚠️ 诚实边界**：这条**我三次都没做到**，尽管每次都在记录里写了判据。原因已定位：**写注释时我不觉得自己在"处理标记结构"**，判据没被唤起。
> **故本条必须留在清单里、且在 A–G 中排位靠后（它最容易被人认为"这次不适用"）。**

## 二·补、**收尾**检查清单（改动**做完之后**过——与 A–H 的"动手前"相对）

> **为什么另分一组**：A–H 防的是"动手时踩到门"；下面两项防的是"**做完了，但记录与事实不符**"。本批实证：**后者每查一次就查出一处**（第 18 轮 2 处、第 31 轮 5 处）。

### I. 改完后**回填修订记录的改动清单**，并**逐条对账 `git status`**

```sh
# 实际改了什么
git status --porcelain
# 记录里列了什么（把 <记录> 换成你的修订记录路径）
grep -n '^| `' <记录>
```
**两条都要做**：① **回填**（新增/删除文件时易漏）；② **对账**（旧的说明行会陈旧，如"909→913"实际已到 919）。
**本批实证**：
- 第 18 轮：待办队列里的陈旧行（F-23/F-24 已处置仍标"未做"）+ 我修改时**新增的重复行**。
- 第 31 轮：清单表 **13 行 vs 实际 17 个改动文件**（漏 4 行）；且 `batch15-qlt5-docs.test.mjs` 那行的说明**停留在 909→913**（实际已同步到 919）。
- **共同根因**：「**边做边加**」的记录，正确性只能靠「**回头逐条对账**」——**而这一步没有任何门强制。**
> **⚠️ 为什么不把它做成仓库测试**（如实记录这个判断）：该断言是「记录清单 = `git status`」，而 `git status` 是**瞬时状态**——**在已提交状态下，一份描述过去某次提交的记录不可能与当前 `git status` 相符**。做成测试会**恒红或恒空转**。**故它只能留在工作纪律里，靠人执行。**
> **判据**：**不是所有"能被发现的不一致"都该做成门。** 先问「这个断言在任何**稳态**下成立吗」——不成立则它是**流程**，不是**门**。

### J. 声明「本批改动已完成」之前，跑**收口动作**

```sh
node scripts/closeout-verify.mjs        # 差集 + 反向核验（仓库级，不随包）
node scripts/no-write-check.mjs         # 工具链不得改写仓库
```
- **边界如实**：`closeout-verify` **只报「需人工回核」，不判「已完成」**（差集只能证明"被记录"）；`no-write-check` 的 `exit 1` 可能是「**被别的红带下去**」而非「有改写」——**要看每一步的「改写」列，而不是只看 exit**（本批第 26 轮实证：全步骤 `改写 0`，红因是 `node --test` 的 exit 1，而那个 1 来自既有的 F-25）。

### K. **「边做边加」的记录会在同一处反复堆叠 → 必须定期「整段重写」，而不是逐段补**

**本批实证（同类错 5 次，全部出在我自己的修订记录里）**：

| 轮 | 查出的问题 |
|---|---|
| 18 | 待办队列的**陈旧行**（F-23/F-24 已处置仍标"未做"）+ 我修改时**新增的重复行** |
| 31 | 改动清单**少 4 行**（13 行 vs 实际 17 个文件） |
| 34 | 改动清单**少 1 行**（上一轮刚加的文件） |
| 36 | 统计**虚增 1**（把派生条目 F-1b 当报告条目）+ **混入 1**（把非报告条目的 F-25 列成"24 条之一"）+ **三行重复** + **一段第 12 轮写的陈旧注**（原文「未做的 9 条」，此后逐条推进至 0 条，那段话没跟着改） |

**共同规律**：

> **「边做边加」的记录，会在"同一处"反复堆叠 —— 因为每次我改的是"当前那一段"，而旧段仍留在文件里。**

**判据与动作**：

1. **修订记录不是"追加日志"，是"当前状态的快照"。** 追加式写法在**短批次**里没问题；**一旦超过 ~5 轮**，同一处就会堆叠出陈旧段与重复段。
2. **定期整段重写**：对「结语 / 统计 / 清单 / 待办队列」这四类**状态型段落**，**每推进若干轮就整段重写一遍**，而不是继续往里补。**本批的 36 轮记录就是反例**——它的 §三 结语被改过 6 次，每次只改"当前那一段"。
3. **对账动作**（与 I 项配合）：重写后跑
   ```sh
   # 陈旧字样扫描：搜索那些"随进度变化"的词
   grep -nE '未做|待办|剩余|共 [0-9]+ 条|已落地 [0-9]+' <记录>
   ```
   **本批实测**：「未做的 9 条」这段**从第 12 轮一直留到第 36 轮**，其间那 9 条**已全部推进完毕**（只剩 1 条需专批）——**而它没有一次自查发现，是第 36 轮顺手对账才翻出来的。**
4. **为什么没有门能代劳**（与 I 项同一判断）：这类断言依赖**记录与当时的真实进度**，而进度是瞬时的 → **它是流程，不是门。**

## 三、一条比清单更重要的判据（来自第 28 轮的失败）

**第 28 轮**（F-13）：我核前提 → 实现 → **六例自测全绿** → **全量回归红**。

**差别只在**：

> **自测用的是我自己理解的语义；回归用的是机制声明的语义。**
> **两者冲突时，后者为准——直到你能证明后者写错了。**

**故另有一条独立动作**：

### H. 若**要"修一个假阳性"/ 放宽一条判据** → **先查有没有测试在守那个行为；若在守，先读它写的理由**

```sh
grep -rn "<相关标识符>" tests/
```
- **反例（第 28 轮 F-13）**：没先查 → 实现完才发现 `tests/g-audit-check.test.mjs:275` **明确断言**「档位下限 5000 与目标 16000 **都进候选**（判据是『落在候选区间内』，故 **5000–16000 之间都算合规**）」→ **我"修"的正是它的意图** → 按纪律回滚。
- **正例（第 29 轮 F-14）**：**先查** → 发现 `g-audit-check.test.mjs:349/398/399` **密集守卫**「专著双写契约」且写明真实事故根因 → **直接驳回，未动手**。**省掉一次完整的实现-回滚循环。**
> **判据**：**「比标准严」不等于「过严」** —— 先问这条严要求**服务的目标**是什么，再判断严是否失当。
