# ADR-0002 — 覆盖写盘一律走 `writeWithSafety`：同目录 `temp + rename` 原子写 + 带时间戳、有界回收的回滚点

> **状态为「回填」**：本决策由 v2.2.x–v18.14.0 期间多次事故**逐层叠加**而成，当时未以 ADR 形式登记。本件于 2026-09-29 按证据回填。

- **Status**：`Accepted（回填，2026-09-29 登记）`
- **Date**：2026-09-29（登记日；各层决策的实际日期见 Context 内的版本标注）
- **Version**：v18.14.0（最后一层：`pruneBackups` 排序修复）
- **Supersedes**：`writeFileSync(目标, 内容)` 直接覆写；固定名 `<原名>.bak`；`pruneBackups` 以文件名时间戳为主键
- **Evidence**：`scripts/_lib/destructive-write.mjs:26`（导入 `renameSync`）／`:91`（时间戳 `.bak` 命名）／`:98-101`（`mtime` 主键及理由）／`:102`（`BAK_MAX = 20`）／`:120-125`（v18.13.0 确定性 tiebreak）／`:158`（v18.2.9/B4 改 temp+rename 及 Windows 语义）／`:180`（`renameSync` 调用点）

## Context

**事故链（四层，逐层暴露前一层没覆盖的东西）**：

1. **静默覆盖输入正文且不留回滚点**（第三方审计 **B-4**）：`apply-diff.mjs` 旧版默认原地覆盖、无 `.bak`。→ **确认「要覆盖」这件事不能靠记忆**，必须由机制落一份带回滚点的副本。
2. **回滚点无上限累积**（v18.3.1 / B4）：每次覆盖新增一个时间戳 `.bak`，一轮多条目修订对同一文件写多次 → 实测某项目 `final/` 下数十个 `.bak` 污染。→ **加 `BAK_MAX = 20` 回收**。
3. **半写损坏**（v18.2.9 / B4）：`writeFileSync(p, …)` 直接覆写，进程在写入中途被杀（超时 kill / 断电 / Ctrl-C）会留下**半写损坏**的目标文件。→ **改 `temp + rename`**：同目录、同卷上 `rename` 原子（Windows 走 `MoveFileEx REPLACE_EXISTING`），要么旧文件完好、要么新文件完整。
4. **回收把最新回滚点删掉**（v18.13.0 补 tiebreak → **v18.14.0 修 CI flaky**）：`pruneBackups` 只按 `mtimeMs` 排序时，**同一毫秒内多次写盘**会让比较器恒返回 0、顺序退化为 `readdir` 实现顺序 → **把刚写的回滚点当最旧删掉**（CI `windows-latest` 上 v10 被误回收）。

**根因（四层的共同形态）**：每一层都在「**写盘是一个不可逆动作**」这一前提上做不完备的近似——**不做备份**、**备份无限**、**写入非原子**、**回收判据不稳**。
另一处**必须记住的坑**：**不能用文件名时间戳做主键**——`<path>.<秒级时间戳>.bak` 的「无序号 = 最旧」假设会在**回收后**被同秒内的下一次写盘复用（第 99、121 行已论证），跨秒比较失真，实测自然场景直接错。

## Decision

**所有覆盖写盘一律走 `writeWithSafety(out, text, { inPlace, source })`**，其语义为四件同时成立：

1. **同文件守卫**（可选，给出 `source` 时生效）：拒绝把文件写成它自己（归一化 + `realpathSync` 解析；不归一 / 不解析就归零）。
2. **覆盖前自动备份**：`<原路径>.<YYYYMMDD-HHmmss>.bak`（**同秒重复调用加 `-1`/`-2` 序号**）——**用时间戳而非固定名**，因为一轮修订里同一文件可能被写多次，固定名会把上一次的回滚点抹掉。
3. **有界回收**：每个原文件最多保留 `BAK_MAX = 20` 个回滚点，超出删最旧。**排序主键 = `mtimeMs`**，并配**确定性 tiebreak**（`mtime → 同秒序号(-n) → 文件名`），使同一 `mtime` 集合的顺序唯一。
4. **原子写入**：`temp + rename`（同目录同卷；`rename` 失败带退避重试）。

## Regression-proof anchor

1. **行为测**：`tests/scripts.test.mjs`（`destructive-write` 相关 9 处）+ `tests/script-surface.test.mjs`（3 处）——覆盖备份生成、上限回收、原子写路径。
2. **源码钉**：**`tests/adr-anchors.test.mjs`（2026-09-29 补实装）**，三组断言：
   - `writeWithSafety` 必须含 `writeFileSync(tmp,` 与 `renameWithRetry(tmp, p)`，且**不得**含 `writeFileSync(p, …)`
   - `renameWithRetry` 必须**白名单式**识别 `EPERM`/`EACCES`/`EBUSY`，且**不得**在重试逻辑里特判 `EXDEV`/`ENOSPC`（防「把真问题掩盖成重试成功」）
   - `pruneBackups` 比较器必须为**三段式**（`mtime` 主键 + `seqOf` 序号 + 文件名兜底）
   > **负向对照已做（2026-09-29）**：把源文件副本分别篡改为「直接覆写目标」与「去掉 tiebreak」，对应断言**均变红** → 断言具备**区分力**，不是恒真的空断言。

## Consequences

### Positive

- 覆盖写盘**可回滚**（时间戳回滚点）、**不会半写损坏**（原子 rename）、**备份有界**（不污染项目目录）。
- 回收判据在同毫秒并发下**确定性**——CI `windows-latest` 不再 flaky。

### Negative

- **【明确认赔】** `.bak` 会真实留在项目树里（最多 20 个/文件），交付目录不「干净」。我们接受——**回滚点的价值高于目录整洁**，且已用上限约束其规模。
- `rename` **只在同目录同卷上原子**；若某调用方把 `temp` 放到别的卷（如 `%TEMP%`），原子性不成立。当前实现靠「同目录」保证，**但这不是断言出来的**（见 Regression-proof anchor 第 2 条的源码钉缺口）。
- 备份是 `copyFileSync`（非 reflink/hardlink）→ 大文件覆盖写有 I/O 开销。

### Neutral

- 增加了约 15.6 KB 的 `_lib/destructive-write.mjs` 与一个必读的 `BAK_MAX` 常量。

## Alternatives considered

- **不做备份，只做原子写** — 驳回。理由：原子写只保证「要么旧要么新」，**不保证能回到旧**；B-4 的事故（静默覆盖、无 `.bak`）正是缺回滚点。
- **固定名 `<原名>.bak`** — 驳回。理由：一轮内同一文件多次写会**抹掉上一次的回滚点**（第 93-94 行已论证）。
- **`pruneBackups` 用文件名时间戳作主键** — 驳回。理由：**同秒内备份名会被复用**，「无序号 = 最旧」在回收后失效；实测自然场景直接错（内存/CI 双证）。
- **`pruneBackups` 只按 `mtimeMs` 排序（不做 tiebreak）** — 驳回。理由：同毫秒下比较器恒为 0 → 顺序退化为 `readdir` 实现顺序 → **刚写的回滚点被当最旧删掉**（CI 实测）。

## Contract for consumers

- **不得**在新增脚本里用裸 `writeFileSync(目标, 内容)` 覆写既有文件——一律走 `writeWithSafety`。
- **不得**改 `pruneBackups` 的排序主键；若要改，先读懂「名字为什么会被复用」（第 91-101、120-125 行）。
- 本决策的源码钉**已实装**（`tests/adr-anchors.test.mjs`）——**该文件是 ADR-0002 的可执行部分**，改动 `destructive-write.mjs` 的写入路径或回收比较器时它应当拦下你。
