## 二、逐条处置（含「为什么是这个改法」）

### P1-1 面板「在等主人」从第一分钟就亮着

- **核实**：用 `status-template.md` 原样建一个空项目，按**旧判据**逐行跑，实测命中 **32 行**——`⬜ Inbox`、裸 `待`、`人在环` 全是**阶段类型**字面，不是「此刻正在等人」。
- **改法**：`lib/panel.mjs:parseOwnerWait` 只认两类证据：① 显式祈使/等待字面（`待主人` / `等主人` / `请主人确认|决定|过目|回复|拍板|裁定` / `待你` / `等你` / `🔄`）；② **活动门那一行**（表内阶段号最小且状态列无 ✅）的 `Inbox|⬜` + `主人|人在环`。
- **两次自我修正**（都写进了代码注释）：
  1. 第一版按「表里第一条未闭合行」取活动门——但模板有**两张表**（角色表在前、阶段表在后），于是 Phase 2.5 被当成活动门。改为取**最小阶段号**。
  2. 第一版的正则把模板 §方法足迹「无需主人手动维护」判成等待语义（`需主人` 前缀匹配）。补 `(?<![无不要])` 否定前缀护栏。
- **结果**：模板原样 → `waiting:false, hits:0`；真实待主人（Phase 0 已闭合、2.5 行 Inbox + 主人）→ 仍正确点亮。**新增反面回归**钉住「模板零命中」。
- **保留的诚实边界**：这仍是字面投影，不解析语义；自由散文写的 `status.md` 可能判不出（宁可漏报，不猜）。

### P1-2 收件箱把「正等主人验货」判成「已交付·不阻塞」

- **核实**：旧 `delivered` 判据只看 `final/定稿.md` 是否存在。而 Phase 5 **门-B 本身就发生在定稿落盘之后**——「定稿写完、终检确认单 §6 没回填」正是最该让主人点一下的状态，却被静默归入「历史、不阻塞」。
- **改法**：`pending-cli.mjs` 改为「定稿在盘 **∧** Phase 5 闸门状态 = ok」。测试夹具从两态扩为三态：真已交付（Phase5 §6 已回填）/ **定稿在盘但 §6 未回填** / 未交付，并断言中间态**必须**留在收件箱。
- **顺带发现**：`readdir` 顺序不等于字典序，夹具断言必须 `.sort()`，否则同一逻辑换台机器就红（已修）。

### P1-4 `-rollback` 返回成功，但全仓没有回滚实现

- **核实**：grep 全仓无 checkpoint 实现、无回退脚本；旧路由只校验 `--confirm` 就返回 `{ok:true, action:'rollback'}`。
- **为什么不能「随便补一个实现」**：真回退要动 `drafts/`、`final/`、`status.md` 与账本的状态一致性，属机制面；在无 checkpoint 的前提下强行实现，风险高于收益。
- **改法**：改为**显式拒绝 + 三条真实路径**（版本号只增不降的正文回退 / git 或自建备份的文件级回退 / 重跑阶段角色且不删产物）。测试同步改判：`-rollback` 无论带不带 `--confirm` 一律 exit 1 且 stderr 说明未实现。

### P2-1 「退回书面路径」全库无一处说做什么

- **核实**：三处（`主人确认-template.md`、`00-主控-扩展职责.md`、`SKILL.md`）都写「工具失败 ≠ 同意，退回书面路径」，但**没有一处定义动作**；叠加「不设超时、同一门只问一次」⇒ `NO_PROVIDER` 场景下流水线无限等待，而主人恰恰因为 UI 不可用收不到通知。
- **改法**：定义四步 —— ① 确认单照写落盘并在 §6 记失败码；② `进展-主人版.md` 记一行「请回复」；③ 主人可自然语言回复，也可直接改 §1 勾选；④ 主控逐字回填 §6。并规定「每推进新阶段前重写一次等待行」，该状态同时进 `-status --pending` 收件箱。

### P2-3 降级「先发生、告知在后」

- **核实**：`06-批判-critical-companion.md` 旧文顺序确为降级先行；`SKILL.md` 只说「显式告知」不定义是否等答复。
- **改法**：五步动作序（发现 → **先请示**（有 UI 用 `ask_user_question`，无 UI 走 §7 书面路径）→ 主人同意 → 才按新档 spawn → 进展页与交付说明记 `降级：A→B｜原因｜主人答复`）。关键补丁是一句话：**未获答复前，顶配角色不得以低档冒充顶配执行**。Phase 0 §0-d 的预授权降级仍可免除询问。

## 四、本批暴露的新问题（比修掉的问题更值得记）

1. **「门数正确」不等于「门在管对的事」**：`content-rules.mjs` 的 M 门项数对账一直拿 `MECH` 比，于是**正确的修订被判漂移、真正的错被放行**。这是「门自己成为缺陷来源」的形态——门必须能表达「除被省略的那一道之外」。
2. **CHANGELOG 验证行是自指陷阱**：`tests/docs-facts.test.mjs` 会拿「最新段声明的 N/N」与静态用例数对账，而修它本身又要改这一段——必须先跑完全量拿到真值再回填，否则永远差一轮。本批的实际做法：先跑到「唯一失败项 = 这条门本身」，再回填，最后复跑为 0 fail。
3. **`edit` 前必须先 `read`**：fs-observation-policy 会拦「未读即改」，把文件内容猜出来改会整批失败。同理，**批量 `sed -i` 对中文/正则边界不可控**——本批全程精确 `edit`。
4. **审计编号本身会漂**：我在 `run-report` 注释里把「同名字段两义」误标成「审计 P1-3」，而该报告 P1-3 实为「账本落地率」。已全部改为「口径批 · 同名字段两义」——**引用别人的编号时，编号也是派生面**。
5. **模板预算余量与语义正确性会打架**：为压预算把「四个完整文件名」缩写成一个斜杠串，立刻触发两条门（链接检查把它当路径、`phase-registry.test.mjs` R5 要求逐字四个名）。已回退为四个完整名，改从别处（历史括注）省字节。
