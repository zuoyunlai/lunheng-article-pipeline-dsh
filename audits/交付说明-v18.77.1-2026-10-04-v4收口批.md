## 二、根因（v4 硬约束）

DSH 升级到会话格式 v4 后，**每条持久化消息的 `source.kind` 必须是"生产者自有的"非空字符串**，且**泛用 `'plugin'` 这个 kind 已被退役**。本插件 H2 监听器向 `tools/post-execute` 的 `additionalContexts` 通道注入标记消息时仍使用旧版包装 `{kind:'plugin', plugin:'lunheng-article-pipeline'}`，被 v4 校验直接拒掉、整轮运行失败并中断会话写入。

报错字面（主人运行提示原话）：

```
format v4 message requires a producer-owned source kind
```

**关键事实**：
- v4 校验**对每个生产者插件独立成立**——本插件的写法错误**不**等于其它插件错；任何注入消息的 `source.kind` 都得过这道关。
- 选纯生产者名 `kind:'lunheng-article-pipeline'` 而非 `kind:'plugin:lunheng-article-pipeline'` 命名空间前缀——理由：(a) 报错明说"producer-owned"，前缀是建议而非硬要求；(b) 该消息只在 additionalContexts 路径上由本插件自己生成、消费方不归并跨插件，纯名更直白；(c) 若未来要跨插件归并，再补 `kind:'plugin:…'` 风格，向后兼容（消费者解析 `kind` 字符串时按字面比对，纯名也是合法生产者自有名）。

## 四、是否需要放宽 `@deepseek-ai/dsh` 的 peer 区间？

`package.json:71` 当前是 `"@deepseek-ai/dsh": ">=0.1.2-rc.1 <0.2.0"`（严格锁在 <0.2.0）。**本批不放宽**，理由：

1. v4 报错**只有主人开发环境**（自装 0.2.x）会撞；DSH 市场副本仍走 0.1.x，**不会撞**。
2. 0.1.x 宿主加载器对 `source.kind:'lunheng-article-pipeline'` **无副作用**——消费者按字面比对 `kind`，纯生产者名是合法生产者自有名（仅"非默认字面"被丢弃解析，而非视为非法）。
3. 放宽 peer 到 `<0.3.0` 会引入 0.2.x 的其它潜在破坏性变更，**单点补丁不足以兜底**。
4. 主人指令本意是「救自己的报错」，不需要为 0.2.x 整体兼容性背书。

如未来主人决定官方支持 0.2.x，**另起一批**：同步放宽 peer + 跑 host-contract-probe 适配 + 补 v18.66.0+ 累积的接口债单（写应用层权限、模型分档面板等）。
