## §零、结论摘要

context-mode 是一个**做对了「上下文预算」这件事的工程样本**：它把「AI agent 每次工具调用都可能一次倒进 56 KB」这个问题，用**拦截层 + 索引层 + 记忆层**三层机制治住，并且（罕见地）**用 ADR 与 benchmark 把每条机制的理由、代价、反悔锚点都留了痕**。

**总判定：值得借鉴的不是它的机制（论衡大半已有或宿主已提供），而是它的「决策留痕形态」与「分层纪律」。**

| 类别 | 项数 | 一句话 |
|---|---|---|
| **采纳**（真缺口，本地无对应物） | 4 | 决策记录（ADR）形态 / 捕获层·收窄层分层纪律 + 反向门 / **计量口径变更固定动作** / 双重计费反模式条目 |
| **采纳-改写**（有想法但形态不合本地架构） | 5 | 阈值显式化 / 一次调用问全部 / 检索式批量纪律 / 昂贵验证护栏 / 反模式文档形态（待核） |
| **驳回** | 7 | 多宿主适配 / MCP 常驻 server / FTS5-SQLite 原生依赖 / 零 exec 哲学 / 跨会话用户画像 / 对外宣称省 token 百分比 / **拦截层** |
| **本地已做对（严禁照抄改进）** | 7 | 退出码体系 / guard 拒绝文案 / 打回任务书 / **写盘安全网（比它强）** / 单一真源纪律 / 上下文协议层 / 残余缺口如实声明 |

**最高性价比三项**（详见 §三）：

1. **A3 计量口径变更固定动作**——**≈1 小时，零机检风险，纯止血**。论衡 v18.22.0 已实测踩中同类坑（§2.3「成本口径纠正」为本报告最重要的单条发现；MEA 族即为此而立），但**没有把「改口径要贴前后复算表」固化成规则**；context-mode 的 ADR-0004 恰好把这件事做到了教科书级。
2. **A4 双重计费反模式条目**——**≈10 分钟**。context-mode 最核心的反模式是「已在上下文的数据再送一次 = 2× 计费」（Playwright 快照 135K → 270K tokens，`skills/context-mode/references/anti-patterns.md:290-291`）。论衡的对应风险点是**主控三播报把子代理原文再贴一遍**——交接报告本身已是摘要（做对了），缺的只是这条显式条目。
3. **A1 决策记录（ADR）形态**——**≈1.5 天，但直击本地最顽固的复发症**。论衡「已修只覆盖当时盯住的那一处」在 2026-09-26 一天内复发 **6 次**（C-2/C-3/C-5/C-7/E-8/E-14）。根因不是疏忽：**修订记录按批次组织，而批次是时间线、不是决策单元**。同一决策在后续批次被再次触碰时，没有任何单一位置写着「这条为什么这样定、试过什么不行」。

**v1 追加（§九 专项复核产出）**：原报告未列的第 5 项采纳动议——**EXEC 族（执行边界与口径收口，4 项）**。它不是「借鉴 context-mode」，而是**由本次复核在论衡自身查出的活体矛盾**：`sha256 回填口径` 在三份文档里给出两个互斥答案、且 `M-Gate-Algorithm.md:825-833` 内部自相矛盾（详见 §九.4）。该项**优先级最高**——它是一条正在生效的、会导致不同执行者写出不同交付件的口径冲突，成本 ≈ 半天。

## §一、context-mode 解剖：它到底在治什么

### 1.1 三层机制

| 层 | 载体 | 职责 | 关键实现 |
|---|---|---|---|
| **拦截层** | hooks（`hooks/pretooluse.mjs` 等 45 个脚本）+ MCP server | 在工具结果返回前改写：改道、外置、封顶 | `src/server.ts:1923-1935`、`hooks/core/routing.mjs`（45,621 B） |
| **索引层** | FTS5（better-sqlite3） | 大输出外置 + BM25 检索回读 | `src/store.ts:475-497`（porter + trigram 双表）、`store.ts:592`（bm25 title 权重 5×） |
| **记忆层** | SessionDB（SQLite WAL） | 会话事件结构化抽取 + 跨压缩快照 | `src/session/extract.ts`（26 类）、`src/session/snapshot.ts:472-513` |

### 1.2 「98% 上下文削减」的工程动作拆解

| # | 机制 | 触发条件 | 产物形态 | 代码位置 |
|---|---|---|---|---|
| M1 | 沙箱执行 + **只回 stdout** | 分析/统计/解析类任务改写为代码 | 仅 stdout（+源码回显供审计） | `src/executor.ts:282-319`；回显上限 `CODE_ECHO_MAX=2000` `server.ts:1511` |
| M2 | **大输出外置 + 指针回传** | stdout > **100 KB**（错误路径同阈值） | `Indexed N sections (M with code) from: <label>` + 检索指引 | 常量 `server.ts:1980`（`102_400`）；守卫 `server.ts:1923-1935`、`2202-2213` |
| M3 | 意图检索（更低一档） | 传了 `intent` 且输出 > **5 KB** | 命中标题 + 首行前 120 字符 + 可检索词 | `server.ts:1979`（`5_000`）、`1982-2030` |
| M4 | **批量合并**（N 命令 → 一次调用） | 3+ 条相关命令 | `## Commands` + `## Indexed Sections`（标题+KB）+ 各 query 命中片段 | `server.ts:3679-3776`、`3831`、`3863-3879` |
| M5 | 检索结果**窗口截取** + 重叠合并 | 命中片段 > 1500 字符 | 命中点 ±300 字符窗口，重叠合并后拼接 | `server.ts:1300-1367`（`WINDOW=300` @1341） |
| M6 | 响应总量封顶 | search > 40 KB / batch > 80 KB | 超限退化为一行 "use ctx_search(...)" | `server.ts:2672`、`1375`、`1388-1391` |
| M7 | **四层检索兜底**（敢削减的前提） | 每次检索 | porter → trigram → 模糊 → LIKE | `store.ts:1340` 起 |
| M8 | 空索引即引导（失败安全） | store 无 chunk | 直接告知先用 indexing 工具 | `server.ts:2597-2613` |
| M9 | 沙箱流级硬闸 | stdout+stderr 合计超限 | 杀进程 + stderr 附注 | `executor.ts:251`（100 MB）、`510-547` |

**切片口径**：`MAX_CHUNK_BYTES = 4096`（`store.ts:153`）；markdown 按标题切、超限再按空行/段落二次切（`store.ts:1646-1762`）；标题取首行前 `CHUNK_TITLE_MAX_CHARS = 80`（`165`）。
**回读接口**：`ctx_search(queries[], source, limit=3, contentType, sort)`，默认 limit 3（`src/search/ctx-search-schema.ts:90-94`）。

**flood-guard** 防的是「单个 agent 用几十次独立检索代替一次批量检索」（`src/search/flood-guard.ts:4-8`）：按 sessionId 分桶滚动窗口计数，超 `softCapAfter=3` → 每查询只回 1 条；超 `blockAfter=8` → 直接拒绝并强制改走批量（`server.ts:2457-2459`、`2651-2670`，窗口 60,000 ms）。

### 1.3 ⭐ 它自己承认的能力上限（本报告最重要的一条外部事实）

`README.md:1403-1424`：**有 hooks 的平台 "~98% saved"，无 hooks 的平台 "~60% saved"**；`README.md:1426` 给出原因——一条未改道的 curl / Playwright 快照可一次倒进 56 KB。

> **判据**：98% 是「**拦截层 + 约定**」的联合产物，**不可替代的是拦截层**；纯 prompt/skill 项目的上限约 **60%，且依赖模型服从**。

**这条事实直接决定了本报告 §四的可行性判定**：论衡没有拦截层，也不该为了这 38 个百分点去做拦截层（见 C7）。

### 1.4 它最独特的资产：四份 ADR

`docs/adr/` 下四份架构决策记录，形态统一且**含反悔锚点**——这是本报告认为**最值得借鉴的东西**（见 A1）：

| ADR | 主题 | 最值得学的一点 |
|---|---|---|
| 0001 | SessionDB 多写者安全 | **先重析根因，发现原方案在解决一个已不存在的问题，于是整体回滚**（删 185 行 `db-lock.ts`）；含「回归锚点」**成对测试**：行为测 + **源码钉**（正则断言源文件里不得出现某标识符） |
| 0002 | 工具描述的语气与结构 | **层区分**：选择线索用 `WHEN / WHEN NOT`，祈使语只许留在系统提示注入层；禁词表（`MANDATORY:` / `BLOCKED` / `Do NOT` / `PREFER X OVER Y` / ✅❌）；**38 次 A/B × 6 探针**实证；并**承认反例**——重框架对 `ctx_purge` 反而**提高**参数保真（5/5 vs 3/5），故**必须探针门控、不可一刀切** |
| 0003 | 改道拒绝理由：redirect ≠ restriction | `blocked` 一词被 Opus 4.6 读成安全限制 → agent 向训练数据投降（6/6 → 0/6）；**裸否定式反而勾起它想否认的框架**（`NOT a network restriction` 让投降率从 0/6 回到 2/6）；**CASE A 改道** vs **CASE B 真限制**两套措辞规范 |
| 0004 | 统计用「严格压缩」口径 | 一个「修显示 bug」的补丁把 `eventDataBytes` 放进比例**两边**，把 95.4% 显示成 56%；**口径变更本身写成一页**，含 **fix 前/后三列对照表** + 明说哪些数字会跳变/不变；**空状态显式**——无数据不画退化柱（不出 0%/100% 假数），只给一行诚实提示 |

## §三、采纳清单（含落地位置与成本）

### A 档 — 采纳（真缺口）

#### A1 【P1｜`[文档]`】决策记录（ADR）形态：一决策一页

- **来源**：`docs/adr/0001-0004`（尤其 0001 的「根因重析 + 回归锚点成对测试」）。
- **为什么是本地最实的缺口**：本地「已修只覆盖当时盯住的那一处」在 2026-09-26 一天内复发 **6 次**（C-2/C-3/C-5/C-7/E-8/E-14）。根因不是疏忽，而是**修订记录的组织单元是「批次」（时间线），不是「决策」**——`机制文件修订记录-<日期>-*.md` 与 `反哺报告-vX.md` 都是批次件；同一决策在后续批次被再次触碰时，没有任何单一位置承载「为什么这样定 / 试过什么不行 / 代价是什么」。
- **可借的四件事**：
  1. **固定字段**：Status / Date / Supersedes / Context（**含根因重析**）/ Decision / **Regression-proof anchor** / Consequences（Positive / Negative / **Neutral**）/ Alternatives considered（**逐条驳回理由**）/ Contract for consumers。
  2. **回归锚点 = 成对测试**：① 行为测（真跑，断言行为）② **源码钉**（正则断言源文件里**不得出现**某标识符）。后者对论衡尤其对口——本地门大量是**字面扫描**类，源码钉正是它们的「反向断言」形态。
  3. **代价三分且必须写 Negative**：本地已有「如实登记的保留代价」（`机制文件修订记录-*` 的 L-16 类），但**没有强制结构**；ADR-0001 的 `### Negative` 段（「未来的同类 bug 将不再由 lockfile 错误信息诊断，而是 30 秒 busy_timeout 后的 `SQLITE_BUSY`——我们接受」）正是本地点评缺失的那种**明确认赔**。
  4. **「替代方案 + 驳回理由」是防复发的主力**：本地 `借鉴评估-v1` 报告已有 C 档驳回表（文化已具备），但那是**批次件**；ADR 把它挂到**决策**上。
- **落地位置**（**关键判据**）：
  - ⚠️ **必须放仓库级 `audits/decisions/`（技能目录外）**——`repo-hygiene-check` 规则⑨ 的词预算棘轮只约束**技能目录内** ≥12 KB 的 .md，`audits/` 不受约束。若放 `references/`（如 `maintainers.md` 新增一节），则**必须在同一次提交里抬棘轮并写明理由**——而 `maintainers.md` 余量本就紧张（v18.22.0 §四.2 已核算过余量 <1 KB 的多项），**放进去必然撞墙**。
  - 模板：`audits/decisions/ADR-template.md`（维护者向，**运行期角色不读**）。
  - 与既有体系的分工：`CHANGELOG.md` = 对外时间线；`反哺报告-*` = 批次动议与差集；`maintainers.md` = 主题参考；**`decisions/` = 单决策真源**。四者不构成「同一事实两处维护」——**但必须在 `maintainers.md` 加一行指针，否则就是第五处漂移源**。
- **成本**：模板 + 目录 + `maintainers.md` 指针 ≈ 半天；**补写 3 条历史关键决策**（建议：`exit 10` 收口 / handoff 门 20·21·22 与 M 门 1·2·3 刻意分离 / 写盘安全网 tmp+rename+bak）≈ 1 天。
- **判据**：`consistency-check` 绿（新增指针行）；抽查一条决策，其 Alternatives 段能回答「当初为什么不用另一种做法」。
- **回滚**：删除 `audits/decisions/` + `git checkout -- references/maintainers.md`。

#### A2 【P1｜`[机制]`】捕获层 ⊆ 收窄层：分层纪律 + 反向门

- **来源**：`skills/context-mode/references/anti-patterns.md:247-269` §8「`ctx_execute` Captures, `ctx_search` Filters — Don't Merge the Layers」。
- **原文判据**（可直接作为本地卡的语言素材）：
  > `ctx_execute` 的产出是**一次性写入索引**。完整跑完、让它进索引；**所有收窄都在下游做**。若你在 capture 层裁剪，就是让 filter 层失业——**索引才是唯一幸存面**；在进索引之前丢掉的东西，本会话的查询面上永久消失。
- **本地实况与缺口**：
  - **正向已有**：`M-Form-11` 判定「正文引用 ⊆ 已加载」+「已加载编号有卡片支撑」（`templates/素材加载清单-template.md:5`）。
  - **反向缺**：若 T1/T2/T3 在**落盘时**就预筛/截断（"只留最相关的 10 条"），下游 T4/T5 永远拿不到被丢掉的部分，且这一动作**在产物上完全无形**——与「整卡通读」恰好相反、却同样不可观测。
  - `素材加载清单-template.md:25` 的「## 已跳过」段是**可选**，且明确「本段编号**不计入加载集**」——**语义正确但无门**。
- **落地位置**（不新增运行期文档）：
  1. `references/_shared/检索注入防御.md`（已是三卡共用单一真源，9 行）增一节「落盘不得预筛」：**卡片条数 = 实际取回条数**；不相关者在卡内标注「本轮不采用 + 理由」，**而非不写**。
  2. `templates/素材加载清单-template.md`：「## 已跳过」由可选改**必填**（无跳过则显式写「无」）——遵循本地既有的「**未做须显式声明，防沉默跳过**」纪律（B2 补扫同款）。
  3. **可选机械化**：`m-gate-check.mjs` 增一条反向判据。⚠️ **必须新开命名空间**，不得复用 M-Form 编号——本地已有「M-Form-12 同号两义」的登记教训（`借鉴评估-v1 §四.2`）。
- **成本**：卡 + 模板 ≈ 半天；加机检 ≈ 1 天（含 tests）。
- **价值**：这是「检索返工」的根因之一——T4/T5 发现素材不足时只能重派 T1，而重派的成本（一次 spawn + 全轮检索）远高于当初多存 20 条卡片。
- **判据**：抽 1 个实战项目，`文献卡`/`数据卡`/`案例卡` 的条目数 ≥ 交接报告自报的取回条数；素材加载清单「已跳过」段非空或有显式「无」。

#### A3 【P1｜`[机制]`】计量口径变更固定动作（**最高性价比**）

- **来源**：`docs/adr/0004-stats-strict-compression-formula.md`。
- **本地实况**：v18.22.0 报告 §2.3 标题即为「成本口径纠正（**本报告最重要的单条发现**）」，MEA 族（MEA-1「测量与口径，必须先做」）因「口径有缺陷」而立——**本地踩过完全同类坑**（把基础设施字节当成进上下文的字节；把主会话成本算进角色成本）。但**「改口径」这件事本身没有固定动作**：`token-budget.mjs` 有「口径三要素」（`:29-33`），那是对**当下口径**的说明，不是对**口径变更**的留痕。
- **context-mode 做对的三件事**：
  1. **口径变更本身写成一页 ADR**，而不是只改代码。
  2. **贴 fix 前/后对照表**（同一个 reporter 的同一批数据，三列：坏版 / 中间版 / 修后版 → 56% / 95.4% / 22× 倍数）。
  3. **明说影响面**：「Section 1 的百分比会从 ~56% 跳到 ~95%，lifetime 数字与 capture 计数不变」——**把「哪些数字会跳变、哪些不会」写成读者能核对的一句话**。
  4. **空状态显式**：`if (avoided + returned == 0)` → **不画退化柱**，只出一行诚实提示，**不允许公式退化成一个好看的数**（`analytics.ts:2197-2198`；`ADR-0004:57-60`）。
- **落地位置**：`references/maintainers.md` 新增固定动作节，与既有两条并列：
  - §七「收口批固定动作：差集 + 反向核验」
  - §十「发布前固定动作：工具链不得改写仓库」
  - → **新增「计量口径变更固定动作」**：改任何计分 / 比例 / 统计口径（`token-budget.mjs` / `token-cost.mjs` / `lunheng-stats.mjs` / `quality-score.mjs` / 任何 `x/5` 或百分比）时，须在同处贴 **① 同一输入 fix 前 / fix 后两列**、**② 受影响显示项清单 + 不受影响项清单**、**③ 若为「无数据」态，须显式给出提示文案而非让比例退化**。
- **成本**：≈ 1 小时。**零机检风险**（纯维护者向规则）。
- **判据**：条文在 `maintainers.md`；下次口径改动时按此贴表。
- **回滚**：`git checkout -- references/maintainers.md`。

#### A4 【P2｜`[机制]`】「双重计费」反模式条目

- **来源**：`skills/context-mode/references/anti-patterns.md:290-291`（`ctx_index(content: response)` 把已在上下文的数据**再送一次 = 2× 计费**）；`BENCHMARK.md` 语境下 Playwright 快照 135 K → **270 K** tokens。

## §四、可行性判定：DSH 宿主侧的决定性事实

> 本节是「能否落地」的技术核心。核查对象：`dsh-plugin-guide/references/official-docs/docs/**`（官方仓库原文）。

### 4.1 宿主已提供的能力（**不要重造**）

### 4.2 论衡插件入口的**实际**形态（实测）

`lib/index.js`（373 行）实际只调 3 个 `ctx.*`：`ctx.effect()`（`:245`、`:302`）与 `ctx.skills.register()`（`:247`、`:267`）；`lib/guard.js:192`、`lib/tools.js:105` 各用 `ctx.get('tools')`。
**全 `lib/` 无任何事件监听**（实测 grep 无 `ctx.on/once/off/emit/intercept/tap` 命中；`tools.js:58-61` 的 `.on()` 是 `child_process` 流监听，非宿主事件）。

> **判据**：论衡当前的插件面 = **「注册技能 + 一处只收紧的写保护」**，**零拦截、零注入、零事件**。这是一条**刻意**的架构边界（`AGENTS.md`：guard 是「比 prompt 强、比机制强制弱」，机制可信度靠 `git` + 四道门 + 主人 review）。

### 4.3 结论：三类借鉴的落地性

| 借鉴类型 | 可落地性 | 说明 |
|---|---|---|

## §九、「零 exec」专项复核（2026-09-29 追加）

> 缘起：主人问「论衡的『零 exec』哲学对于 DSH 系统有意义吗？」→ **前提不成立**，但复核查出一处活体口径矛盾，故单列。

### 9.1 前提纠正：论衡**没有**「零 exec 哲学」

「零 exec」是 **OpenClaw 线**（本报告 §一 所称「外部」）的立场；论衡是**受限 shell**。论衡**主动否认过三次**：

| 位置 | 原文（节录） |
|---|---|
| `glossary.md:316` | 「（v2.5.2-dsh.4 审计修订）论衡**不是零 exec**——主控按需执行随包脚本白名单内的脚本…」 |
| `glossary.md:307` | 「（v2.5.2-dsh.5 审计修订：如实声明，**非「零 exec」**）」 |
| `checkers/中文AI痕迹-checker.md:221` | 「检测器零 shell 属实；论衡主控/终检另有白名单脚本，故**不说「论衡零 exec」**」 |
| `_shared/format-export.md:74` | 「**执行边界**（v2.5.2-dsh.5 修订，**非「零 exec」**）」 |

「主动否认三次」本身说明这个混淆**之前已经咬过一次**。

### 9.2 但 `SKILL.md:24` 仍留一句反话（措辞漂移）

`SKILL.md:24` 表格单元格原文：「…**主流程默认零 exec**（白名单脚本见「执行能力边界」）」——同一句里既称零 exec 又指向白名单，且与上表四处相反。撞本地教训 #156（同一事实两处必漂）。

### 9.3 分层结论（答主人之问：分两层，答案相反）

| 层 | 对 DSH 有无意义 | 理由 |
|---|---|---|
| **环节级纪律**（判定归 LLM 推理、不跑脚本） | **有** | 它守的不是「不用 shell」，而是 ① **机械只做守恒、不做强度判定**（`_lib/causal.mjs` 设计原则）；② **判定理由可写进报告、可被 T7 复核**（脚本只给数字，不给理由）。DSH 下另有一层价值：**跨权限模式行为一致**——DSH 有 sandbox / approval / `danger-full-access` 等档位（本会话即 `danger-full-access`），纪律使论衡在**任何**档下行为相同，不依赖「这次没被拦」 |
| **项目级哲学** | **无**（且已在亏本） | ① **白名单在 DSH 上不是机械强制**——`SKILL.md` 结构性要点 1 明写「**技能级工具白名单/denied 在 DSH 无效**——工具集由 Agent 预设决定，技能声明不了也禁不了工具」，故「白名单」是**自我纪律**而非机制；② 论衡**已主动放宽过**（`M-Gate-Algorithm.md:826`「DSH 例外」）；③ 它是**另一个宿主的环境限制**推导出来的，移植 = 把别人的约束当成自己的设计目标 |

> **判据一句话**：准确的说法不是「零 exec」，而是 **「判定归 LLM、测量归脚本、白名单是自我纪律而非机制」**。

### 9.4 ⭐ 复核副产品：`sha256 回填口径` 存在**活体矛盾**（→ 新增动议 EXEC-1）

`M-Exist-2` 的算法段**自身给出三个互斥答案**：

- `M-Gate-Algorithm.md:825`：「主控 LLM **不能**直接计算 sha256 二进制哈希 → 主控用 `read` 读全文 + 推理验证」（← 零 exec 侧）
- `:826`：「**DSH 例外**：DSH 下主控有 `pwsh` 工具，**可直接计算 sha256 回填，不必留占位符**…仅在主控决定不跑 shell（严格零 exec 场景）时才降级为占位符」（← 受限 shell 侧，并把零 exec 降格为「一种可选场景」）
- `:827-833`：「**生成 sha256 占位**…⚠️ 是【待主人在 host shell 手动计算后回填】的占位符，**不是 agent 计算结果**」（← 回到零 exec 侧，**与 `:826`「不必留占位符」直接冲突**）

下游两份文档各选一边、**均未跟上 `:826` 的例外**：

- `deliverables.md:122`：「sha256 占位符 `[哈希校验待主人回填]`（人类可选回填；**agent 不执行 sha256**）」
- `SKILL.md:31`：「真实 hash/字数**由主人在 host shell 回填**」

**而真源其实早已存在**（本报告新增实测）：`build-evidence-bundle.mjs:38,287,302,314-331` 逐文件算 sha256 写入 `manifest.json`，其 `:332` 自述「（N 个文件记 sha256；**M-Exist-2 据此复算**）」，`:280` 更直言「M-Exist-7 的『证据包指纹』**只核「占位符出现了没有」**」。
→ **`交付说明.md` 的「证据包指纹」段是 `manifest.json` 的冗余载体**，而三份文档互斥争论的正是这个冗余载体该写什么。

> **顺带消一个可能的误判**：`mexist-gates.mjs:895-896` 的正则为 `\[哈希校验待主人回填\]|sha256[:：]?\s*[0-9a-f]{16,}`，**两种形态都放行**，故写实值**不会撞 M-Exist-7**；只是该门的失败诊断措辞只点名了占位符那一形态。

> **✅ 定案（2026-09-29 主人裁定）**：**「证据包指纹」段写实值，权威真源 = `final/证据包/manifest.json`，无需主人回填**；`[哈希校验待主人回填]` 路径**废弃**。执行口径与**派生决策点**（机检是否同批收紧，否则定案落不到机制层）见《[修订计划-context-mode借鉴-v1.md](修订计划-context-mode借鉴-v1.md)》§十一。

**这正是 §三 A1/A3 所诊断的复发模式的活体样本**：DSH 例外（v2.5.2-dsh.0）只加在**一处**，兄弟文档从未同步。

### 9.5 另一处未经验证的约束（成本已实测）

`segment-chars.mjs:19` 注释原文：「T5 子代理**无脚本执行能力**（论衡主流程零 exec），只能目测 → **实测偏差 6~10%**」（实例：清单预估 16,987 / 实测 18,071，超上限 1,271 字 → 被迫 3 轮削裁）。

但**全库 `.md` 无任何角色卡或门禁断言此条**（本报告实测 grep 零命中）——该约束**只存在于一句脚本注释里**；而按 `SKILL.md` 结构性要点 1「工具集由 Agent 预设决定」，子代理**很可能有 `pwsh`**。
→ 若该假设不成立，论衡即为**一个不存在的约束支付了 6~10% 的实测误差**。**须实核，不应继续假设**（→ 动议 EXEC-4）。

> 需公平记载：论衡**处置方向已正确**——`segment-chars.mjs:21-22` 让**主控**在派发前跑一次实测、把准确「现况」写进派发话术，误差由「双向」降为「单向」。这正是「测量归脚本、判定归 LLM」的正确形态，故 9.5 的问题**不是方向错，而是一条口径没有被验证过即被当成事实使用**。
