# 代码审查报告 — 性能与安全隐患（2026-10-02）

- 审查对象：`lunheng-article-pipeline` v18.62.4
- 审查面：`lib/**`（运行时入口，5 个文件 / 共约 104 KB）+ `skills/*/scripts/**`（用户输入可达面）
- 方法：静态通读 + **可复现的动态验证**（所有结论均在 Node 22.12.0 / Windows 实测复现，脚本见文末）
- 结论摘要：**1 项 P0（数据静默丢失）+ 1 项 P0（工具结果被静默改写）+ 2 项 P1 + 6 项 P2**

> 说明：本仓的静态门（`consistency-check.mjs`）扫描根是**技能根**（`ROOT = join(__dirname, '..')` = `skills/lunheng-article-pipeline`），  
> `lib/**` **完全在扫描面之外**。这不是批评门的设计，而是解释「为什么下面这些缺陷能长期存活」——  
> 它们是**行为缺陷**，而 `lib/**` 只有少数几个测试触及，且恰好都用了小输入。

## P0-1 · 脱敏钩子把超过 60000 字符的工具结果**静默截断**

**位置**：`lib/index.js:344` → `lib/ethics-sanitize.js:150,241-244`

```js
// lib/index.js:344  —— 未传 maxChars
const out = sanitize(b.text, { mode: 'basic', dicts })
```

`sanitize()` 的 `maxChars` 默认值是 **60000**，超出即 `out.slice(0, maxChars)` 截断。

**实测复现**：

| 输入         | 输出            | 尾部标记                      |
| ---------- | ------------- | ------------------------- |
| 150,016 字符 | **60,000 字符** | `结尾标记-END-OF-FILE` **丢失** |

因为截断会让 `out.text !== b.text`，`changed` 置真 → 必然执行 `result.content = sanitized`  
（`lib/index.js:356-357`）。而回传的 `summary` 只装了  
`{ mode, counts, replacements, degraded, degradedReason }`——**没有 `truncated`**。

**影响面（这是本仓最痛的一类缺陷形态）**：

- 触发条件是 `read` / `web_*` / `subagent*`（`lib/index.js:336`）——**恰好是流水线的主数据通路**；
- 长文流水线必然读大文件、收长子代理回报，**>60000 字符是常态而非边界**；
- 截断**完全不可见**：模型拿到的是一份「看起来正常」的文本，没有任何 `truncated` 标记，  
  后续角色会基于残缺材料作业并给出「合格」回报——与仓内反复批判的「静默降级」是同一形态。

**建议修法**（二选一，推荐第 1 种）：

1. 钩子内显式传 `maxChars: Number.MAX_SAFE_INTEGER`（钩子的职责是脱敏，不是限流；限流应由宿主/工具侧负责）；
2. 若必须限流，则把 `truncated` / `truncatedAt` 一并写入 `result.ethicsSanitized`，并**在文本尾部插入显式标记**，  
   使下游无法把截断读成完整。

## P0-2 · 脱敏钩子**改写** `result.content`，而非仅注入元数据

**位置**：`lib/index.js:342-360`

```js
const sanitized = blocks.map((b) => { ... return { ...b, text: out.text } })
if (changed && result && typeof result === 'object') {
  result.content = sanitized          // ← 真实改写，且回写到 result 本身
  ...
}
```

`SECURITY.md`（"H2 伦理脱敏监听器" 行）对它的描述是  
「把 `reviewFlags` 与 `ethicsSanitized` 计数**注入** result」——**未声明它替换正文**。  
文档与实现的行为描述不一致，而真实行为更激进：**所有 `read` / `web_*` / `subagent*` 的文本块被无条件改写**。

**实测误伤样例**（均为完全合法的非个人数据）：

| 输入                                         | 钩子后的模型可见内容                             |
| ------------------------------------------ | -------------------------------------- |
| `ts=1735689600000 创建于该时刻`                  | `ts=1735689600000 创建受访者A刻` ← **语义被破坏** |
| `订单 ID = 1234567890123456 已入库`             | `订单 ID = [银行卡号-REDACTED] 已入库`          |
| `const BANK_ACCT = "6222021234567890123";` | `const BANK_ACCT = "[银行卡号-REDACTED]";` |
| `payload=9876543210987654`                 | `payload=[银行卡号-REDACTED]`              |

第二行值得单独说明：`创建于该时刻` 里「于」被判为姓氏，`trimGiven` 裁掉「该」后替换成 `受访者A` ——  
**这是把普通中文词切成人名**。仓内注释早已如实承认「中文人名切分在无词表边界时本质上是歧义问题」，  
但承认歧义 ≠ 可以**默认对全量工具输出执行改写**。

**风险性质**：

- **数据完整性**：读源码 / JSON / 日志 / 财报数字时，模型看到的是被改写的版本，且**它自己不知道**；
- **审计留痕失真**：闸门实据依赖落盘产物，而 agent 的推理输入已被改写；
- **不可控面**：`web_*` 结果同样入钩，第三方页面内容会被静默修改。

**建议修法**：

1. **默认只标记不改写**：`basic` 模式下把命中项写入 `result.reviewFlags` / `result.ethicsSanitized`，  
   **不动 `result.content`**；改写行为改为显式 opt-in（`Config.hookRewriteContent: true`，默认 `false`）；
2. 若保留默认改写，至少收窄触发面：仅对**材料类路径**（`references/`、访谈稿命名约定、`mode` 由调用方声明）  
   生效，而非对 `read` 的**任意**文件生效——读 `lib/*.js`、`package.json` 时不应触发脱敏；
3. 修正 `SECURITY.md` 的描述，明确「会改写正文」这一事实与其边界。

## P1-1 · 机制写保护存在三类可复现绕过

**位置**：`lib/guard.js:39-40`（`WRITE_TOOLS` / `PATH_KEYS`）

实测（`allowed: () => false`，目标 = 技能包内 `SKILL.md`）：

| 场景                                    | 结果                                 |
| ------------------------------------- | ---------------------------------- |
| `write` + `{path: <技能包内绝对路径>}`        | 🛑 已否决（正常）                         |
| `Write`（大写）+ `path`                   | 🛑 已否决（v18.16.0 修复生效）              |
| `apply_patch` + `patch`（文本内路径）        | 🛑 已否决（正常）                         |
| `apply_patch` + `patchContent`        | 🛑 已否决（v18.18.0 的 `includes` 修法生效） |
| **`write` + `{"0": <路径>}`（数字键位参）**    | ✅ **放行**                           |
| **`write` + `{targetPath: <路径>}`**    | ✅ **放行**                           |
| **工具名 `write_file` + `{path: <路径>}`** | ✅ **放行**                           |

**根因**：

- `writtenPaths()`（`lib/guard.js:114-118`）对**顶层字符串值**只在键名命中 `PATH_KEYS` 时才收；  
  数字键名（位置参数形态）既不命中键名、`v` 又是 string 而非 object，两条分支都不进 → 静默漏检；
- `PATH_KEYS` 未含 `targetPath` / `pathToFile` / `absolute_path` 等常见变体；
- `WRITE_TOOLS` 未含 `write_file` / `create_file` / `notebook_edit` / `fs_write` 等命名。

**风险**：当前 DSH 宿主的写工具名与参数键恰好落在集合内，所以**实际不可利用**；  
但该守卫的自我定位是「机制级否决」（`SECURITY.md` 措辞：命中受保护根的写调用**在分发前即被否决**），  
一旦宿主换工具名/换参数键，守卫会**静默失效**——属于「安全控制失效且无告警」的高危形态。

**建议修法**（低侵入）：对**顶层参数**增加一条兜底——若某字符串值能被解析为绝对路径、  
且其父级键名不在已知的**内容类键**白名单（`content` / `text` / `old_string` / `new_string` /…）内，则一并纳入候选。  
另：数字键名一律纳入（位置参数语义）。同时把「收不到任何候选路径」改为 `warn` 上报，  
避免「静默不设防」。

## P1-2 · 守卫内部异常时 **fail-open**（静默放行）

**位置**：`lib/guard.js:246-248`

```js
} catch {
  return undefined // guard 自身异常不改变权限（宁松勿误伤）
}
```

注释的取舍是清晰的，但后果是：**任何未预期的参数形状导致守卫抛错时，写操作照常放行且无任何日志**。  
对一个「机制级」安全控制而言，fail-open + 静默 是应当被重新评估的组合。

**建议**：保留 fail-open（避免误伤），但**必须留痕**——catch 分支调用 `report?.('warn', …)` 输出  
「守卫判定异常，本次调用未被检查」。这与其 `lib/index.js:192-198` 已确立的「降级必须可观察」口径一致。

## P2-1 · `runScript` 按 Buffer 分块解码，多字节字符被切碎

**位置**：`lib/tools.js:58-59`

```js
child.stdout.on('data', (d) => { out = append(out, d) })   // 未 setEncoding
```

`String(d)` 对每个分片独立做 UTF-8 解码，跨分片边界的汉字会被解成 `U+FFFD`。

**实测**：7.2 万字符中文输出 → 实得 72003 字符，含 **5 个 `U+FFFD`**。  
本仓三个工具脚本（M 门 / 交接门 / 字数）都会输出大量中文，触发门槛约 64 KB。

**建议修法**：`child.stdout.setEncoding('utf8')` / `child.stderr.setEncoding('utf8')`，  
或改用 `StringDecoder` 以保留跨分片的半个字符。

## P2-2 · 脱敏对超大文本无上限，同步阻塞工具结果通路

**位置**：`lib/index.js:344`（钩子）/ `lib/tools.js:396`（工具）

实测耗时（basic 模式）：

| 输入规模     | 单次耗时                        |
| -------- | --------------------------- |
| 32 字符    | 0.13 ms（固定开销很低，正则在千级分支下仍廉价） |
| 2 KB     | 0.13 ms                     |
| 200 KB   | ~13 ms                      |
| **2 MB** | **~150 ms（同步）**             |

固定开销不构成问题（这一点此前容易被误判，实测已排除）。  
真实风险是**线性成本 + 无上限**：`read` 一个大 JSON / 日志（10 MB 量级）会引入约 1 秒的同步 CPU，  
且 `lunheng_ethics_sanitize`（`lib/tools.js:394-396`）用  
`readFileSync` 全量读入 + `sanitize(raw, { maxChars: Number.MAX_SAFE_INTEGER })`，  
在超大文件上会同时占用「原文 + 脱敏副本」两份内存。

**建议**：钩子侧加一个**体积上限**（例如 >256 KB 跳过改写，仅回传 `{ skipped: true, reason: 'too-large' }`），  
使「改写」不在不可控体积上发生；工具侧保留分页（已具备 `offset` / `maxChars`），  
不要在内部再以 `MAX_SAFE_INTEGER` 展开全文。

## P2-3 · `ethicsSanitized.summary` 取的是**最后一个**文本块，不是聚合

**位置**：`lib/index.js:347-353`

`summary` 在 `blocks.map(...)` 内被反复覆盖，最终只保留**最后一个** text 块的结果；  
`counts` / `replacements` 同样是**单块**而非全文聚合。  
多块结果（`read` 带附属说明、`web_*` 多段落）下，`result.ethicsSanitized` 会**低报**实际替换量。

**建议**：在 `map` 外维护累加器，或明确把字段改名为 `lastBlock` 以避免被读成全文统计。

## P2-4 · `lib/**` 不在任何静态门扫描面内（系统性成因）

- `consistency-check.mjs:106` `ROOT = join(__dirname, '..')` → 技能根；`walk(ROOT)`（`:159`、`:375`）只扫技能目录；
- `lib/index.js:426-430` 自己的注释也已登记「`lib/**` 完全在扫描面之外」。

**后果（本报告的直接证据）**：P0-1、P0-2 都是**行为缺陷**，而门只扫版本号/锚点/计数这类**形态**；  
`tests/h2-h5-listeners.test.mjs` 覆盖了 H2，但用例输入是短文本（手机号），  
既不断言 `result.content` 的改写结果，也不覆盖 >60000 字符的路径 → 静默截断**无门可守**。

**建议**：至少补一条 **行为级回归**：构造 150,000 字符的 `read` 结果，断言  
① `result.content[0].text.length` 未缩短；② 存在 `truncated` 标记。这条用例的成本极低、价值极高。

## P2-5 · `SECURITY.md` 与实现漂移（安全文档失真）

1. `/lunheng-stats` 行（`SECURITY.md:24`）称「**仅接受 `--json` 一个旗标**；其它 token 一律拒绝」，

2. H2 行（`SECURITY.md:25`）未声明「**会改写 `result.content`**」这一事实（见 P0-2）。

**建议**：同步这两处；若可能，把「文档声明的监听器行为」纳入 `consistency-check` 的可机械核对面（至少把  
`--run-dir` 是否出现在两处做交叉断言）。

## P2-6 · 命令脚本的路径围栏不一致（低危）

`lib/commands.js` 对 `/lunheng-status` 的 `pickProject` 做了**三层收口**（词法 → 结构 → 物理 realpath），  
对 `/lunheng-stats --run-dir` 做了白名单 + 包含关系判定——这两处的严谨度值得肯定。

但同族脚本侧不一致：

- `skills/lunheng-commands/scripts/history-cli.mjs:48` `join(RUN_DIR, projectId, 'history.jsonl')`  
  —— `projectId` **完全未校验**，`../` 可越出 `run/`（后缀固定，危害限于读取同名文件）；
- `skills/lunheng-commands/scripts/pending-cli.mjs:172` `resolve(args[i + 1])` —— `--run-dir` **无围栏**。

因调用者是 agent / 主人且仅读，**实际风险很低**；登记的意义在于：  
同一「读 run/」语义在两处实现出两套安全强度，属可维护性隐患。

**建议**：把 `lib/commands.js` 的收口逻辑抽成共用函数，或在脚本侧照抄一份。

## 已验证为**良好**的部分（避免只报忧）

- **无硬编码密钥**：全仓正则扫描 `api_key|secret|password|token = "…"` 零命中；
- **无命令注入面**：`lib/**` 与随包脚本中的 `spawn`/`spawnSync` 全部使用 `process.execPath` + **参数数组** + `shell:false`；  
  `shell:true` 仅出现在 `scripts/`（**仓库级开发门，不在 `package.json` 的 `files` 白名单内，不随包发布**）；
- **工具入参不能注入命令**：脚本路径由入口拼死（`join(skillRoot, 'scripts', …)`），不经 shell；
- **`guard.js` 的 `canonicalPath` 做得很扎实**：长路径前缀、盘符大小写、`realpath` 解 junction/8.3 短名、  
  两基准（会话工作区 + 进程 cwd）取并集——这三点是多数同类实现会漏的；
- **`Config` 零依赖校验**：不 import `@deepseek-ai/schemastery` 以避免 pnpm 布局下解析失败，是**实测驱动**的正确取舍；
- **降级可观察口径**：「warn 永不静音」「降级必须打一行」已贯穿 `guard.js` / `tools.js` / `index.js`，  
  与「静默降级是本包第一缺陷形态」的自述一致。

## 复现方式

本次审查使用的临时验证脚本（均以 `node <脚本>` 直接运行，不依赖宿主）：

- 截断复现：构造 `'A'.repeat(150000) + '结尾标记-END-OF-FILE'`，比对 `sanitize()` 输出长度与尾部；
- 误伤复现：对 `ts=<13位时间戳> 创建于该时刻` 等 5 条样例跑 `sanitize()` 比对文本；
- 守卫绕过：构造假 `ctx`（`{ get: (n) => n === 'tools' ? { guard: (f) => { guardFn = f } } : undefined }`），  
  以 8 种参数形态调用 `guardFn({ name, arguments, agent })`；
- 分块解码：`spawn` 一个输出 72 KB 中文的子进程，按 `lib/tools.js` 原写法 `out += String(d)` 收集后统计 `U+FFFD`。
