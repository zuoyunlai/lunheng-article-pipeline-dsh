## 1. 审计结论

### 1.1 一句话结论

论衡的**架构骨架与"机械下沉"的工程化程度属同类技能包第一梯队**——插件/宿主边界清晰、写栅栏与路径围栏是真控制、20 条卫生规则与 7 作业 CI 是硬约束、737 条用例全绿且无 skip。

但**"插件 ↔ 宿主"的契约层存在功能性空洞**：H2 伦理脱敏监听器在真宿主上**整体静默失效**，H7 三档路由监听器**恒空转**；而现有全部测试与门**结构性看不见**这两者——因为**全仓零测试 import 真宿主**，所有 `lib/**` 行为测试跑在自建桩上，桩与实现共同犯同一个错。

问题不在"做得糙"，而在**机械化用在了"仓内自洽"上，没有用在"跨进程契约"上**。

## 4. 核心发现与主理人独立复核

> 以下四项由主理人**亲自读宿主源码复核**，不依赖成员转述。成员报告中的行号凡涉宿主，均由我重新定位并确认。

### 4.1 H2 失效的两条独立机制（复核结论：两条**均成立**）

**复核方法**：直接读 `node_modules/@deepseek-ai/dsh-tools@0.1.2-rc.1/lib/index.js`。

**机制 D1 — 对已冻结对象赋值直接抛错**

```text
:3439  createSuccessResult 返回 this.markCanonical(exec, this.materializeFinalResult({ isError:false, value, content, ...meta }))
:3466  materializeFinalResult(result)
:3477      return deepFreeze({ ...materializePresentation({...}), value: result.value })   ← 深冻整张对象图
:3449  normalizeDispatchResult: if (this.canonicalResults.get(result) === exec.token) return result   ← 原样返回同一个 canonical 对象
:3242  finalizeScheduledExecution(exec, result) → :3244 this.postExecute(exec, result)
:3379      const decision = await this.ctx.waterfall(scopeTarget(this, exec.agent), "tools/post-execute", exec, result, () => Promise.resolve({ kind: "accept" }))
```

→ 交给 `tools/post-execute` 的 `result` **就是那个被深冻的对象**。插件 `lib/index.js` 是 ESM（严格模式），对其新增/修改属性抛 `TypeError`。
→ 插件侧吞错点：`lib/index.js:452` `catch { /* 脱敏失败不动 result */ }` —— **裸 catch，连 warn 都没有**。

**机制 D2 — 非契约字段到不了任何消费方**

```text
:3467-3471  const presentation = { content, ...meta?, ...additionalContexts? }
:3472-3484  isError 分支 materializePresentation；否则 deepFreeze({ ...materializePresentation({isError, ...presentation, concludesTurn?}), value })
```

→ 字段白名单只有 `content` / `meta` / `additionalContexts` / `isError` / `error` / `value` / `concludesTurn`。
→ 插件的 `reviewFlags`（`lib/index.js:435`）与 `ethicsSanitized`（`:437`）**被结构性丢弃**，从未到达模型、会话日志或 `tools/result` 通知。
→ 即使某次调用因 `deferredContexts` 走了未冻结分支使 D1 不触发（宿主 `:3215`），D2 **依然独立成立**。

**主理人复核结论**：成员报告的 D1、D2 **两条均由源码证实**，且**任一单独成立即可使 H2 整体失效**——这是它定级为 P0 的依据。

1. **把"跨进程契约"提升为一等公民（最高收益）**。本仓已证明机械脚枪能整类消灭缺陷（规则 ①⑳㉓：跨文件版本、M 门节头项数、阈值总表），但**全部作用在仓内**。跨进程面（宿主事件 arity、payload 键集合、结果对象可变性、字段投影白名单、工具 output DSL）应当有**同等强度的产物级断言**。这是本次审计最大的单点改进空间，收益是 R1/R2 这类缺陷**永不复发**。迁移：只加脚本 + CI 一行，不改任何既有门语义。
2. **`lib/index.js` 拆分候选**。把三个监听器抽到 `lib/hooks.js`（每个 hook 一个导出 + 契约注释块），`apply()` 只做编排。收益：`host-contract` 门可以从"正则解析 607 行"升级为"import 模块、检查导出的 arity 常量"，顺带把 E6 的"注释即契约"变成"代码即契约"。**纯重构、无宿主风险，适合在 P0 修完之后做**。
3. **"宿主传入对象只读"写成仓内规则**。在 `repo-hygiene` 加一条"`lib/**` 禁止对宿主传入对象赋值"（正则级即可），配合集成测试形成"规则 + 用例"双保险——与本仓既有风格完全一致，成本极低。
4. **扩展点收尾**。`Config` 7 键 + env 开关 + 4 工具 + 2 命令已是清晰边界；唯一缺失的是"这些键的**行为**有没有测试"。`docs-facts.test.mjs`（63KB）已在做"文档 ↔ 代码事实"对齐，把 `hookRewriteContent` 等键的**行为**纳入即成闭环。
