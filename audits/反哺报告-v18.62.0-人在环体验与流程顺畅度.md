# 反哺报告 — v18.62.0 人在环体验与流程顺畅度

> **性质**：**体检型反哺**（主人 2026-09-30 提问「论衡插件流水线是否顺畅，流程是否还存在值得优化的地方？另外人在环的交互体验是否还可以更好？」→ 主控出诊断 → 主人批示「成文反哺报告落盘，然后开始依次全部修订」）
> **报告依据**：**只读勘察**（仓库自身文档 / 脚本 / `case-studies` 的实测记录）——**不是**本次现场跑机观测。**如实边界**：主控**未跑过真实端到端流水线**（需数小时 + 主人四门在场，agent 无法自主完成，`references/_shared/模型路由.md` 已自陈同一限制）。
> **证据口径**：每条结论都给出**仓库内可复核的出处**；无出处的判断一律标「缺口」。

## 一、总判据（一句话）

**流水线本身是顺畅的**——中断韧性（三段式 + 骨架先行 + 交接门机械验收）、契约前置（preflight）、机检覆盖（M 门 25 项 / G0–G14 / 四道仓库门）都已被实战反复打磨，且**6 个已知卡点已被前人修过**（见 §二）。

**真正的未覆盖面只有两类**：

- **A 类「软约束空转」**：写在说明文字里、无 checklist、无硬门禁的义务 —— 至今仍有一处活着（审计视图刷新）。
- **B 类「人不在场」**：4 门必须 + `ask_user_question` **不设超时** + 「未答复就等」，而实测 **17 个有效项目里 8 个跨度 ≥8 h** → 主人吃饭/睡觉时流水线**硬停在门上，无任何离线出路**。

## 三、待修项（本批落地；F 族编号）

> 命名：`F` = Flow / 人在环族（与报告 v2/v3/v4 的 `H` 族 DSH 接缝**刻意分开**——那族是「接宿主能力」，本族是「流程与交互」）。

### F1 · 主人离场预案（**优先级最高**）

**缺口（有据）**：
- `pipeline-readme.md:327`：四门**全部必需、不设可省任一门**（轻量档只减角色、不减门）
- `templates/主人确认-template.md:82`：**不设超时**——「主人未答复就等」
- `templates/主人确认-template.md:81`：**工具失败 ≠ 主人同意**（`NO_PROVIDER`/`ASK_ABORTED` 不得当通过）
- `case-studies.md:147` / `SKILL.md:147`：**17 个有效项目里 8 个跨度 ≥8 h、另 8 个 ≤4 h**

**后果**：主人离线（吃饭 / 睡觉 / 出差）→ 流水线**硬停**在该门，既不能推进也不能自动降级。而「默认通过」会毁掉 §6 的可追溯性（正是 81 行要防的）。

**修法**：Phase 0 增加**离场预案**（主人**事前显式预授权**）。关键设计——它与「工具失败≠同意」**不是同一件事**：

| 维度 | 工具失败（禁止当通过） | 离场预授权（允许当通过） |
|---|---|---|
| 谁表达的 | **没人**表达 | **主人**在 Phase 0 显式写下 |
| 留痕 | 只有失败码 | §6 记「预授权 + 条件 + Phase 0 出处」 |
| 生效条件 | —— | **仅当**(1) 主控建议=通过 (2) 无 P0 (3) 无「未做项」时 |
| 越界处理 | —— | 条件不满足 → **仍须等主人**（预授权不兜底风险决策） |

**机械落点**：`handoff-check` 的 A7 **不需改**——预授权门同样要回填 §6（写「提问方式 = Phase 0 预授权」+ 条件核验结论）。这是刻意选择：**不新增脚本分支**，风险最低。

### F2 · 确认单显式「本门增量」

**缺口（有据）**：四门各一份单（`主人确认-template.md` 结构 = 7 段 + Phase 0 附加 3 段）；`:94` 写「主人每次读本单 1-3 小段即可」。但主人**看不到「这一门比上一门新增了什么需要我判断」**——选**全单 vs 微确认单**是主控的**隐式**判断（`:109` 微确认单只给了「全部为常规项」这个条件，没有可核对的判据）。

**修法**：确认单增加**一行显式的「本门增量」**，并给微确认单一个**可对照的判据**：增量 = 0（无缺口 / 无待决 / 无风险升级）→ 强制走微确认单；增量 > 0 → 全单，且必须把增量写在这一行。

**为什么值得**：把「主控凭感觉选格式」变成「有判据、主人可核」。

### F3 · 数值型约束上桌

**缺口（有据）**：`00-主控-扩展职责.md:550` QLT-5（2026-09-28）实录——主控按机制拒开轮（「B 轨累计已达 1 → 不再开」），主人回「**B轨额度恢复了啊**」→ 主控只能走「**辨名**（额度 ≠ 轮次上限）→ 记为主人显式授权例外 → 读数冻结」。根因：**机制数值对主人不可见、不可改**，冲突时全靠主控临场解释。

**修法**：确认单增加**「本门生效的数值约束」**段（如 `A 轨 1/2 轮`、`B 轨 1/1 深化`、`字数上限 · 已用`），并明确：**主人可在本门当场显式变更该数值**，变更即写进 §6 留痕（效力等同机制修订的授权例外）。把「辨名」变成「**看到 + 决定**」。

### F4 · 多项目「待我决策」收件箱

**缺口（有据）**：主人侧三件套（`pipeline-readme.md:318` §主人侧三件套）全部位于 `run/<项目>/`；`进展-主人版.md:11` 的「🙋 需要你做的事」也是**单项目**内视角。主人同时跑 2 个项目时，「现在需要我做什么」分散在两处，**无聚合视图**。

**修法**：`/lunheng-status`（`lunheng-commands` 内嵌子技能）增加**「待我决策」聚合段**——扫 `run/*/阶段确认-*.md` 的 §6 未回填项 + 各 `进展-主人版.md` 的「需要你做的事」。**纯聚合、零新数据、零新留痕义务**。

### F5 · 流程只读仪器化

**缺口（有据）**：
- `case-studies.md` 给出**双峰分布**（8 个 ≥8 h / 8 个 ≤4 h）——但**无归因**；
- `模型路由.md:154` 自陈「真实运行测量**未做**」（需数小时 + 含人在环四节点，agent 无法自主完成）。

**修法**：**不改流程**，只加一个**仓库级只读汇总**（不随包），从既有产物派生 4 个可观测量：

| 观测量 | 派生自（已有产物，无需新留痕） |
|---|---|
| 每门间隔时长 | 四张 `阶段确认-*.md` §6「回复时间」之差 |
| 返工轮次 | `drafts/修订说明-vN.md` 的 N + `audits/审计报告-vN.md` 的 N |
| 门首次通过率 | §6「主控落盘结论」是否含「打回」 |
| 续接次数 | `agents-log.md` 的 Tn 记录条数 vs 角色数 |

**为什么先做它**：双峰无法归因 = 后续任何「优化流程」都是**猜**。先有数，再谈优化。
