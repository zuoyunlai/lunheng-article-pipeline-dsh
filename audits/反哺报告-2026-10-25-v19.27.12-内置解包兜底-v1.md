# 反哺报告 · v19.27.12 —— 发版被跑者 tar 卡住，`pack-smoke` 加内置解包兜底

> 日期：2026-10-25｜范围：`scripts/pack-smoke.mjs`、`scripts/_lib/untar.mjs`（新）、`tests/scripts/untar.test.mjs`（新）
> 授权：主人 2026-10-24「按规则发版」；本批为发版卡点的真修，不改任何门判据与断言强度。
> 结论一句话：**包没问题，是 Windows 跑者的 `tar` 对一份合法归档误判**；门从此不再被它卡住，且兜底分支每次 CI 都被真跑一遍。

---

## 一、问题

`v19.27.11` 的 tag 已推，但 npm 上仍是 **19.27.3**。原因不是发布脚本，而是发布链前一道闸：

- `publish.yml`（tag push 触发）的 `gates` 作业要求「同 SHA 的 `ci.yml` 必须成功」；
- `ci.yml`（commit `ca7e96d8`）唯一红的两项都在 windows-latest：`pack-smoke (windows-latest)` 与 `script-tests (windows-latest, 22.19)`；
- 红的原因是解包：`tar 解包失败（exit 1）：tar: Archive entry has empty or unreadable filename ... skipping`；
- `gh run rerun --failed` 连试两次（共 3 次）**同样红**。

于是「按规则发版」这条路被一个与代码无关的环境缺陷堵死——**fail-closed 设计本身是对的**（宁可不发，也不发未经门禁的包），但它把上游抽风直接升级成发版阻塞。

## 二、证据链（先分清「包坏」还是「环境坏」）

| 侧面 | 实测 | 读法 |
| --- | --- | --- |
| 同一次 CI 的其它 OS | ubuntu / macOS 的 `pack-smoke`、`install-smoke`、`script-tests` 全 success | 同一份产物换一种 tar 就正常 → 不是产物 |
| 本机门 4/4 | `node --test tests/scripts/pack-smoke.test.mjs` → 1/1 pass | 本机链完全正常 |
| 归档完整性 | GNU tar 1.35 `tar -tzf` 列 213 条；`gzip -t` 通过 | gzip 层无损、目录结构可读 |
| 与已发布包对照 | 与 registry 上的 v19.27.3 包逐条比：**212 → 213**，唯一新增 `package/skills/lunheng-commands/scripts/owner-cli.mjs`，零消失 | 发布面变化正是本版该有的那一处 |
| 重跑 | `--failed` ×2 全红 | 不是瞬时抖动，是可复现的环境缺陷 |

**判定：产物合法、跑者的 tar 有毛病。**「重跑到绿」不是修复，只是碰运气——所以本批不选它。

## 三、处置（tar 优先，内置解包器兜底，门强度不降）

1. **新增 `scripts/_lib/untar.mjs`**：`untarGz(gzBuffer, destDir)` 支持 ustar（`name`+`prefix`）、GNU 长名 `L`、PAX `x`/`g`（取 `path=`）、目录、普通文件；**逐块校验和验证**（坏块抛错）；**拒绝绝对路径与含 `..` 的条目**、跳过符号链接/硬链接并计数；**解出 0 个文件即抛错**。
2. **`scripts/pack-smoke.mjs` 接线**：`tar -xzf` 仍首选（Linux/macOS 走系统实现，零风险）；仅在它失败时 `rmSync(package/)` 清掉半成品 → 内置解包器重解同一份 tgz → **继续跑原有全部断言**（关键文件齐备 / `lib/*.js` 与真源逐一对齐 / 发布面裁剪 / 入口 apply 真跑 / frontmatter 剥离）。
3. **让兜底可被验证**：新增 `LUNHENG_PACK_SMOKE_FORCE_BUILTIN_TAR=1` 强制跳过系统 tar；新增 `tests/scripts/untar.test.mjs` 五段——PAX 长名（>100 字节，头里是截断名）/ `../` 越界 / 空条目名（**正是跑者报的坏头形态**）/ 空归档 / **端到端真 `npm pack`**。

## 四、验证（不是复述结论）

- **解包器 vs python `tarfile`**：同一份真实 `lunheng-article-pipeline-19.27.11.tgz` → 213 个文件，`onlyTar` / `onlyMine` / `hashDiff` **三空**，输出 `IDENTICAL`（逐文件 sha256 全等）。
- **强制兜底跑门 4/4**：打印 `内置解包器：213 个文件 / 0 个目录`，exit 0，后续断言全绿。
- **四门**：consistency 93 个 `.md` + 0 漂移；plugin-surface 11 通过 / 0 失败 / 0 提示；hygiene 全项通过；pack-smoke 解包 4397 KB / 213 文件。
- **全量回归**：1417 例 / 1415 pass / 0 fail / 2 既有登记 skip（较 19.27.11 增 5 例）。
- **派生面**：change-surface 2 条、bump --check 待改 0、derive-facts 三数一致。

## 五、教训（会复发的都在这）

1. **「门绿」不等于「兜底被验证过」**：本机系统 tar 正常，兜底分支永远不执行。任何「只在异常路径才跑」的代码，必须配一个强制走该路径的开关 + 端到端用例，否则它是未验证代码。
2. **先分清包坏还是环境坏，再决定修哪里**：四个独立侧面（其它 OS / 本机 / 归档完整性 / 与已发布包对照）比复述 CI 报错有用得多。
3. **rerun 是运维手段，不是修复手段**：两次同形即停，转做真修；否则下一次发版会把同一段时间再花一遍。
4. **工具坑（Windows + bash）**：heredoc 吃反斜杠（`.split('\\')` 变 `.split('\')`）；python `io.open(...,'w')` 默认把整文件写成 CRLF（门 3/4 立刻报 `[eol]`）；`import ... from 'E:/...'` 报 `ERR_UNSUPPORTED_ESM_URL_SCHEME`；PATH 里放 `tar` stub 顶不掉 `tar.exe`（PATHEXT 只认 `.exe`）——最后这条正是需要环境开关的直接原因。
5. **修门不等于放宽门**：兜底之后，断言一条没减；区别只是「从哪份字节里读出文件」。
