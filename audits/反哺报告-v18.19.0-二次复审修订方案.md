## §一、复审方法与核验协议

### 1.1 为什么换方法

首轮是「读码 + 跑门 + 对照官方包」，其结论止于**门声称能抓什么**。本轮改为**受控变异（mutation）+ 形态探测**：真的把漂移注入进去，看门红不红。理由是首轮已经证明：**门的存在 ≠ 门有效**（`e0a2f59` 与 `29dff27` 两条提交都是「缺陷逃过当时全部门，事后才补门」）。

### 1.2 核验协议（本轮实际执行的）

| 约定 | 内容 |
|---|---|
| 隔离 | **全部注入在 `$TMPDIR` 的仓库副本上做**，真实工作树零改动（复审结束时 `git status --short` 仍为空） |
| 正控 | 每类注入都配一条「门必须红」的正控（否则绿无意义——可能门整个坏了） |
| 负控 | 对怀疑的盲区，注入**同型**内容到同一门应覆盖但实际未覆盖的位置，观察是否绿 |

### 1.3 变异矩阵（14 组，完整清单见 §附录 A）

有效 13 组：**11 组门按预期红**（`[localpath]` / `[changelog]` / `[exit-code]` / `[e-family]` / `[doc-budget]` / `[syntax]` / 五语行数 等精确标签）、**3 组实证盲区**（`docs/architecture.md`、`docs/faq.md`、⑦ 对 gitignored 文件）、**1 组夹具无效**（⑧b，已更正）。

### 3.1 M 族修订项

#### M-1 发布物集 ≠ 扫描集：gitignored 文件会进 npm 包，却对 ⑦ 凭据扫描隐形（**P1**｜[仓库级]）

- **位置**：`scripts/repo-hygiene-check.mjs:68-86`（`tracked` / `untracked` / `scanSet` 三集合）、`:147`（④ 用 `git ls-files --eol`）、`:262-277`（⑦ 用 `scanned`）、⑤ 的实现；`package.json` 的 `files` 白名单
- **实测证据**（副本内，注入后未清理的是副本本身）：
  ```
  注入 skills/lunheng-article-pipeline/tmp-creds.env.bak（内为密钥形态串，本报告不复现原文）
    → ⑦ 凭据扫描：233 个文本文件 × 10 类模式，无命中        ← 扫不到
    → npm pack --dry-run --json：146 个文件，**含该 .bak**   ← 但要发布出去
  对照：git check-ignore → .gitignore:19:*.bak
  对照：注入 3 个未跟踪文件 → ⑤ 计数 234 **不变**；git add 后 → 237，并立刻报 [eol] / [utf8]
  ```
- **机制**：三个集合互不相等——
  - ① 的扫描集 = `scanSet`（`tracked ∪ 未跟踪且未被 ignore`）
  - **④ / ⑤ / ⑦ 的扫描集 = `tracked`**（实证：计数随 `git add` 变化）
  - **npm 的打包集 = `files` 白名单，按盘上文件取，不受 `.gitignore` 约束**（实证：`.bak` 被收录）
  三者之差 = 「未跟踪的普通文件」（对 ④⑤⑦ 隐形）∪「被 ignore 但在白名单目录内的文件」（对**全部**规则隐形，含 ①，因为 `--exclude-standard` 会跳过它们）
- **为什么不是理论风险**：`.gitignore` 自己列了 **5 种 `.bak` 形态**（`*.bak` / `*.bak2` / `*.bak3` / `*.bak-fix`），即本仓库的编辑流程**持续制造**这类文件；此刻仓库根就有 `SECURITY.md.bak`。而 `e0a2f59` 的提交信息已经把这类不对称讲清楚了（「npm pack 包含尚未 `git add` 的新文件」→ 所以把 ① 改成扫 `scanSet`）——**④⑤⑦ 是同一类的漏网**，属第三次出现的「修一处不修一类」。
- **修法**（三件，缺一不可）：
  1. `④` / `⑤` / `⑦` 的输入从 `tracked` 改 `scanSet`（与 ① 同源）；
  2. **新增差集门**（位置紧接 ⑥ 之后）：以 `packFiles` 为期望集，要求「pack 清单里每个文本文件都被 ④⑤⑦ 覆盖」，**差集非空即报**（把「扫描集 ⊇ 打包集」变成不变量，而不是靠人记得）；
  3. `package.json` 的 `files` 加负向项 `!**/*.bak*`、`!**/*.tgz`（`files` 的负向条目可显式排除；`.gitignore` 挡不住 pack——见 `pack-smoke.mjs:271` 已记录同类实测）。
- **验收判据**：
  ```
  node scripts/repo-hygiene-check.mjs                     → exit 0，且 ④⑤⑦ 的计数 ≥ ⑥ 的 pack 文件数
  注入 skills/**/x.bak（含密钥形态串）                     → ⑦ 必红
  注入未跟踪的 CRLF / 非 UTF-8 文件                        → ④ / ⑤ 必红
  差集门自证：临时从扫描集排除一个 pack 内文件              → 差集门必红
  ```
- **回滚**：`git checkout -- scripts/repo-hygiene-check.mjs package.json`（+ 删除新增的差集门代码块）。

#### M-2 npm 12 形态变更引发的三道连锁：⑥ 红 / ⑦b 真空合格 / 3 条自证台静默失效（**P1**｜[仓库级]）

- **位置**：`scripts/repo-hygiene-check.mjs:180`（`npm pack --dry-run --json`）、`:187-190`（**数组假设**）、`:241`（解析失败 → `fail('pack')`）、`:181-182`（`packFiles` 初值 `[]`，被 ⑦b 消费）；`tests/docs-facts.test.mjs:468`、`tests/local-path-scan.test.mjs:73`、`tests/pack-negative.test.mjs:64`
- **实测证据**（**真实仓库 HEAD，未做任何改动**）：
  ```
  node -v → v26.7.0   npm -v → 12.0.2
  npm pack --dry-run --json 的首字符 → {           （npm ≤11 为 [）
  node scripts/repo-hygiene-check.mjs → exit 1
    ✗ 未通过：1 项
      - [pack] npm pack --json 解析失败：Unexpected non-whitespace character after JSON at position 19635 (line 727 column 6)
    而同一次运行里：
      ✓ ⑦b 本机绝对路径：发布物 0 处（须为 0）／非随包树棘轮 22/22 …        ← 空集上真空通过
  ```
  代码根因：`JSON.parse(pack.stdout.slice(pack.stdout.indexOf('[')))` + `arr[0]?.files`。对象形态下 `indexOf('[')` 落在 `"files": [` 处，切出 `[...]  } }` → 解析必抛。
- **两个更坏的副作用**：
  - **⑦b 真空合格**：解析抛错 → `packFiles` 留空 → 「发布物硬零」在空集上成立并打印**合格字样**。这是「失败路径输出合格」——与首轮 D-2「凭据扫描照绿」同构，而 ⑦b 本是为防 D-2 复发而加的。
  - **3 条反假绿自证静默跳过**：
    ```js
    try { packed = JSON.parse(execSync('npm pack --dry-run --json'))[0].files.map((f) => f.path) }
    catch { return }   // 注释自称「跳过而非假绿」
    ```
    对象形态 → `[0]` 为 `undefined` → **TypeError 被这个「npm 不可用」的 catch 吞掉** → 用例 `return` = **通过**。它自带的反恒真防线 `assert.ok(files.length > 100, '派生失败会让本断言恒真')` **永不执行**。实测：用例报 `✔`、`pass 5 / fail 0`；当日全量套件 **`skipped 0`**（若真跳过会记 skip）。
- **环境分叉**：CI 固定 Node 22.19（npm 10.9.3）/ 24（npm 11）→ 数组形态 → 全绿；而 `package.json` 的 `engines` 为 `^22.19.0 || >=24.0.0`，**声明支持 Node 26**（= npm 12）。
- **升级路径**：若 CI 升到 Node 26，同一改动会让 CI 也失去这 3 条自证并让 ⑦b 真空合格 → **届时应升 P0**。故本条宜尽快修。
- **修法**（四件）：
  1. 新建 `scripts/_lib/pack-manifest.mjs`：`JSON.parse(stdout)` → `Array.isArray(raw) ? raw : Object.values(raw)` → `[0].files`；**形状不认识就抛错并指名**（照 `_lib/exit-namespace.mjs` 的「形状变了会抛错而非静默通过」正例）；
  2. ⑥ 与 3 个测试**共用**该解析器（消灭 5 份就地实现）；
  3. **三态判定**：解析失败 → `packFiles = null` → ⑦b 记 `UNKNOWN`，**不得打印合格字样**（UNKNOWN 不计入合格）；
  4. 测试的「依赖不可用」catch **按错误类型分流**：只把 `ENOENT` / `EPERM`（沙箱禁子进程）当环境、记 `t.skip('理由')`；`TypeError` 一律照抛（不得被吞）。
- **验收判据**：
  ```
  node scripts/repo-hygiene-check.mjs                       → 本机（npm 12）exit 0
  ```

#### M-5 `writeWithSafety` 的 `renameSync` 无重试（**P2**｜[机制]）

- **位置**：`skills/lunheng-article-pipeline/scripts/_lib/destructive-write.mjs:171`
- **实测证据**：当日全量跑出现一次
  ```
  Error: EPERM: operation not permitted, rename '<tmp>/.cpy…lunheng-tmp' -> '<tmp>/a.md'
      at writeWithSafety (…/destructive-write.mjs:171)
      at TestContext.<anonymous> (…/tests/scripts.test.mjs:2808)
  ```
  重跑（前台，326 用例）**未复现** → 确认是 Windows 瞬时抖动，非稳定红。
- **数据安全面（本轮已核实，结论是安全的）**：该函数为 `temp 写入 + rename`，失败时 `catch { unlinkSync(tmp); throw e }` → **目标文件保持原状、temp 被清掉、第 ② 步的 `.bak` 仍在、错误向外抛**。故这是一个**响亮的失败 + 可恢复**，不是静默损坏 —— 严重度维持 P2（不升 P1）。
- **修法**：`renameSync` 失败且 `errno === -4048` / `EPERM` 时**有界重试**（3 次，退避 10 / 50 / 200 ms），注释写明「Windows 上 `MoveFileEx` 可瞬时 EPERM（杀软 / 索引器持有句柄）」；测试侧该用例的断言消息带上重试次数，避免下次再当新问题查一遍。
- **验收判据**：把重试临时关掉并施加「外部持句柄」的模拟（或用 `chmod` / 打开句柄的方式构造）→ 必红；开启后稳定绿。
- **回滚**：`git checkout -- skills/lunheng-article-pipeline/scripts/_lib/destructive-write.mjs`。

### 3.2 O 族优化方向（本轮最有价值的部分）

#### O-1 建立「规则 ↔ 反向自证」双向账（**元门**）——本轮四条发现能长期存在的根本原因

现状：**没有任何门能回答「这 37 条规则里哪几条从未被证明会红过」**。门的增长模式是「出事 → 补一条」（`e0a2f59` 补 scanSet、`29dff27` 补 `⑬` 都是事后），缺「同类穷举 + 自证」这一步。`tests/gate-hardening.test.mjs` 只覆盖 4 条历史发现（L-53/L-46/L-35/L-47），不是穷举账。
**建议**：为每条规则登记 `id + 反向自证用例名 + 最后拦截日期`，并让 CI 跑一个**变异矩阵 job**（本报告 §附录 A 的 14 组可直接作为起点）；`最后拦截日期` 长期为空的规则进入评审（是规则无效还是规则多余）。

#### O-2 三态判定：`PASS` / `FAIL` / `UNKNOWN`

任何以外部命令输出为输入的规则，输入未就绪时一律 `UNKNOWN`，且 **UNKNOWN 不计入合格**。这一条能一次性消灭「失败路径输出合格字样」这一类（`⑦b` 现为反例；`⑧b` 的解析器「形状变了会抛错」是正例，可直接复用其写法）。

#### O-3 解析器单点化 + 静态禁止就地解析

同一事实的解析只允许一处实现。首轮 A-1/A-2 是「L 编号正则」的双份；本轮 M-2 是「`npm pack --json` 形状」的**五份**（1 门 + 4 消费点）。**建议加一条静态规则**：门与测试里禁止出现 `JSON.parse(execSync('npm pack…'))` 形态，必须 import `_lib/pack-manifest.mjs`。

#### O-4 把「扫描集 = 打包集」写成不变量（并写进 `CONTRIBUTING`）

不只是补 M-1 的差集门，而是确立口径：**凡「发布物面」的规则，输入必须是 pack 清单，不是 git 索引**。`CONTRIBUTING.md` 的「升级流程」节加一句即可（那里已经有「发布面裁剪是机械门，不是自觉」的同类表述）。

#### O-5 测试的跳过必须可见

`catch { return }` 改 `t.skip('理由')`（`node:test` 会记 `skip`；当前这种写法记 **pass**）；并禁止在「依赖不可用」的 catch 里吞掉**断言输入构造错误**（按 errno / 错误类型分流，见 M-2 修法 4）。

#### O-6 环境矩阵要跟上 `engines` 声明

`engines` 声明 `^22.19.0 || >=24.0.0`（含 Node 26），而 CI 只跑 22.19（npm 10.9.3）与 24（npm 11）→ **声明宽于证据**，且差额恰好是本次翻车的那一档。建议二选一：① 收紧 `engines` 到实测范围；② 在 CI 加一个 Node 26 leg。无论哪条，把「**node / npm 大版本升级**」列入门失效高危事件（本仓已有 3 处规则依赖 npm 的输出形态）。

#### O-7 规则数量治理 + 常驻集瘦身排期

- 规则数：24 类主规则 + 5 子规则 + 13 项 hygiene，而 `E-15` 已把「规则数」**刻意降级为手工同步**（门无覆盖）。建议规则数**从规则清单派生**（一条正则即可），并给每条规则登记**拥有者 + 耗时 + 最后拦截日期**。
- 常驻集：本轮已把 SKILL.md 从 38,539 B 降到 **36,424 B**（+2.1 KB 余量）——方向正确，但 AGENTS.md 余 **41 B**、pipeline-readme 余 **204 B**，棘轮又贴墙。建议把「SKILL.md → 20 KB」（文件里自己写着的长期目标）**排期**，而不是每次被上限逼出来的临时动作。

```js
import { readFileSync, writeFileSync, appendFileSync, rmSync } from 'node:fs'
import { spawnSync } from 'node:child_process'
import { join } from 'node:path'
const R = process.argv[2]
const HYG = ['scripts/repo-hygiene-check.mjs']
const CC  = ['skills/lunheng-article-pipeline/scripts/consistency-check.mjs']
const M = [
  { n: 3, file: 'README.md', kind: 'replace', find: 'lunheng_handoff_check', to: 'lunheng_X',
    gate: ['--test', 'tests/docs-facts.test.mjs'], expect: 'RED' },
  { n: 9, file: 'skills/lunheng-article-pipeline/references/_shared/期刊数据库.md', kind: 'replace',
    find: 'CSSCI/北大核心，28 个', to: 'CSSCI/北大核心，27 个', gate: HYG, expect: 'RED' },
  { n: 14, file: 'skills/lunheng-article-pipeline/tmp-cred-probe.bak', kind: 'create',
    text: 'token=<密钥形态串（勿写真实值）>\n', gate: HYG, expect: 'RED' },
]
for (const m of M) {
  const abs = join(R, m.file); const bak = m.kind === 'create' ? null : readFileSync(abs, 'utf8')
  if (m.kind === 'create') writeFileSync(abs, m.text)
  else writeFileSync(abs, bak.replace(m.find, m.to))
  const r = spawnSync(process.execPath, m.gate, { cwd: R, encoding: 'utf8', timeout: 300000 })
  const tags = ((r.stdout || '') + (r.stderr || '')).split('\n').filter((l) => /^\s+- \[/.test(l))
  console.log(`[${m.n}] exit=${r.status}`, tags.map((t) => t.trim().slice(0, 90)).join(' ⏐ '))
  if (m.kind === 'create') rmSync(abs); else writeFileSync(abs, bak)
}
```
