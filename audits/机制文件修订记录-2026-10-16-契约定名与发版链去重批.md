## 一、⭐ ⑥ 的**定性被推翻**：不是「超时配置错」，是「同 commit 双 ci 并发争用」

### 1.1 我原先的说法（错）与其更正

批次五的记录把它写成「**既有 CI flaky**：`loader-smoke` 的『真实 Loader 冒烟』超时」。**读全日志后推翻了**——真正的失败步骤不是冒烟：

```
✓ pack   ✓ install   ✓ dump-config   ✓ headless-smoke      ← 装载四步全过
✗ uninstall                                                 ← 挂住的是这一步
The operation was aborted  →  FAIL: uninstall failed
```

时间线：`install` 于 `03:20:48` 完成，失败报于 `03:28:03` —— **正好 7m15s ≈ `DSH_PLUGIN_DEV_TIMEOUT`（420s）**。即 **`uninstall` 子步骤挂住不退出**（它内部的 pnpm 部分只用 2s 就 `Done`，随后进程不退出 → 撞安装/打包超时被 abort）。报错里那句「raise --timeout or --smoke-timeout」是 CLI 的**通用提示**，**不是**超时配置不足的诊断。

### 1.2 机制：**发版流程本身制造了并发**

| `ci` 触发 | `loader-smoke` | 耗时 |
|---|---|---|
| **master** 推（v19.6.7 / 19.6.8 / 19.7.0 / 19.7.0续） | **success** ×4 | ≈3.5 min |
| **tag** 推（v19.6.8 / v19.7.0） | **failure** ×2 | ≈8.5 min |

根因链条：

1. 发版流程要求「**推 master 并 推 tag**」（两处都要做，否则 GitHub 文件视图停旧版）⇒ 两者**指向同一 commit**；
2. `ci.yml` 的并发组是 `group: ci-${{ github.ref }}` ⇒ master 与 tag 是**不同 ref ⇒ 不同组 ⇒ 两个 run 并发**；
3. 两个 run 各自跑重量级安装（pnpm 解析 **301 个包**）→ **互相争用** → 其中一个的 `uninstall` 超过 420s 被 abort；
4. 于是**同 commit 的两个 `ci`，一个绿一个红**（实测 v19.6.8 / v19.7.0 均如此）；v19.6.7 只推一处即两处皆绿。

### 1.3 修法：**让 `ci` 不接 `v*` tag**（去重，且不留覆盖缺口）

```yaml
on:
  push:
    branches: ['**']
    tags-ignore: ['v*']
  pull_request:
```

**为什么这是安全的（不是放宽判据）**：`publish.yml` 的 **`gates` 作业**在 `v*` tag 上覆盖**同样四道门 + 回归**，而且**更强**——
- 门 2 带 `STRICT_WARN: '1'`（warn 也阻塞；`ci.yml` 不带）；
- 测试由 **`no-write-check` 包裹**（=「无改写」守卫，`ci.yml` 的 `script-tests` 做不到）。

⇒ `v*` tag 上再跑一遍 `ci` 是**纯重复**；删掉它**不减少任何覆盖**，只消除争用。**非 `v*` 的 tag 仍会触发 `ci`**（`tags-ignore` 只排除 `v*`）⇒ **不留覆盖缺口**。

**为什么不选「抬超时」**：`uninstall` 是**挂住**不是**慢**（其 pnpm 部分 2s 完成），抬 `--timeout` 只会**更慢地红**。
**为什么不选「把 uninstall 判负吞掉」**：那是**放宽判据**（会掩盖「卸载不干净」这一真问题），本仓明文禁止为让门变绿而放宽判据。

**本批可验的一半 / 不可验的一半（如实）**：master 推之后应**只触发一个** `ci` run——**当场可验**（见 §四）；「`v*` tag 不再触发 `ci`」这一半**只能在下次发版时验证**（本地无法在不真正推 `v*` tag 的情况下验，而推 `v*` tag 就是发布）。

## 二、① 契约定名：04 卡 §13 新增「标题可检索性契约」

- **病灶（验证记录 V6c）**：09 卡 M3 的数据源列点名「大纲『识别策略与反事实』段」，而真实项目里该内容叫「§6 分析框架与因果识别策略」/「§6.2 因果识别策略」⇒ **按字面找不到节**，与批次一 F1（「方法卡」幽灵制品）同族但性质不同（F1 是制品不存在，本条是**节名不匹配**）⇒ **假 P1**。
- **批次五已做的**：**消费面**容错（09 卡 M3 数据源列 + 05 卡 §4①，按内容定位 + 「找不到节 ≠ 缺声明」护栏）。
- **本批补的（投到源头）**：**定义面**——`04-分析-analyst.md` §13 新增「**标题可检索性契约**」：

  > 本节点的**标题用词不限**（实测项目用「§6 分析框架与因果识别策略」「§6.2 因果识别策略」等），但**须含可检索词**——「识别策略」/「因果识别」/「反事实」三者之一。

  并在同节 M3 判别行补「**按字面找不到节 ≠ 缺声明**，须按内容再定位」。

> **为什么用「须含可检索词」而不是「定一个固定标题名」**：定死标题名会**立刻与全部存量项目冲突**（存量标题各不相同且无门可核，不会自动对齐）；而「须含可检索词」是**最小可检索性契约**——它让**未来的**大纲标题至少能被搜到，**不追溯存量**，且不与既有标题冲突。**边界（如实）**：本契约**无门可核**（识别策略的标题形态属语义判断，加正则门会「见词即合规」= 假绿）；故它是**约定**，靠 T4 照写 + T9-m 按内容定位兜底。
