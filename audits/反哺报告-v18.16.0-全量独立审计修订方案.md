### 2.3 为什么 9 个版本全绿：三条机制性盲区（**这是本报告最重要的一节**）

1. **扫描面盲区**：`consistency-check` 的 `ROOT = skills/lunheng-article-pipeline`，**`lib/**` 不在其内**（`lib/index.js:222` 自己记着这条）；而 `lib/**` 恰是「工具数 / 命令数 / Config 键」的唯一真源 → 对外声明的三处计数漂移，**9 个版本无门可拦**。
2. **镜像面盲区**：规则 ㉑ 只镜像五语 README 的**结构**（表格行数 / H2 数 / 语言切换行），**不比对行内事实** → 五语「两个只读工具」在结构上完全对称，门照绿。
3. **判据面盲区**：规则 ⑧ 的退出码契约表只做**字面量静态解析**（`repo-hygiene-check.mjs` ⑧ 自报「23/23 已核」），对**动态 exit**（三元表达式）看不见 → `methodology-check` 的真实 `exit 2` 至今不在表内。

**根因一句话**：**「修复只做一半」**——注释化修复（把「已修」写进注释或版本注记）后，**同义文本在别处继续存活**，而对外与机械门够不到的那一半没人回头改。v18.6.0 修了 `SKILL.md` 的「漏列第三个工具」却没修五语 README / `SECURITY.md` / `installation.md` 是同一个模式；L-33 在一处已补门、另一处仍写「尚未机械化」也是同一个模式。**故本方案的第三批专门处理「让『已修』可机检」**，否则同一批矛盾会在下一次全量审计里以新编号再次出现。
