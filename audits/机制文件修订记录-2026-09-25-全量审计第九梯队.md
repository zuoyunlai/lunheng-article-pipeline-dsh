## 一、`apply-diff` / `apply-revision-cycle`：三条静默数据丢失（L-57 / L-58 / L-59）

三项同属一个主题：**脚本在「用户看不出」的情况下破坏了正文，或吞掉了本应应用的修订**，且都报 `ok: true`。

### L-57 正文里合法的行尾括号被当元注记删除

- **原判定**：`apply-diff.mjs:87-94` 把 `文字（对应的系数）` 截成 `文字`，落盘后 `ok: true`、`exit 0`。
- **实测复现**（修前）：输入 `（对应的系数）` 形态的行 → 输出缺尾括号，无任何告警。
- **根因**：剥离判据只用了「行尾有一个 ≥2 字符的括号」这一形状，而正文里**括号本身就是合法内容**
  （数学系数、单位、并列术语、英文缩注都会用）。
- **修法**：把判据收紧为「括号内**含 ≥2 个 ASCII 字母/数字**」才算元注记（`META_TAIL`）：
  `/\s*[（(](?=[^）)]*[0-9A-Za-z][^）)]*[0-9A-Za-z])[^）)]{2,60}[）)]\s*$/u`。
  真正的元注记形如 `（按 G14 报告 C-01）` → 仍剥离，并在 JSON 里留 `stripped_meta` 痕迹（可审计）。
- **验证**：`tests/batch12-audit-tables.test.mjs` 两条用例——① `文字（对应的系数）` 必须**原样保留**；
  ② `（按 G14 报告 C-01）` 仍被剥离**且留痕**。

### L-58 多行「现况」的续行被静默丢弃 → 半截替换仍报 ok

- **原判定**：`apply-diff.mjs:144-162,240` 只认标签行，续行直接丢弃，`ok: true` + hint「全部条目已机械应用」。
- **实测复现**（修前）：清单写
  ```
  [Diff 1]
  现况：第一行
  第二行（本应属于现况）
  修改：新内容
  ```
  → 只替换「第一行」，正文残留旧句，`applied=1`、`ok: true`。
- **修法**：新增 `droppedLines` / `unparsedHeads` 两个数组；`ok` 的判据从「有应用条目」改为
  「有应用条目 **且** `droppedLines.length === 0`」；JSON 增 `dropped_count` / `dropped_detail` / `unrecognized_head_lines`，stderr 逐行点名。
- **验证**：两条用例——丢续行时必须 `ok:false` + `exit 1` + **点名行号**；规规矩矩的清单仍 `ok:true` / `exit 0`（不误伤）。

### L-59 清单里的 `[L01]` 引用行被当条目头 → 真 diff 被吞

- **原判定**：`apply-diff.mjs:30,145` 的条目头正则过宽，把 `[L01] 备注：…` 当条目头；而头注释宣称支持的 `[C-n]` 形态**不识别**。
- **实测复现**（修前）：清单含一行 `[L01] 备注：…` → `applied=0`、`exit 1`；真 diff **整条没应用**。
- **修法**：条目头限定为**四族**`[Diff N]` / `[P0-N]` / `[P1-N]` / `[C-N]`（`HEAD_RE` + `headId()`）；
  非四族的方括号行不再是条目头，且**在 stderr 逐条点名**（不再只说「未解析出任何条目」）。
- **验证**：两条用例——`[L01]` 行不得吞掉真 diff（必须 `applied=1`）；`[1]` 这类非族头 → 0 条并点名。

## 二、`apply-revision-cycle` / `apply-compression-cycle`：字数口径（L-56）

- **原判定**：① `measure()` 在**应用 diff 之前**测 `post`，而 `:76` 就用该值判 G5、`:85` 才应用 diff、**不重测**；
  ② `:113-126` 把它写进 `修订说明-vN.md` 的「脚本实测」列（该表是修订说明的唯一数据源）。
  实测：v2 实际 **300** 汉字，脚本报 **754**（= 改前值）。
- **实测复现**（修前）：改前 754 / 改后 300 的稿件 → 「脚本实测」写 **754**，`delta = 0`。
- **修法**：
  1. `measure()` 移到步骤 ③（应用 diff）**之后**重算；步骤序现为 ①②③④⑤⑥⑦；
  2. body 口径改与 `count-chars` **同源**：`bodyStartAfterAbstract` + `firstEndnoteIndex(text, from)` + `maskFences`；
  3. 顺带修同族缺陷——`--diff-list` 的路径解析 `join(process.cwd(), v)` 在绝对路径下产生
     `C:\repo\C:\Users\…\list.md`，改为 `resolve()`；
  4. 目标字数解析 `\d{4,5}` 让 `300 字` / `12,000 字` / `1.2 万 字` **全部返回 null → G5 整段静默跳过且 exit 0**
     （主控会以为「已核」）→ 抽 `_lib/target-chars.mjs` 的 `parseTargetChars()`，支持 3–5 位 / 千分位 / 万·千·k，
     范围为 `MIN_TARGET=300` / `MAX_TARGET=200000`；解析不到时**显式 stderr 告警**。
- **验证**：`tests/batch12-audit-tables.test.mjs` 的 L-56 两条用例 + 1 条口径守卫。
  实测：`prevBody 353 / nextBody 253 / delta -100`（清单恰删 100 字），且 `nextBody` 与 `count-chars` 的
  `hanChars` **逐字同值**；3 位目标 `300` 解析成功、G5 真的判定（报「低于阻塞线 17 字」）。

> **口径守卫为什么必须存在**：复核 L-56 时我曾据「`count-chars` 头注释说『不含题名』」推断出一个**假缺陷**
> （以为 body 含题名），根因是**没有一条用可区分字符写成的边界断言**，只能靠「题名字数 + 切片长度」心算 → 算错。
> 本次用「题名 3 / 摘要正文 50 / 正文节标题 3 / 正文 300 / 文末 20」的夹具把三个区间各自钉死：
> `body = 353 = 50 + 3 + 300`（题名不计）、`full = 382`、`full − body = 29 = 题名 3 + 摘要标题 2 + 文末标题 4 + 文末 20`。
> 精确边界同时写死进 `sections.mjs` 与 `count-chars.mjs` 的注释，防二次误判。

## 五、如实登记的「保留代价」（L-16）

### L-16 「脚本计数漂移」规则对散文误报

- **原判定**：该规则在审计报告撰写过程中误报 **6 次** P1（3 次初稿 + 3 次补写），每次改写措辞后即复绿。
- **根因**（本次确认，非推断）：规则 ⑩b 的触发是 `l.matchAll(/(\d+)\s*项/g)`——**任何**「N 项」都会进入判定，
  随后靠一串限定词（`SUBSET_POST` / `TOTAL_TAIL` / `MEch` / 分项主语…）短路。**散文里出现「N 项」而限定词判不出主语时，
  规则按 ⑥/⑦ 分支落判**——这正是它的设计：宁可误报也不放过真漂移。
- **为什么不修**：放宽则「脚本计数漂移」这条门失去意义（本包历史上正是靠这类机械门防漂移）；
  收紧需要**语义理解**（作者说的是哪一类计数），超出正则能力。**这是刻意的代价，不是疏忽**。
- **处置**：保持现状 + 本记录登记。豁免方式已有（`HIST_QUOTE`：显式标注为旧值的行豁免），
  写审计报告时用该形态即可。
