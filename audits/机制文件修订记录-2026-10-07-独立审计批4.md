## 1. 真问题 A（新发现，比原审计项更严重）：审计档被**日期后缀**抢走

**实测病灶**：`model-routing.mjs` 输出的三档主选曾是
`检索 deepseek-flash` / **`强档 claude-haiku-4-5`** / **`审计档 claude-haiku-4-5`** ——
**审计档的需求原文是「顶配防漏判（严格审计 / 不放水）」，策略明写「不得为省钱降档」**，却推了一个
**小参数快模型 haiku**，而 `claude-opus-4-8` 落到兜底。

**根因（已定位到行）**：`versionOf` 的第三条兜底 `/(\d+(?:\.\d+)?)\s*$/` 对 `claude-haiku-4-5-20251001`
抓到的是**日期后缀 `20251001`** → `version = 20251001`；而 `scoreOf` 里有 `s += 0.3 * c.version`
→ 该项贡献 **+6,075,300 分**，把推理（权重 3）与上下文（权重 3）**全部淹没**。
同族 id `deepseek-v4-pro-260425`（6 位 YYMMDD）同样得 `260425`。
⇒ **这不是「启发式不完美」，是排序被一个与模型能力无关的日期字段决定。**

**修法（两段 + 一道保险）**
1. `versionOf` **先剥日期**（8 位 YYYYMMDD、6 位 YYMMDD），再依次试 `M<num>` / `v<num>` / 尾部 ≤3 位数字 / `-<1~2 位>-`；
2. `scoreOf` 里**夹取** `Math.min(c.version, 10)`——即便将来出现没预料到的 id 形态，版本项也只能是
   **温和 tie-break**（≤3 分，与 reasoning 权重同量级），**不可能再压过能力维度**。

**真机验证（修前 → 修后）**：强档 `haiku-4-5` → **`claude-opus-4-8`**；审计档 `haiku-4-5` → **`claude-opus-4-8`**；
检索档保持 `deepseek-flash`（正确，需求就是"便宜快"）。
**判据（本批最有价值的一条）：排序项必须与它声称衡量的东西相关——一个能被 id 里任意数字串放大的项，不是「版本偏好」而是噪声。**

## 2. 真问题 B：把「每档 ≥2 候选」从**无人校验的口号**变成**机器可读的可满足性**

**审计 P1-5 的成立部分**：`模型路由.md` 要求策略 ②/③ 的前置 =「每档 ≥2 个可用候选（跨平台至少一跳）」，**无脚本校验**。
**修法（刻意不是"再加一条规则"）**：`model-routing.mjs` 新增输出 **`strategyVerdict`**——从**实测候选池**逐档导出
`candidateCount` / `distinctProviders`，据此判定三条策略**是否可满足**，并给出**不可满足的具体原因**：

| 策略 | 实测判定（本机） | 依据 |
|---|---|---|
| ① 继承会话模型 | ✅ 恒可 | 零配置可用 |
| ② 同平台分档 | ✅ **可满足** | 每档实测 **42** 个候选（≥2） |
| ③ 跨平台分档 | ❌ **不可满足** | 仅 1 个 provider；**且 `LUNHENG_*_PROVIDER/_MODEL` 一对变量只能表达一个 provider+model → 「跨平台一跳」在配置面根本无法表达** |

**这条同时更正了我审计时的措辞**：我写的是「前置不可满足」；实测是**策略 ② 完全可满足**（42 候选），
只有「跨平台」这一跳不可满足——**而且是配置面表达力的问题，不是候选不足的问题**。
**边界（如实）**：`strategyVerdict` **只报可满足性、不替主人选策略、不改宿主配置**。
