## 二、根因：**决定的「技术前提」变了，结论没跟着变**

- **旧链条（当时为真）**：`npm publish` 走 OIDC 不需要凭据 → 但 `npm dist-tag add` **仍需写鉴权** → 本仓 `NPM_TOKEN` 取到空值 → **结论**「CI 永远动不了 `latest`」→ **政策**：发版后由维护者手工补打（`SECURITY.md` 记 2026-09-29 主人决定；`dist-tag-check.mjs` 头注释同步）。
- **新事实（2026-09-30，即该决定次日）**：npm 为 trusted publishing 新增 **opt-in 的 dist-tag 权限**（`Allow npm dist-tag`，与「直接 publish」**相互独立**、**默认关闭**），dist-tag 写入不再需要长期凭据；CLI 前提 **npm ≥ 11.21.0**。
  依据：[GitHub Changelog](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/)｜[npm Docs · Adding dist-tags](https://docs.npmjs.com/adding-dist-tags-to-packages/)｜[npm Docs · Trusted publishing](https://docs.npmjs.com/trusted-publishers/)。
- **为什么这不是「推翻主人 2026-09-29 的决定」**：那次决定的**理由**是「不引入需 90 天轮换的长期凭据」——**OIDC 恰好不需要它**。故自动前移与该决定的**意图一致**；变的只是**当时为真、现在已假**的技术前提。
  > **判据（本仓反复出现的一类）**：**记录「结论」时必须同时记录它的前提**——只记结论的文档，会在前提消失后继续被当事实执行（本次即：一条**已被上游功能作废**的限制，被当成政策执行了 3 天）。

## 三、改了什么（四处 + 一条回归网）

1. **`.github/workflows/publish.yml`** — dist-tag 步重写为「**OIDC 优先 / token 兜底 / 失败不阻断 / 不回退**」：
   - 真去写：先 `npm dist-tag add "$PKG@$VER" latest`（**不要求** `NPM_TOKEN` 非空）；
   - CLI 前提：该步**显式安装 pinned `npm@11.21.0`**（Node 24 自带 11.19.0 不满足）——**只在该步**，发布仍用 runner 自带 npm（发布环境可复现性不变）；
   - 失败语义：无凭据 → `::warning::` + 两条闭合路径、**不 exit 1**（发布不可逆，tag 前移失败不该判红）；token **存在却失效**（E401）→ `::error::` + exit 1（那是真问题）；
   - **不回退**：仅当「本次版本 == registry 最新版」才前移（补推历史 tag 的 run 不会把 tag 拉回旧版）；
   - 顺带修一处**旧缺陷**：setup-node 写的 `.npmrc` 读 `NODE_AUTH_TOKEN`，旧版只注入 `NPM_TOKEN` → token 分支**从未真正生效**，现两者都注入。
2. **`SECURITY.md`** — 标注 2026-09-29 决定的**前提已变**（原文留痕）、给 npm 侧一次性动作（勾选 `Allow npm dist-tag`）与两个前提、`NPM_TOKEN` **降级为兜底**、更新故障排查与完整发布链。
3. **`references/maintainers.md` §四** — 发版后**先看该次 publish 运行的 dist-tag 步日志**；人工命令降为**兜底路径**（`--registry` 与顺序两条坑**仍对兜底适用**，故保留）+ 核验 tips 补第三次缓存复现。
4. **`scripts/dist-tag-check.mjs`** — 头注释把「CI 永远动不了 latest」标为**已过期**；本脚本定位收窄为「独立只读复核」（**仍不接进 CI**，理由不变：发布链已自己前移，再挂一道只会制造习以为常的红/绿）。

## 七、**v18.62.9 续批：首跑实测抓出 v18.62.8 的「自我否定守卫」**（主机 CI 日志为证）

**现象（v18.62.8 的 publish run `37005938621`，dist-tag 步原始输出）**：

```text
--- 发布后 dist-tags（前） ---
{ "latest": "18.62.7", "dsh": "18.62.7" }
本次版本=18.62.8 ｜ registry 最新=18.62.7
##[notice]本次 18.62.8 ≠ registry 最新 18.62.7（补推历史 tag 的 run？）→ **不动** latest，避免把 dist-tag 拉回旧版。
```

→ 该 run 的 `dsh` 正确到 18.62.8（`npm publish --tag dsh`），但 **`latest` 仍停在 18.62.7**（注册表 API 实测）。即：**守卫在唯一需要它的场景下拒绝工作**。

**根因**：判别式写成 `NEWEST="$(npm view "$PKG" version)"` —— `npm view <pkg> version` **解析的是 `latest` 标签指向的版本**，而 `latest` 正是坏掉的那个。**用被监控对象当基准**，于是「latest 落后」必然被判成「本次是历史 tag」→ 直接 `exit 0`。

**判据（可迁移，值得单列）**：
> **「不回退」的参照物必须是「版本序」，不能是「某个标签」**。更一般地：**守卫的参照量不能取自它要修复的状态**（同型：用 `latest` 判 `latest`、用当前配置判当前配置是否需迁移）。
> 而这条缺陷的**失败模式与它要防的缺陷外观相同**（都是「dist-tag 没动」）→ **只有真跑一次才有信号**。这正是本仓「发版后必须实测、不得只信脚本自述」的又一例证。

**修法**：判据改为「**是否存在严格更新的版本**」——

```bash
NEWER="$(npm view "$PKG@>$VER" version 2>/dev/null | tr -d '[:space:]' | tail -n1 || true)"
if [ -n "$NEWER" ]; then ... exit 0; fi   # 本次是历史 tag → 不动 dist-tag
```

- `@>$VER` 无匹配时 npm 报 **E404**（本机实测：`@>18.62.8` → E404；`@>18.62.7` → 18.62.8）→ 必须 `|| true` 兜住 `bash -e`，否则整步被 abort。
- `references/maintainers.md` §四 判据句同步更正（并保留缺陷实例）。
- 回归网加强：同一条用例新增**反向断言**（判据不得退回 `npm view "$PKG" version` 形态）+ 正向断言改为匹配 `@>$VER`。

**状态**：`latest` 在 v18.62.9 发布后需前移（若 npm 侧 OIDC 权限仍未开启，则**仍走人工兜底**——见 §四）。
