## 二、关键工程决策（可审计）

1. **H2 标记的形状选择**：元素 = `createUserMessage()` 产物（`{role:'user', content:[{type:'text',text}], source:{kind:'lunheng-article-pipeline'}, id: randomUUID()}`）。这与宿主 `@deepseek-ai/dsh-llm` 的实现形态一致；缺少 `id` 会被 `dsh-agent` 的 `Inbox.validate` 判重失败（已验证：`Inbox.js:177-182` 检查每个 candidate 消息的 id 唯一性）。`randomUUID` 来自 `node:crypto` 内置，零依赖。**v18.76.x 收口**：DSH 0.2.x 升级到会话格式 v4 后，`source.kind` 必须为生产者自有名（不允许再套 `{kind:'plugin', plugin:'…'}` 包装，否则整轮被 `format v4 message requires a producer-owned source kind` 拒掉）。本插件改用纯生产者名 `kind:'lunheng-article-pipeline'`，对应测试断言与本条交付说明同步更新。
2. **标记的「命中/异常」触发**：仅当 `aggReplacements > 0 || skippedTooLarge > 0 || deduped.length > 0 || !!dicts?.missing?.length` 时才注入 additionalContexts，避免每次 material 调用都吃 token。`ethicsSanitized` 结构化字段始终留在返回值（同进程监听器可读），但**永不**作为消费方契约。
3. **H7 删除 vs 保留**：选删除。原监听器每次请求都空转返回 `next()` 的结果（行为等价于"不注册"），删除后无副作用。保留需要先做真宿主探针确认可用判别键（`agent/request` 派发形态目前唯一信息是 scope 与 `{turn, step, signal}`，无 toolName）。
4. **产物探针的解析策略**：pnpm 命名 `+<pkg>_<hash>` 无 `@version`、传递依赖只在兄弟节点——故 resolver 必须「遍历所有 `@deepseek-ai+` store 目录 + 检查兄弟」；不能假设 `node_modules/@deepseek-ai/<pkg>`（如 `dsh-system-prompt` 不被根软链）。
5. **STRICT_WARN=1 在 ci.yml 启用**：本地实测 0 warn（11 通过 / 0 失败 / 0 提示），故本项改动零风险。`plugin-surface-check.mjs:348` 自述「CI 与发布门统一打开」原为承诺、现已对齐实现。
6. **规则 ㉚ 的设计取舍**：先剥注释（块 `/* */` 与行内 `//` 到行尾），再看剩余代码里有没有 == `pkgVer` 的 semver —— 剥离方向只能制造假阴性、不会制造假阳性。本仓注释惯例正是引用当前版本号（属"留痕"），故必须剥。已知边界：`Config` 的 `why` 字段是字符串字面量（非注释）——若其中含当前版本字面量（v18.76.0）则被标记。本批已就地改成"本批修复" + 指向 CHANGELOG。
7. **本地路径棘轮**：报告与核实报告头各 1 处 `E:\HERNESS\...`（"审计对象" / "核实对象"表）按既定的"审计范围界定 = 报告结论前提"判据登记入 `LOCAL_PATH_BASELINE`，不上调到硬零（与既有 30+ 历史修订记录同型）。同时也修复了修订时误删的 `audits/机制文件修订记录-2026-10-04-不能评估的忠诚批.md` 棘轮项。
