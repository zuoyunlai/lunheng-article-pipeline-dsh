### 3.1 N 族修订项

#### N-1（**P1**｜`[文档]`+`[仓库级]`）文档安装路径产出 18.15.0，且没有任何步骤能让用户察觉

- **位置**：`docs/installation.md:5-16`（安装三步）、`:31-53`（验证）；`lib/index.js`（启动状态行不含版本）
- **实测证据**（一次性 `DSH_HOME`，逐字照抄文档第 1 步）：
  ```
  $ dsh plugin --profile audit add lunheng-article-pipeline
  dsh: initialized profile audit at <scratch>/dshhome/profiles/audit
  + lunheng-article-pipeline ^18.15.0                     ← 装到 18.15.0
  $ node -e "…require('<profile>/node_modules/lunheng-article-pipeline/package.json').version"
  18.15.0
  $ npm view lunheng-article-pipeline version
  18.20.4
  ```
- **根因（已排除 dsh 与本包）**：
  - `dsh plugin` 是 **pnpm 薄转发**（`<dsh 安装>/lib/plugin-Ddi42qoW.js` 全文件 5,962 B：无版本逻辑、无 `fetch`/`catalog`/`market` 字样；`anchorPathSpec` 只处理相对路径）；
  - 手动 `pnpm add lunheng-article-pipeline`（同一 pnpm **11.27.0**）**同样得 18.15.0**；
  - pnpm 元数据缓存有两个命名空间，`registry.npmjs.org/…` 停在 `latest: 18.0.1`（09:49），`view` 用的另一个是新的（18.20.4）；
  - `--config.preferOffline=false` 仍得 18.15.0 → **未定位到 pnpm 内部规则**（如实标注：本机 pnpm 解析状态导致，不归因给 dsh 或本包）。
- **影响（已量化）**：18.15.0 vs 18.20.4 随包 **147 → 145 个文件，约 80 个文件不同**：
  - `lib/guard.js` **43 行差异**（含 `*** Move to:` 重命名分支、depth `SENTINEL_DEPTH_EXCEEDED` 拒绝、工具名小写化、`WRITE_TOOLS` 变更）→ **按文档装的用户拿到的是未含首轮 guard 加固（B-1~B-5）的构建**；
  - `lib/index.js` / `lib/commands.js` / `package.json` 各 1 处；`SECURITY.md` 20 行（披露面）；5 个 README；69 个技能机制文件。
- **修法**（三件）：
  1. `docs/installation.md` 第 1 步改为**钉版本**：`dsh plugin --profile <profile> add lunheng-article-pipeline@18.21.0`，并加一句「不钉版本时会用本机解析器**当时**的状态，可能是旧版」；
  2. 新增**版本核对**命令（文档里可直接粘）：
     ```sh
     node -e "console.log(require('<profile>/node_modules/lunheng-article-pipeline/package.json').version)"
     ```
  3. `lib/index.js` 的启动状态行带上版本号（`pkg.version`）——**装错了要看得见**（当前入口不打印版本，只有 `~standard.vendor` 字段含包名）。
- **验收判据**：文档命令逐字可跑；核对命令输出 == 期望版本；`LUNHENG_QUIET` 未设时启动行含版本。
- **回滚**：`git checkout -- docs/installation.md`（脚本侧回调 `lib/index.js` 状态行）。
- **授权**：`docs/installation.md` 随包 → 实质更正须发版；`lib/index.js` 属「入口」非机制文件，但建议同批 review。

#### N-2（P2｜`[文档]`）`installation.md` §验证 的判据对 `disabled` 不敏感，且与 §分档 矛盾

- **位置**：`docs/installation.md:33-41`（§验证 的「预期看到」）、`:65`（§分档「v18.2.6 起默认不装载」）；对照 `scripts/consistency-check.mjs` 与 `_lib/cc-rules/**`
- **实测证据**（真实 profile，同一命令三种环境）：
  ```
  LUNHENG_TIERING 未设 → tool-subagent-{retrieval,strong,audit} 命中 3 行
  LUNHENG_TIERING=on   → 3 行
  LUNHENG_TIERING=off  → 3 行                    ← 完全不可区分
  ```
  即 `--dump-config` **不反映 `disabled` 裁剪**；而 §验证 要求「三档工具行应出现」、§分档 又写「默认不装载」→ **文档自相矛盾，且该命令无法判别**。读者在默认环境跑，看到三行就会误判「分档已生效」。
- **同时关闭仓库自 v18.2.4 挂着的「残留不确定」**（`cordis.patch.yml` 内自陈：本机 `--dump-config` 仍只打印声明行）——源码级，对**已安装的** loader：
  ```
  @deepseek-ai/cordis-plugin-loader/lib/index.js
    :377-379  disabledOf = isJsExpr(disabled) ? Boolean(evaluate(expr)) : Boolean(disabled)   ← 与本包披露同形
    :391-393  refresh() { if (this.disabled) return; await this.init() }                       ← off ⇒ 不进 init、fiber 不建、工具真的不存在
    :363-371  _disabled() 还沿父 fiber 链判定（本包三行是顶层，不受影响）
    :426-437  update() 候选为 disabled 时 _dispose(previous)                                   ← 热更新会主动卸载
  ```
  **结论**：机制是真的；当年「改成恒真后 dump 里三行依旧在」的观察也是**正确**的——那不是 dump 的缺陷，是 dump 的语义（**声明视图，不反映裁剪**）。故**不能用 dump 判 tiering**。
- **修法**：
  1. §验证 改写为「dump 只能证明 **bundle 层存在 + 自注册行存在**（承重项，v18.0.0 事故的防线）」；把三档工具行的「预期看到」删掉或显式标注**不反映装载态**；
  2. 加一句「tiering 的可见性只能在真实会话里看工具清单」；
  3. 新增一致性规则：「`docs/installation.md` 的验证段不得声称 dump 能判别 `disabled` 行」。
- **验收判据**：改回旧措辞 → 一致性规则必红；文档不再出现「三档工具行应出现」这类不可判别断言。
- **回滚**：`git checkout -- docs/installation.md`（+ 摘除新增规则）。

#### N-3（P2｜`[仓库级]`）同一检验器两个版本 pin：CI 落后于发布门

- **位置**：`.github/workflows/ci.yml:131` ↔ `scripts/plugin-surface-check.mjs:61`
- **实测证据**：
  ```
  .github/workflows/ci.yml:131        pnpm dlx dsh-plugin-guide@0.3.16 verify .
  scripts/plugin-surface-check.mjs:61 CLI_SPEC = process.env.DSH_PLUGIN_DEV_SPEC || 'dsh-plugin-guide@0.3.19'  // v18.20.2 抬升
  本机跑发布门输出                     ✓ …｜CLI 0.3.19
  ```
  而 `b19c333` 的提交信息声称「pin 0.3.16 → 0.3.19」——**只抬了一处**；CI 的「真实 Loader 冒烟」仍用旧检验器。两处 hardcode 均无门守护 → 下次抬升还会漂（与仓库标志性的「修一处不修一类」同型）。
- **修法**：CI 从**单点**取版本（`env: DSH_PLUGIN_DEV_SPEC` 或让 CI 读 `plugin-surface-check.mjs` 的 `CLI_SPEC`）；加一致性规则「同一外部 CLI 只允许一处 pin」。
- **验收判据**：改动 `CLI_SPEC` 后 CI 与发布门版本必然一致；故意在 `ci.yml` 写死不同版本 → 规则必红。
- **回滚**：`git checkout -- .github/workflows/ci.yml`。

#### N-4（P2｜`[仓库级]`）宿主版本矩阵窄于 peer 声明

- **位置**：`package.json` 的 `peerDependencies`（`@deepseek-ai/dsh: >=0.1.2-rc.1 <0.2.0`）；`.github/workflows/ci.yml:126`（`npm i -g @deepseek-ai/dsh@0.1.7-rc.2`）及其注释
- **实测证据**：peer 声明下限 `0.1.2-rc.1` **从未被任何实测覆盖**；CI 只装 0.1.7-rc.2（注释自述：0.1.5-rc.2 起 `dsh-app-boot` 在 `patchReload: live` 且无 HMR 时抛「requires the Cordis HMR service」→ loader-smoke 必红，与本包代码无关）；作者本机为 **0.1.5-rc.2**，我实测其 `--dump-config` **正常** → 红点在 **app boot**，不在装载/组合层。
- **影响**：本条现在**只写在 ci.yml 注释里**——用户看不到；于是「本包支持 dsh ≥0.1.2-rc.1」这句声明宽于证据，而差额恰好是上次翻车的那一档（与二次复审 O-6 同源）。
- **修法**（二选一，须主人定案，§三.3 定案 1）：
  1. CI 增加**最低支持宿主版本** leg；或
  2. 把 peer 收紧到实测下限，并在 `docs/installation.md` 写明「真实 Loader 冒烟需宿主 ≥0.1.7-rc.2；已知 0.1.5-rc.2 在 app boot 阶段有上游 HMR 守卫问题」。
- **验收判据**：`peerDependencies` 的取值区间内**至少每个端点在 CI 中有一条实测腿**（或在文档中显式说明已知缺陷与规避）。

#### O-2 给「dump ≠ 运行态」立一处权威说明

既然 dump 不反映裁剪，权威判据只剩真实会话的工具/技能清单。把这条写进 `docs/architecture.md`（机制侧）与 `docs/faq.md`（用户侧）——这是最容易被误用的一条，且**仓库自己也曾被它误导过**（v18.2.4 的「残留不确定」正是 dump 语义造成的）。

#### O-3 外部 CLI pin 单点化 + 静态门

`.github/workflows/ci.yml` / `.github/workflows/publish.yml` / `scripts/plugin-surface-check.mjs` 三处统一从 `CLI_SPEC` 派生；加一致性规则。

#### O-4 把本轮的宿主对照变成**常设门**

本轮验证的三类事实都是从宿主包**机械可派生**的：`skills.register` 的载荷形状（`validateRuntimeSkill` / `SkillResourceBase` 联合体）、guard 的 `WRITE_TOOLS`/`PATH_KEYS` 对真实工具名与路径键的覆盖、`inject` 服务名。建议新增「宿主契约对照」测试：**读已安装 `@deepseek-ai/*` 的导出与校验函数**做断言，而不是靠人读文档（本仓历史上「入口 import 宿主包会炸」的教训要求这类对照尽量走**运行时探测而非静态 import**）。

#### O-5 承上轮的 O 族（7 条仍在）

规则↔反向自证双向账（把二次复审的 14 组变异矩阵搬进 CI）、三态 `UNKNOWN` 推广到所有以外部输出为输入的规则、解析器单点化推广、测试跳过必须可见（`t.skip` 而非 `catch { return }`）、环境矩阵与声明对齐、规则数量治理、常驻集瘦身排期（`SKILL.md` → 20 KB）。
