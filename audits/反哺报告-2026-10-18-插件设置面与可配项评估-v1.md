# 反哺报告 · 论衡插件的「设置面」与可配项评估（v1）

> **被评估版本**：v19.17.0（`796ccb1b`）
> **触发问题**（主人 2026-10-18）：① DSH 面板左侧「插件 → lunheng-article-pipeline」里能否加**更新按钮**与其它**设置项**？② 素材池目录、个人风格基线目录能否由用户在设置里指定，还是保留现状更好？
> **方法**：读插件实际代码（`lib/index.js` 的 Config 形态、`lib/client.js` 的 slot 注册、`package.json` 的 `dsh.client`）+ 对照官方契约（`dsh-plugin-guide` 的 `adding-a-settings-card.md` §1–§5）+ 统计文档影响面。
> **纪律**：本报告只提动议与判断；**不改任何机制文件**。上一轮我在对话里给过的「20 行就能做」的估算**在本报告中已被推翻**（见 §二 F-1），以此处结论为准。

## 一、结论（先给答案）

| 问题 | 答案 |
|---|---|
| 能加「更新按钮」吗 | **能**，官方有 `plugins.detail.actions` slot（挂在插件详情页顶部）。但**只能做半自动**：检查 npm 最新版 → 提示 → 复制升级命令，**不能自己装**（见 §三 红线） |
| 能加「设置项」吗 | **技术上能，但成本被我此前严重低估**：论衡的 Config 不是 Schemastery，官方表单渲染不了它的字段；且 `Volatile` 出现 **0 次** ⇒ 改完要重载插件，没有热更新 |
| 素材池目录可配 | **不建议进插件设置**——它是**工作区级**，而插件 Config 是 **profile 级**，错层会污染池与负知识账本。磁盘需求用 junction 解 |
| 风格基线目录可配 | **该配**（用户级，语义匹配），但成本是 **22 处文档 + 写回通道**，不是「加个字段」 |

**一句话**：论衡的「设置」里，**只有"环境适配类"值得配**；"约束类"不该给 UI 开关，"项目级"给了是错层。而"更新按钮"值得做，但要接受它只能提示、不能代劳。

## 二、现状事实（逐条带实据）

### F-1（**推翻前判**）Config 不是 Schemastery ⇒ 官方设置表单渲染不了

- **事实**：`lib/index.js:37-45` 明确写着**刻意不用** `@deepseek-ai/schemastery`。理由有实测：宿主用 pnpm 安装，只给**已声明依赖**建 `node_modules` 链接，而 schemastery 不在本包依赖表 → `import()` 解析不到；即便按 profile 布局手工放好，经 junction 后 Node 按 **realpath** 向上找依赖仍找不到 → **Config 恒为 undefined**。
- **后果**：论衡的 `Config` 是 `CONFIG_SPEC`（`{ kind, def, why }` 普通对象）+ 自实现的 standard-schema `validate()`。官方 *Plugin Configuration Forms* 依赖 Schemastery 的**字段元数据**（`.volatile()` / `.step()` / `.min()`）来生成表单 ⇒ **官方设置卡片无法识别这 9 个字段**。
- **我上一轮的错误**：说过「风格基线设置项约 20 行」。按本条事实，要么重写 Config 形态（已实测失败），要么自建表单 + 接 Host 的 ConfigEditor 写回 —— **都不是 20 行**。

### F-2 `Volatile` = 0 ⇒ 没有运行时热更新

- **事实**：`lib/index.js` 全文 `Volatile` 出现 **0 次**（`grep` 计数）。
- **后果**：即使做了写回通道，配置变更也**不会热生效**——必须重载插件行（`loader/volatile-update` 未接）。这让「UI 设置」相对「手改 `cordis.patch.yml`」的收益**只剩"少编辑一个 yaml"**，却要付出写回通道 + 重启的成本。

### F-3 客户端半边已有 4 个 slot，但 `dsh.client.inject` 是空数组

- 已注册：`sidebar.panellist`（运行面板图标）、`main`（中央面板）、`conversation.input.dock`、`sidebar.right.pane.tab`（`lib/client.js:2346-2386`）。
- **未注册** `plugins.detail.actions` / `.badge` / `.section`。
- `package.json` 的 `dsh.client = { platform: 'web', immediately: true, inject: [] }` —— **inject 为空**。官方 §5 的示例要求注入 `@deepseek-ai/dsh-client-ui-settings` 才能拿到设置页的 `form`。
- **风险**：加 inject 会引入一个**当前未声明的宿主包**；技能里反复提醒「装了但没反应」在 `dsh web` 下可能完全无日志。此步必须实测，不能纸面推定。

### F-4 两个目录的层级不同（这是全部结论的分水岭）

| 目录 | 定位 | 消费点 | 影响面 |
|---|---|---|---|
| `evidence-pool` | `join(workspaceRoot, 'evidence-pool')`（`pool-query.mjs:55` 等）—— **工作区级**，与 `run/` 平级 | 3 脚本 / 6 处；`pool-store.mjs` 各函数接受 `poolDir` 入参（好改） | 文档 12 处（`素材池.md` 5 处为真源） |
| `style-baseline` | `~/.lunheng/style-baseline/<文类>/` —— **用户级** | **0 个脚本消费点**（运行时由主控按 SKILL 流程读目录） | 文档 **22 处**（13 文件） |

> **推论**：**位置的"层级"决定它能不能进插件设置**。插件 Config 是 profile 级（一个 profile 可开多个工作区）；把工作区级路径写进 profile 级配置，就会出现「A 工作区的素材进 B 工作区的池」。而用户级路径（风格基线）与 profile 级语义**天然兼容**。

### F-5 「设置」在论衡里其实是三种不同的东西

| 类 | 例子 | 该不该上 UI |
|---|---|---|
| **A 环境适配** | `scriptTimeoutMs` / `scriptMaxOutputBytes` / `hookMaxBlockChars` / `hookMaxTotalChars` / `quiet` / 风格基线目录 | **可以**（调参不改变协议语义） |
| **B 约束** | `handoffLevel`（basic/strict）、`ethicsHook`（脱敏总开关）、`hookRewriteContent`（是否改写正文）、`allowMechanismEdit`（放行机制文件写入） | **不该**（见 §四） |
| **C 项目级** | 检索档（全网/本地）、文类、目标期刊、FLOOR/WAIVER 标记 | **不该**（属于 `run/<项目>/01-任务简报.md`，不是插件配置） |

## 三、「更新按钮」的可行边界

**能做**（官方 `adding-a-settings-card.md` §4）：
- `plugins.detail.actions` —— 页面顶部控件；
- `plugins.detail.badge` —— 标题旁标签（适合"有更新"）；
- `plugins.detail.section` —— 内容下方一节（适合版本/诊断详情）；
- 用 `subject` 过滤，只在 `subject.kind === 'bundle' && subject.pkg.name === 'lunheng-article-pipeline'` 时渲染。

**不能做**（官方红线，`dsh-plugin-guide` 契约段）：
> **禁止**：在会话运行期间改 profile 的 `cordis.patch.yml`；手写 profile 的 `package.json`；**在 profile 目录里跑 pnpm**。

而 `dsh plugin add` 恰恰做这三件事。**自更新 = 在运行中的宿主里替换正在加载的 `node_modules`**，最坏结果是当场崩会话语。

**建议形态（半自动）**：按钮点击 → 只读 `https://registry.npmjs.org/-/package/lunheng-article-pipeline/dist-tags` → 显示「当前 v19.17.0 / 最新 vX.Y.Z」→ 提供可复制的 `dsh plugin --profile desktop add lunheng-article-pipeline@X.Y.Z` + 提示重启。**不做任何写盘**。

## 四、为什么「约束类」不该给 UI 开关（本报告的核心判断）

论衡不是一个"服务型插件"，它的本体是**一套流程协议**：四门、M 门、G 审计、机制文件写保护、交接门。这 9 个 Config 项里有 4 个直接是**协议约束的强度**：

- `handoffLevel: strict` = 交接门从 A0/A1/A2 扩到 A3/A4/A5/A6/A8/A9
- `ethicsHook: false` = 整个会话不扫、不注入伦理标记
- `hookRewriteContent: true` = 用脱敏正文替换工具结果
- `allowMechanismEdit: true` = 放行机制文件写入（**P0 违规的解禁开关**）

把它们做成"随手可点的开关"，等于把「闸门强度」变成 UI 上的一个 toggle。**默认路径一旦变成"点一下就能放宽"**，协议的自证能力就被削弱了——而本仓恰恰以「闸门必须留机械证据」「N/A ≠ 跳过」为立身之本。这类开关的正确位置是 `cordis.patch.yml`（部署级、需要写文件、改完要重载），**摩擦本身就是防护**。

> 这条判断也解释了现有设计：为什么 `allowMechanismEdit` 宁可做成 env + Config 双通道，也不做一个按钮。

## 五、候选清单（含"不做"的理由）

### 建议做（只读信息面，零 Config 改动、零写回、零重载）

| # | 位置 | 内容 | 价值 |
|---|---|---|---|
| P-1 | `plugins.detail.section` | **版本实况**：插件版本 / npm 最新版 / 是否落后 | 避免「我到底装没装新版」的反复确认 |
| P-2 | `plugins.detail.badge` | 有新版本时显示标签 | 同上，被动可见 |
| P-3 | `plugins.detail.section` | **环境诊断**：把 `model-routing` 的 `envRoutingWarnings` 直接展示（当前 `MiniMax-M2.7` 未登记这类问题，只在 CLI 出现一次） | **最高价值**：把"派发时才炸"的问题提前到页面可见 |
| P-4 | `plugins.detail.section` | **配置实况**：9 项当前取值（只读表格，附"改法：cordis.patch.yml"） | 消除"配置到底生效没"的疑问 |
| P-5 | `plugins.detail.actions` | **检查更新**（只读 registry + 复制命令） | 半自动更新，见 §三 |

> P-1..P-5 都不碰 Config、不写盘、不需 volatile、不需 inject（`plugins.detail.*` 是纯 slot 注册）——**这是本轮唯一低风险且高价值的一批**。

### 不建议做

| 项 | 理由 |
|---|---|
| `handoffLevel` / `ethicsHook` / `hookRewriteContent` / `allowMechanismEdit` 做成 UI 开关 | §四：约束类，摩擦是防护 |
| 素材池路径做成插件设置 | F-4：工作区级 vs profile 级，错层污染 |
| 检索档 / 文类 / 期刊 做成插件设置 | 属 `01-任务简报.md` 项目级字段 |
| 自更新（点按钮就装） | §三 红线 + 崩会话风险 |
| 环境变量类（`LUNHENG_*_MODEL`）做成设置 | 写在宿主进程 env，改完要重载插件行；且与 `dsh` 的 profile 机制不是一层 |

### 磁盘压力（素材池的真实诉求）——零代码解

```
mklink /J <工作区>\evidence-pool <另一块盘>\evidence-pool
```

junction 对 Node 的 `join/readdir` 完全透明，脚本零改动、语义不变（池仍是"工作区下的一个目录"）。**这是本轮我最推荐的池方案**——用对了机制，就不必改代码。

## 六、若坚持要做「可配路径」，三条路的真实成本

| 路 | 做法 | 成本 | 我的评价 |
|---|---|---|---|
| ① 自建表单 + 接 ConfigEditor | 在 `plugins.detail.section` 渲染表单，经 Host 的 `form.mutate` 写回 `cordis.patch.yml` | 需 inject `ui-settings` + 自建表单 + 处理写回校验；**无 volatile ⇒ 改完仍需重载** | 收益（少编辑 yaml）远小于成本 |
| ② 只做只读 + 复制命令 | 显示当前路径与"如何改"的 yaml 片段 | 极小（同 P-4） | **推荐**：诚实且零风险 |
| ③ 重写 Config 为 Schemastery | 换回官方 schema | **已被实测否决**（pnpm 布局解析不到，见 F-1） | 不可行 |

**结论**：论衡的 Config 形态（零依赖 standard-schema + 无 volatile）决定了「UI 设置项」的收益上限就是"少编辑一个 yaml"，而成本是写回通道 + 重载。**这个性价比不成立**。要走，就走 ②。

## 七、对两个目录的最终建议

1. **风格基线**：**保持现状路径约定不变**，但在 P-4 的配置实况里显示「当前目录 / 是否存在 / 收录了几种文类」——让用户**看见**而不是**改**。若确需换位置，junction 同样适用（`~/.lunheng/style-baseline` 指到个人文档库），且不涉及任何代码或文档改动。
   - 注意：它是**不外发**的私密语料。把它 junction 到云同步盘 = 同步上云，这一点必须在做之前说清（本轮没有做，仅提示）。
2. **素材池**：**不进设置**。磁盘需求用 junction。若将来真要让池与 `run/` 分离，那是一次**工作区级配置**的立项（要同时处理 `--seed` 路径、负知识账本扫描面、跨工作区复用计数），不是加个字段。
