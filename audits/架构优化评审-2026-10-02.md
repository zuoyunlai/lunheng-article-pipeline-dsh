## 2. 核心论断（Executive Summary）

这个仓库的工程成熟度很高：**代码可派生的「事实」已被测试守住**（工具集 / 配置键 / 命令集 / M 门项数 / G 项清单都从代码 `derive`，见 `tests/docs-facts.test.mjs:201-230`、`:655-700`）。它真正的架构债是**另一类**：

> **凡「不能被代码派生」的事实（版本点位、角色清单、阶段序列、env 变量名、门清单本身），都靠人手在多点位同步；漂移因此成为本仓的第一缺陷形态。** 仓库自己把这条写进了若干处注释（`command-enum-subskill-version.test.mjs:1-8`、`docs-facts.test.mjs:155-166`、`consistency-check.mjs:10-14`），但只在**部分**事实族上做了机械化。

由此衍生三条 P0：

1. **运行期入口 `lib/**` 缺乏行为级门与统一观察面**——组合根（568 行的 `apply`）过载、业务逻辑内联、热路径同步，且其「事实」（版本、配置键、env 名、H2 的脱敏聚合）多数不在任何内容门内。代码级报告的 8 条缺陷是同一结构洞的多次显影。
2. **单一真源未落地为「派生」**——版本 12 种字面形态、角色清单、阶段序列、`LUNHENG_*` env 名各散在 3–7 处，靠 `bump-version.mjs` 的手工 RULES 表 + `consistency-check` 的正则规则族维护。
3. **「文档即程序」的编排没有机器状态真源**——9 角色 / 6 阶段 / G14 三层防御 / 修订回环全部是自然语言，唯一机械强制是交接门；`status.md` 是无 schema 的 markdown 表。漂移会**静默改变执行路径**（规则 ㉔ 正是为一次「Phase 1.5/4.2 消失」而立的门）。

## 3. P0 — 架构风险

### P0-1 ｜ 运行期入口 `lib/**`：组合根过载 + 业务逻辑内联 + 覆盖洞（三位一体）

**问题**：
1. **组合根过载**：`lib/index.js` 的 568 行里，`apply()` 一个人同时承担：Config schema（`:51-120`）、frontmatter 解析（`:146-163`）、状态上报器（`:176-184`）、版本自证（`:196-202`）、技能注册（`:246-294`）、工具安装（`:309-319`）、**内联 H2 监听器（`:335-432`，约 100 行脱敏聚合逻辑）**、内联 H7（`:453-476`）、内联 H4（`:493-513`）、guard 安装（`:515-550`）、命令安装（`:551-561`）。这是「组合根 + 领域逻辑」的混合体。
2. **业务逻辑内联**：H2 的脱敏**聚合**（`aggCounts` / `distinctPersons` / `blockCount` / `skippedTooLarge` / `hookMaxBlockChars` 判定，`lib/index.js:357-429`）本应属于 `lib/ethics-sanitize.js`（脱敏模块）或独立的「钩子策略」模块，却住在入口。后果可见于代码级报告 P2-3：`summary` 取最后一块、`counts` 只反映单块——正是「内联写聚合器」的典型走样。
3. **热路径同步**：H2 监听 `tools/post-execute`（`:335`），对 `read|web_|subagent*` 的**每个结果**同步跑 CPU-bound 脱敏（`sanitize` 是纯同步函数，`ethics-sanitize.js:147`）。触发面恰是流水线主数据通路。
4. **覆盖洞**：`consistency-check.mjs:106` 的 `ROOT = join(__dirname,'..')` = 技能根，`walk()`（`:145-157`）只收 `.md` → **`lib/**` 完全在内容门扫描面之外**（代码级报告 P2-4 已实测该事实）。且 `tests/` 中触及 `lib/` 的只有 `entry / commands / guard-bypass / guard-config / h2-h5-listeners / h3-h4-h7-listeners / host-contract / third-review-gates` 8 个文件，其中**没有一个**断言「钩子在超大输入 / 多块 result / 未预期 result 形状下的行为不变量」。

**证据**：`lib/index.js:215-568`（`apply` 单函数）；`:335-432`（内联 H2）；`:453-476`（内联 H7）；`:493-513`（内联 H4）；`lib/ethics-sanitize.js:147-258`（`sanitize` 纯同步、无钩子感知）；`consistency-check.mjs:106,145-157`；`tests/h2-h5-listeners.test.mjs:182-210`（唯一的大输入用例，但断言的是**默认不改写**而非「聚合正确」）。

**影响**：这是代码级报告里 **8 条缺陷中至少 5 条（P0-1/P0-2/P1-1/P2-2/P2-3）的共同结构成因**——因为入口同时是「组合」与「实现」，任何行为缺陷都缺少一条自然的门（门扫文档、测试扫小输入）。且入口越涨越大，H2 已经从「注册一行」长成「100 行聚合器」。

**建议方案**（分层，可分批）：
- **A（小）**：把 H2/H4/H7 三个监听器**移到各自的模块**（`ethics-sanitize.js` 导出一个 `installEthicsHook(ctx, cfg, report)`；模型路由监听移入新 `lib/hooks/model-routing.js`；prompt 追加移入 `lib/hooks/prompt-tail.js`），`apply()` 只做「装配」。
- **B（中）**：把脱敏**聚合**从入口挪进 `ethics-sanitize.js`（`sanitizeBlocks(blocks, opts)` 返回聚合结果），并**给 `sanitize()` 拆分职责**——「纯变换全文」与「分页读取」分离（正是代码级报告 P0-1 的结构性修法）。
- **C（中）**：把 `consistency-check.mjs` 的扫描根从「技能根」提升为「仓库根」，或**新增一条 lib 级规则族**（至少覆盖：版本点位、Config 键名、env 名、`ctx.on` 事件名/形参——后者已由 `host-contract.mjs` 部分做到，规则 ⑮）。**更根本**：给 `lib/**` 补一条**行为级门**（不是文档门）——例如「H2 在（超大 / 多块 / 非文本块 / 缺 content）四种输入下的不变量」套件，正是代码级报告 P2-4 的推荐，但应作为**门**而非一次性用例。

**工作量**：A 小 / B 中 / C 中。
**风险**：A/B 会动入口与模块边界，需同步 `tests/entry.test.mjs`、`h2-h5-listeners.test.mjs`、`host-contract.mjs` 的解析面（`host-contract.mjs:49` 的正则只匹配**箭头函数**且只解析 `lib/index.js`——**监听器一旦移出 `index.js`，规则 ⑮ 会「未解析出任何监听器」而 fail-closed 报红**）。→ 移监听器必须**同批**把 `host-contract` 的扫描面扩到多文件，否则会触发一次真实红。C 的提升扫描根会**首次**让 `lib/**` 进入版本/计数规则——大概率先暴露既有漂移（见 P0-2），需一次性清账。

**问题**：仓库已经掌握「从代码派生事实」的正确手法（工具集、配置键、命令集、M 门项数在 `tests/docs-facts.test.mjs` 中 `derive`），但这套手法**只覆盖了能正则从 `.js/.mjs` 抓出来的事实**。以下事实族仍以「多点位字面 + 手工同步清单」存在：

| 事实 | 现存的物理点位（实测） | 维护方式 | 是否有门 |
|---|---|---|---|
| **版本号** | `package.json:3`、`SKILL.md` frontmatter `:3`、`SKILL.md` 正文头 `:8`、`cordis.patch.yml:1`、`lib/index.js:502`（H4 尾注，v18.62.4 改为运行时读）、五语 README、`docs/introduction.md`、`QUICKSTART.md`、`examples/**` | `scripts/bump-version.mjs` 的**12 条 RULES 字面表**（`bump-version.mjs:57-70`），新增形态须手工加行 | 部分（`consistency-check` 规则①②⑧⑫⑬） |
| **角色清单 T1–T9** | `package.json:4`(description)、`SKILL.md:102`、`SKILL.md:236`、`AGENTS.md:32`、`references/dispatch-cards.md`、`references/agents/`（11 张卡）、`model-routing.mjs`（tool→roles） | 纯文本 | 弱（`docs-facts.test.mjs:425-446` 只断「9 张卡都在 + 无文档否认其存在」） |
| **阶段序列** | `SKILL.md:103`（唯一 Phase 真源）、`references/pipeline-readme.md`（`流水线全景`）、`AGENTS.md:14-27`、五语 README 概览块 | 纯文本 | 有（规则 ㉔ 断言 Phase 编号 ⊆ 速查表） |

**证据**：`bump-version.mjs:57-70`（12 形态手工表，注释自陈两次漏形态）；`consistency-check.mjs:10-14`（自述「两个数字不做机械门…手工同步即可」）；`repo-hygiene-check.mjs:36-38`（自述清单曾落后于实现）；`docs-facts.test.mjs:155-191`（C-1 门被一次真实事故逼出：文档造出一个**代码里不存在**的开关 `LUNHENG_HANDOFF_LEVEL`）；`lib/index.js:457-461` 与 `cordis.patch.yml:109,120,131` 的 env 名重复。

**影响**：漂移是本仓的**第一缺陷形态**，且已多次造成「文档声称 A、代码是 B、四道门全绿」（C-1 事故）。每一次新增事实族都要付出「新规则 + 新测试 + 手工登记进两处清单」的固定税，而没有一处**生成**它们。

**建议方案**：
- **版本**：把 `bump-version.mjs` 的「字面形态表」改为**从真源生成**——所有「当前版本声明」改为读一个 `VERSION`（或 `package.json`）并在文档里用**占位标记**（如 `<!-- v:current -->`）或**构建期注入**；或至少在 `consistency-check` 里新增一条「未知版本形态检测」（扫到 `v\d+\.\d+\.\d+` 且邻近含「当前/版本/plugin v」但不属于已登记形态 → 报 P1，逼新形态登记）。后者成本低、见效快。
- **env 名**：把 `LUNHENG_*` env 名收口为一个**单一真源模块**（如 `lib/env-names.mjs` 导出常量），`cordis.patch.yml` 的 `!!js` 无法 import（宿主加载期求值，`cordis.patch.yml:30-42` 明确只允许 `process.env.*` 字面）——故**补一条门**：断言 `lib/index.js` / 文档里出现的 `LUNHENG_[A-Z_]+` 必须 ⊆ `cordis.patch.yml` 中出现的同名集合（双向），把「三处硬编码」变成「三处必须一致且有门」。
- **角色 / 阶段**：把 T1–T9、Phase 0–5 抽为 `references/_shared/pipeline-manifest`（结构表），文档只留指针；或至少补门：断言 `package.json` description、`SKILL.md`、`AGENTS.md` 的角色编号集合**相等**。

**工作量**：版本门 小 / env 门 小-中 / 角色-阶段 manifest 中-大。
**风险**：低（多为**新增门**，不改运行期）。但沿用「先加门再清账」的既有节奏：新门上线会**先报出既有漂移**，需一次清账提交。若改为 manifest 驱动，则触及 `bump-version`、`consistency-check`、五语 README 生成——**变更面大**，建议后置。

### P0-3 ｜「文档即程序」的编排缺机器状态真源（漂移即静默改变执行路径）

**问题**：9 角色 T1–T9、6 阶段、G14 三层防御、修订回环 A 轨、并行点（Phase 1 三角 / Phase 4.5）**全部以自然语言**定义在 `SKILL.md` + `references/pipeline-readme.md`（**112 KB**）+ `references/agents/*.md`（11 卡）+ `dispatch-cards.md`。唯一的机械强制是**收报侧** `lunheng_handoff_check`（`lib/tools.js:273-339`）+ 主控自跑的 M 门。流程状态真源是 `run/<项目>/status.md`（**无 schema 的 markdown 表**，主控独占写）+ `agents-log.md`（子代理追加）。

**证据**：`AGENTS.md:11-51`（Phase 协议全部为自然语言段）；`dispatch-cards.md`（派发 prompt 模板，规则 ⑮ 限每卡 ≤12 行）；`lib/tools.js:273-339`（交接门是唯一编排侧机械验收）；规则 ㉔（`consistency-check.mjs:41-44`）**因一次真实事故而加**——「pipeline-readme 流水线全景里的 Phase 1.5/4.2 **消失**了整轮修订回环」，主控的 `todo_write` 里就没有那一步；`AGENTS.md:36`（status.md 独占写 / agents-log 追加写的分工）。

**影响**：编排的**正确性 = 模型是否读全并遵守一个巨大语料**。任何一处文档漂移（旧门已多次抓到时序/编号漂移）都会**静默**改变实际执行的流水线，且因「闸门只在收报侧」而**无门可拦**。这是长期演进中最大的隐性风险：门越加越多，但**编排层**（谁先谁后、谁该 spawn）几乎完全靠自觉。

**建议方案**（不引入 workflow 引擎，尊重 `AGENTS.md:130` 的「显式禁接 workflow/goals」）：
- **轻量状态契约（推荐，中）**：为 `run/<项目>/` 定义一份**机器可读的状态清单**（如 `run-state.json`：`{phase, gates:{T2.5:exit, T7.5:exit}, roles:{T1:{artifacts:[…],reportVerified:bool}}, revisionRound}`），`status.md` 降为**它的渲染视图**（人读）。交接门 / 一个新增的 `run-state-check.mjs` 校验它。收益：把「主控独占写 markdown」升级为「有 schema 的真源」，让幂等重入（resume）有据可依。
- **编排不变量门（小-中）**：在现有规则基础上补「编排原子」门——例如断言「`SKILL.md` 的角色表 ∪ `dispatch-cards.md` 的卡 ∪ `references/agents/` 的卡 ≡ T1–T9」，「并行点（Phase 1/4.5）在 SKILL.md 与 pipeline-readme 两处编号一致」。
- **幂等/重入（大）**：为每个 Phase 定义「产物存在即已完成（幂等）」的显式契约，`resume` 按状态清单跳过已完成 Phase。

**工作量**：状态契约 中 / 编排门 小-中 / 幂等重入 大。
**风险**：状态清单是**新增真源**，会让 `status.md` 与它出现「一事实两处」——必须立刻决定**谁是真源**（建议 `run-state.json` 真源、`status.md` 生成），否则会把 P0-2 的病复制到编排层。改动触及 SKILL/AGENTS/主控卡 + 交接门，**测试面广**。

## 4. P1 — 结构改进

### P1-1 ｜ guard 的信任边界：工具名黑名单 + 只覆盖工具调用层；路径归一化三份实现

**问题**：
1. **黑名单式**：`guard.js:46-51` `WRITE_TOOLS`（工具名集合）+ `:52-59` `PATH_KEYS`（参数键集合）+ `:75-83` 补丁文本正则。v18.62.5 又各加了 5–6 个条目以堵 3 类绕过（`guard.js:39-44` 注释自陈）。这是**可被无限延伸**的军备竞赛——只要宿主换工具名/键名就静默漏检（代码级报告 P1-1 实测 3 类，虽「当前不可利用」）。
2. **只覆盖工具调用层**：`guard.js:8-15` 如实声明「guard 只看工具调用；`pwsh`/子进程不经此门」，逃生口是 `LUNHENG_ALLOW_MECH_EDIT=1`（`guard.js:12-14`）。官方无 per-path 只读声明（`fs/write-intent` 无 deny 返回），故这是**宿主能力的天花板**，非本包可独力突破。
3. **路径归一化三份**：`guard.js:92-107 realpathBest`、`lib/run-path-fence.mjs:18 realOrResolve`、以及 `lib/commands.js:165` 内联的 `norm`（`/lunheng-stats` 的 `--run-dir` 包含判定）。三处逻辑**同旨不同实现**。`run-path-fence.mjs` 头注释（`:1-12`）正是为「同族收紧 ≠ 一致」而抽的，但抽出后**并未**把 guard 的 `canonicalPath` 也统一过来。

**证据**：`guard.js:39-59`（黑名单扩面）、`:8-15`（边界自陈）、`:268-274`（先判 `WRITE_TOOLS`，不在即放行——黑名单的根）；`run-path-fence.mjs:1-20`；`commands.js:165`。

**影响**：安全控制的**失效模式是静默**（漏检无告警，v18.62.5 才补 warn）。架构上，把「哪个工具会写」的判断交给**工具名枚举**，等于把守卫的可靠性绑定到宿主命名——与「用代码派生事实」的正确路线相反（这里是**枚举**而非**判定**）。

**建议方案**：
- **倒转为「路径中心」**：guard 一旦被任意**写语义倾向**的调用触发，就**不依赖工具名**，而是「抽取所有候选路径（任意深度、任意键、含绝对路径兜底）→ 解析后若落在受保护根内即否决」。工具名集合降级为「提示」。当前 `guard.js:191-198` 已有该兜底但被 `depth === 0` 与 `isAbsolute` 限制、且入口先被 `WRITE_TOOLS` 截断（`:274`）。可考虑：对**未知工具名**也做路径中心判定（代价 = 误伤面上升，需评估只读工具是否会被误拦——注意 guard 对**所有**工具调用都会跑 `guardFn`，故需按「工具名疑似写」或「路径命中受保护根」两条任一成立才否决）。
- **统一路径归一化**：把 `guard.js` 的 `canonicalPath` 与 `run-path-fence.mjs` 合并为**一个** `lib/path-canon.mjs`，三处共用。

**工作量**：小-中。
**风险**：路径中心化会**扩大否决面**——误伤合法写调用会让「主人授权」变成高频。必须先用现有 `tests/guard-bypass.test.mjs` + `guard-config.test.mjs` 做回归，并保留现有 `PATH_KEYS` 作为**优先**路径、路径中心作为**兜底**。归并路径函数风险低（纯重构，测试可覆盖）。

### P1-2 ｜ 钩子模型：契约靠「源码正则解析」守、顺序耦合隐式、语义开关暴露在设计层

**问题**：
1. **契约守卫靠解析源码文本**：`scripts/_lib/host-contract.mjs:49` 用一个**正则**解析 `lib/index.js` 的 `ctx.on(...)` 箭头函数形参，比对硬编码的 `HOST_CONTRACT` 表（`:29-45`，ver 声明「真源 = 宿主 `@deepseek-ai/dsh` 0.2.0-rc.2」）。这套机制**必要且聪明**（它抓住了 `ctx.on`「注册成功 ≠ 会触发」的死监听器问题），但它同时意味着：**监听器签名与事件名的正确性，建立在「正则能解析出源码形态」之上**——非箭头函数/变量引用会 fail-closed（`host-contract.test.mjs:84-90`）。这是「脆弱契约」的机械化代偿。
2. **顺序耦合隐式**：`tools/post-execute` / `system-prompt/assemble` / `agent/request` 都是 waterfall；`lib/index.js:503-509`（H4 必须 `await next()` 后追加，否则**截断下游**，含 dsh-agent 的模型选择——`:489-491` 注释如实登记了这次 P1-2 事故）。waterfall 的「必须调用并传递 next」规则**无法声明式表达**，只能靠注释 + 门。
3. **语义开关暴露在设计层**：`hookRewriteContent`（`index.js:57`，默认 false = 只标记不改写）、`hookMaxBlockChars`（`:58`）在入口 `CONFIG_SPEC` 里作为**裸 config 键**。它们所表达的不是「部署旋钮」，而是**「钩子该不该改写工具结果」这一设计决策**被做成了运行期开关——这正是代码级报告 P0-2 的根源（默认行为曾改写全量工具输出，触发面 = `read/web_*/subagent*`）。

**证据**：`host-contract.mjs:29-49`；`host-contract.test.mjs:47-51`（断言「当前恰好 3 个监听器」）；`index.js:487-492`（H4 截断事故登记）；`index.js:57-58`（两个语义开关）；`tests/h3-h4-h7-listeners.test.mjs`。

**影响**：钩子是**全流程热路径**且**契约最易错**的部分（历史上有 H5/H3 死监听器、H2 4 参错位、H4 截断三个真实事故）。当前靠「正则门 + 逐条测试 + 长注释」维持正确性——可维护，但每加一个钩子都要同时维护：实现、`HOST_CONTRACT` 表、正则、测试、注释。

**建议方案**：
- **声明式钩子注册（中）**：抽 `lib/hooks/registry.mjs`，用一张**表**声明 `{ event, arity, params, install() }`，`host-contract` 直接读表而非解析 `index.js` 源码文本——把「正则解析源码」降级为「读一张真源表」，消除解析退化面。
- **语义归位（小）**：`hookRewriteContent` 的默认值应**固定为「不改写」并移除该开关**（改写是 P0-2 认定的错误默认），或将其从 Config 降级为**不可配置的模块常量**——把「设计决策」从「部署开关」里拿掉。
- **waterfall 守卫（小-中）**：把「必须调用 next」的纪律写进 hooks 基类（注册器对 waterfall 事件包一层「若未调用 next 则构造期/测试期报警」）。

**工作量**：声明式注册 中 / 语义归位 小 / waterfall 守卫 小-中。
**风险**：注册器化会动 `host-contract.mjs` + `host-contract.test.mjs` + `h2-h5/h3-h4-h7` 测试 + 规则 ⑮；语义归位会改 `docs-facts.test.mjs:263`（Config 键数 7）与 `docs-facts` 的 C-1 四集合断言、以及多处文档——**变更面中等，但都受门保护**，属可控。

### P1-3 ｜ 退出码被当成「语义裁决通道」：工具/门/报告生成器无统一协议

**问题**：技能内 28 个脚本 + 仓库 10 个脚本被**要求**共享退出码语义，但它们实际是**三类东西**：门（判定）、工具（计算）、报告生成器（输出）。仓库用一套**命名空间**（0/1/2/3/10/30/70，交接门另 20/21/22，`model-routing` 另 4）来管理撞义，甚至明确规定某些脚本的 `1` **不得被自动化消费**——`SKILL.md:48`：「`refresh-gates.mjs` 的退出码**不得被任何自动化链消费**（`1` 与 M 门 `1 = P1 内容失败` 字面撞义）」。

**证据**：`SKILL.md:63`（闸门退出码枚举 `0/1/2/3/10/30/70`）；`lib/tools.js:133,278`（工具描述内嵌 exit 语义）；`SKILL.md:48`（refresh-gates 撞义声明）；`AGENTS.md:39`（「只要脚本不做内容判定，它的 `1` 就一定是撞码」）；`repo-hygiene-check.mjs:24-26`（规则的退出码契约表/命名空间双向对账）；`docs-facts.test.mjs`（未覆盖退出码语义一致性）。

**影响**：一个进程退出码同时编码「结果判定」「参数错误」「内部错误」「是否可被自动化消费」四种含义——命名空间是在**补丁式**管理这种过载。新增脚本时，「该拿哪个码」需人工查 `troubleshooting §8` + `EXIT_CONTRACT`，并有撞义风险（已有的 `refresh-gates` 就是活例）。

**建议方案**：
- **统一脚本协议头（小-中）**：所有随包脚本输出**统一 JSON 信封** `{ok, kind:'gate'|'tool'|'report', verdict?, exit, …}`，把「语义裁决」放进 `verdict` 字段，进程退出码只保留「0 正常 / 10 用法 / 70 内部」三种**进程级**语义。门类额外用 `verdict` 表达 P0/P1/P2/SKIP。这样 `refresh-gates` 的 `1` 不再是裁决。
- **给「门」一个接口契约（中）**：定义 `Gate = (input) => {verdict, evidence}`，用同一 runner 驱动；`无统一的门抽象` 是目前每个门各写 JSON + exit-guard 的根因。

**工作量**：中-大（触及全部门脚本 + 消费方 + 文档 + 测试）。
**风险**：**高**——这是全仓脚本的输出契约，mock/夹具（`tests/_fixtures.mjs`、`docs-facts`、各 `*.test.mjs`）大量依赖当前 JSON 形态与退出码。属**长期演进**，必须分阶段（先加 `kind/verdict` 字段保持向后兼容，再迁移消费方）。

**工作量**：小（收声明带）/ 中（扩矩阵）。
**风险**：扩矩阵增加 CI 时长；收声明带可能拒掉当前能用的版本——需以实测为准。低代码风险。

### P1-5 ｜ 测试架构：行为断言占比低 + 批次命名累积 + 与「门」的职责重叠

**问题**：
1. **批次命名**：`tests/` 存在 `batch7-scan-surface` … `batch17-qlt5-batch6`（10 个文件），命名反映「按需求批次累积」。`command-enum-subskill-version.test.mjs:6-8` 甚至直接说「沿用 batch12 教训」。

**证据**：`tests/batch7..batch17`、`lib-line-refs.test.mjs`、`docs-facts.test.mjs:258-373`、`command-enum-subskill-version.test.mjs`；`consistency-check.mjs:1-66`（29 规则，与多个测试重叠）。

**影响**：测试套件 600+ 用例**大部分在守文档/契约漂移**，而**守运行期行为**的比例低。这意味着：文档改了会红（好），但**行为悄悄坏了不会红**（代码级报告的 P0-1/P0-2 正是「604 个用例全绿时」漏掉的）。金字塔应是「行为 > 契约 > 文档」，当前更像「文档 ≈ 契约 > 行为」。

**建议方案**：
- **补行为层（小-中，最高性价比）**：为 `lib/**` 建立**行为不变量套件**（不是逐行，而是「性质」）：H2 的（超大 / 多块 / 非文本 / 缺 content / 未知 result 形状）不变量；guard 的（路径写法矩阵）；commands 的（路径围栏矩阵）。这是把代码级报告 P2-4 上升为**固定门**。

- **去重（中）**：把 `consistency-check` 与 `docs-facts` 的重叠事实收口到一处（前者为 commit 门、后者为 CI 门，语义不同，但应共用同一「事实派生」函数，避免两处各派一遍）。

**工作量**：补行为层 小-中 / 批次重组 中 / 去重 中。
**风险**：低（纯新增测试）。批次重组触及 10 文件、易与在飞的改动冲突——**建议排在所有 P0 之后**。

## 5. P2 — 长期演进

### P2-1 ｜ 可观测性：遥测是「文件聚合」而非「结构化事件」；运行时无结构化日志

**问题**：运行期唯一的输出通道是 `makeReporter`（`lib/index.js:176-184`），产出**无结构字符串**（`say('info', '· 论衡 v…')`）。遥测能力存在但是**离线聚合**：`/lunheng-stats`（`lib/commands.js:121-210`）与 `flow-metrics.mjs` 聚合 `run/` 下的文件；成本靠 `model-routing.md`（会话 ID）+ `token-cost.mjs`。

### P2-2 ｜ 单文件无界增长：`CHANGELOG.md` 5596 行 / 771 KB；`audits/` 100 份

**证据**：`CHANGELOG.md` 5596 行、771 KB；`audits/` 100 项；`references/pipeline-readme.md` 112 KB；`references/_shared/M-Gate-Algorithm.md` 97 KB（`SKILL.md:89` 已用 `ref-get.mjs` 按需读缓解）。

**影响**：`repo-hygiene-check` 规则⑨ 已对 ≥12 KB 的 `.md` 设**棘轮上限**（`AGENTS.md:73`，只降不抬）——说明维护者已知情并设了护栏。但 `CHANGELOG.md` **不在随包**、也不在技能目录（规则⑨ 只覆盖技能目录），故它可**无界增长**。**建议**：给 `CHANGELOG.md` 也设棘轮或按主版本**归档拆分**（`CHANGELOG/18.x.md`）。**工作量小，风险低**。

### P2-3 ｜ 扩展扇出与「load-bearing 行」式脆弱点

**问题**：新增一个事实的**改动扇出**（实测）：

| 新增… | 需改的物理点位 | 是否被门守住 |
|---|---|---|
| **角色** | `references/agents/0X.md` + `dispatch-cards.md` + `SKILL.md`(×2) + `AGENTS.md` + `package.json` description + `model-routing.mjs` tool→roles | 弱 |
| **M 门项** | `mgate-gates/*.mjs` + `M-Gate-Algorithm.md` + `-appendix.md` + `规范-机械门对照表.md` + `m-gate-check.mjs` 头计数 + 阈值表 | **强**（多测试守） |
| **斜杠命令** | `route-command.mjs` COMMANDS + `SKILL.md` 计数 + `package.json` description + 五语 README + `lib/index.js:279` 运行期串 + `command-routing.md` | 中（规则㉕ + C-1） |
| **检索源** | `外部检索源接入面.md` + 角色卡 + `glossary.md` | 无 |

**证据**：`docs-facts.test.mjs:425-446`（角色卡守恒）、`:752-808`（对照表登记）、`consistency-check.mjs:45-49`（命令数真源）；`cordis.patch.yml:8-14`（自注册行 load-bearing，v18.0.0 缺陷，由 `tests/bundle-contract.test.mjs:42-53` 守）；`cordis.patch.yml:30-42`（6 处 `!!js` 加载期执行面）。

**影响**：**扩展成本不均**——加 M 门项代价高但被门守（安全）；加角色/检索源代价低但**无门**（易漂）。**建议**：按「是否被门守」对齐——给「角色」「检索源」补轻量一致性门（角色：三处角色集合相等；检索源：接入面里的源枚举 ⊆ 引擎降级链）。

### P2-4 ｜ 安装完成信号缺失（测试靠定时等待）

**证据**：`tests/_fixtures.mjs:176-183`：`settle()` 是**固定 80 ms 等待**，注释自陈「因应用完成信号尚未在 `lib/index.js` 暴露（v18.16.0 F-1 留 half-修）」。多个 `entry/h2/guard` 测试依赖它（`entry.test.mjs`、`h2-h5-listeners.test.mjs:79` 等）。

**影响**：`apply()` 里所有可选能力都装在**异步 IIFE**（`lib/index.js:307-562`）内，测试只能猜时长。CI 高并发下是 flaky 真源（注释已实测「CI 80.6 ms 上界」）。**建议**：入口暴露一个安装完成信号（如 `apply` 返回的 effect disposer 上挂 `ready` Promise，或 `ctx.effect` 返回带 `ready` 的对象），测试 `await` 它。**工作量小-中，风险低**——但它与 P0-1（入口重构）强相关，建议同批做。

### P2-5 ｜ 文档即程序的执行者身份未机械化：T8 终检「主控亲执行」无结构保证

**证据**：`SKILL.md:10,32`（T8 由主控亲执行、不 spawn）；`AGENTS.md:26`（Phase 5 由 T8/主控完成）。

**影响**：T8「不 spawn、主控亲做」是**语义约定**，靠模型遵守；无门校验「T8 阶段是否真的没起子代理」。属编排层（P0-3）的子项，**未验证**是否有必要机械化（长期演进项）。

## 7. 推荐执行序列（先做什么、后做什么）

**排序依据**：① 收益（消除「静默失败」类风险）> ② 成本（改动面 × 测试耦合）> ③ 依赖（是否被其它改动阻塞）。

| 序 | 动作 | 关联 | 为什么排这里 |
|---|---|---|---|
| **1** | **补 `lib/**` 行为不变量套件**（H2 输入空间矩阵 + guard 路径矩阵 + 入口安装完成信号 `ready`） | P0-1(C)、P2-4、P1-5 行为层 | **成本最低、收益最高**：不加新门，只加「能抓住代码级报告那类缺陷」的用例。是后续所有 `lib` 重构的**安全网**——没有它，第 2 步会盲改。 |
| **2** | **入口解耦**：H2/H4/H7 移出 `index.js` 到 `lib/hooks/*`；脱敏聚合移入 `ethics-sanitize.js`；`sanitize()` 拆「全文变换 / 分页」 | P0-1(A/B)、P1-2、代码级报告 P0-1/P0-2/P2-3 结构修法 | 依赖第 1 步的安全网。**同批必须**扩 `host-contract` 扫描面到多文件，否则规则⑮会红。 |

| **4** | **补 SSOT 派生门（低风险那半）**：`LUNHENG_*` env 名双向一致门；版本「未知形态检测」门；角色集合三处相等门 | P0-2、P2-3 | 纯新增门、不改运行期。**先加门会让既有漂移变红**，一次清账即可。**不要**先做 manifest 生成（大改）。 |

## 8. 未验证 / 推断项（如实声明）

1. **DSH 宿主实际版本分布**：本沙箱 `spawnSync('git')` 拿不到 git（沿用代码级报告的环境限制），故 `peerDependencies` 区间内各版本的真实行为**未逐版验证**（P1-4 的「落差」是**声明 vs CI 单点**的静态事实，不是逐版实测）。
2. **`agent/request` 事件行为**：`lib/index.js:450-451` 自陈该事件为宿主实验事件、本机无法实测（缺 API key）——H7 的**运行期有效性未验证**。本报告只分析其**结构**（env 名重复、只读性质），不宣称其生效。
3. **`cordis.patch.yml` 的 `disabled` 裁剪实际生效性**：`cordis.patch.yml:91-93` 自陈「`--dump-config` 仍只打印声明行，故 off 时工具数是否真的少 3 仍未在能起 headless 的环境核对」——P2-3 对「自注册行 load-bearing」的判断基于 `bundle-contract.test.mjs` 与注释，**未在本机复现加载器裁剪**。
4. **「路径中心化 guard」的误伤面**：P1-1 建议的可行性判断基于代码阅读（guard 对**所有**工具调用都跑 `guardFn`，`:268`），但**未实测**「把判定从工具名倒转为路径中心后，对只读工具的误拦率」——需以 `tests/guard-*.test.mjs` 做回归实验。
5. **`status.md` 作为状态真源的充分性**：P0-3 对「无 schema / 漂移会静默改执行路径」的判断基于规则㉔ 的立规动机（`consistency-check.mjs:41-44`），**未穷举**所有依赖 `status.md` 的下游读取点。
6. **`ethics-sanitize` 的正则性能曲线**：代码级报告已实测（2 MB ~150 ms），本报告只引用其结论用于论证「热路径同步」的结构判断，**未独立复测**。
