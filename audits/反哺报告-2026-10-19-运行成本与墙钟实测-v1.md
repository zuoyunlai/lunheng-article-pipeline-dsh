## §一、实施摘要（先读这段）

**核实结论：口头报告的「大方向对，但 4 条判断错、3 处数值/口径不严」。** 修正后的结论是：

1. **成本 ≈ 步数 × 上下文，不是「写得多」**（**成立**）：11 篇合计 759.5M token，其中 **93.7% 是 cacheRead**、**输出仅 0.67%**。同一件事（写 8 千字初稿）实测 **4.4M ~ 35.0M**，差 8 倍。
2. **钱在「写作 ↔ 审计」往复，不在检索**（**成立，但需按已归账子集表述**）：能按角色归账的 353.5M 中，T5 写作族 **56.1%** + T7 审计族 **16.4%** = **72.5%**；T1-T3 检索合计 **14.2%**。**另有 406.0M（占全样本 53.5%）根本归不了账**（见 F2）。
3. **真正的成本主导是离群轮 + 计量漏项**（**成立，且比口头报告更严重**）：`轮次账本` 按设计**只计量 A/B/G 三轮**，把**最贵的机械轮**（压缩/收口/引用闭环/收尾修复）整体排除在额度与计量之外——xingbie 单篇这四类轮 **34.3M（该篇 23.1%）**，**无任何上限**。
4. **「G14 ∥ T9 并行」是错的**（**口头报告错误 R1，已撤回**）：v18.75.0 明令串行，并行会破坏「终闸报告 = 最终版本真源」不变量。⚠️ 同时撤回「T9 三视角目前串行」——规则本就要求**并行** spawn（见 R2）。
5. **「T7 首轮只查 5 项」是历史案例被误读**（**口头报告错误 R3，已改写**）：规则早要求 T7 首轮跑**全量机械门 + G0-G14 全 15 主项**；「5 项」是 v18.2.7 之前的旧清单，`pipeline-readme.md:978` 自己把它记为历史案例。真正的缺口**不是要求缺失**，而是「**全量**」到底几项没有唯一口径（四处写 24、三处写 25，见 M5）——G 项覆盖本身已有 `M-Exist-9` 机检。

### 3.4 墙钟（方法如实）

- 方法：项目内全部文件 mtime 升序，间隔 ≤30 分钟的相邻差值累加 = 活跃时长；>30 分钟记为 idle。
- 结果：xingbie 2.1h / 台海 2.2h / test-v18-78-2 2.5h / 生成式AI 1.9h / 不能评估的忠诚 3.5h / 中国古典学 3.4h；跨度分别 46.6 / 47.1 / 102.9 / 11.1 / 172.0 / 269.1 h。
- **偏差方向（如实）**：子代理连续工作期间不落盘，故活跃时长**被低估**；idle 中混有"模型在跑但未写盘"的窗口。结论只用于"空转主体不在门里"这一判据，不用于报"每篇需 X 小时"。
- 门等待真值（`gate-receipts.jsonl`）：10 / 19 / 63 / 36 / 518 / 2 分钟（6 项目）。

### 3.5 成本复算通道**不稳定**（新发现，F2/M4b 的根；R6 更正了首版判据）

对 4 个项目实跑官方工具：

```
node skills/lunheng-article-pipeline/scripts/token-cost.mjs --project run/xingbie
```

→ 首轮实测：xingbie / 台海 / 生成式AI / 不能评估的忠诚 **`matchedSessionCount` 均为 0**。**复测出现相反结果**：xingbie 21/21 全部命中（`matchedFromLiveStore: 21`、总量与快照一致 148.6M），其余三篇仍为 0。
→ **更正（R6）**：本门不是「已失效」，而是**不稳定 + 会静默低估**——`run/中国古典学的学科划界` 的 live 只命中 **2/3** 个会话（2.14M），而其交付快照是 **10.90M**（差 5 倍）。成因：`--project` 的 id 抽取面随日志改动而变（该项目的 `model-routing.md` 后来才补行），且 `readLiveUsage` 按「首个含该 id 的工作区目录」取值，多工作区时会落到陈旧副本。
→ 结论不变、判据更强：**交付时落盘的 `final/token-cost.json` 是唯一稳定证据**，live 复算只能当交叉校验。这正是 10-10 报告 E3「分档成本收益是信念非数据」的结构成因：**不是不想测，是测完就没了 / 测了也不一致**。

### M1【P0·治本】机械修订轮脚本化：把「压缩/字数/引用闭环/收尾修复」从 spawn 改为脚本

**问题**：`轮次账本` 按设计只计量 A/B/G 三轮；「不占额度的常规相位产物（首稿、**压缩轮**、**收口轮**、**修复轮**）」被明文排除在计数之外（账本头注释 + `round-ledger.mjs` 的 `TRACKS`/`ROUND_CAPS`）。于是**最贵的机械轮无额度、无计量、无上限**。

**证据**：
- xingbie 单篇：压缩轮 `12.52M` + 收口轮 `9.51M` + 引用闭环 `9.05M` + 收尾修复 `3.26M` = **34.34M / 148.6M = 23.1%**（分项取自该篇 `model-routing.md` 的会话 ID ↔ `token-cost.json` 的 token 行）。
- 压缩轮产物自述：`run/xingbie/drafts/修订说明-v2.md` 首行「**本轮 = 压缩轮（字数 P1）**」——纯字数收敛，无论证变更。
- 为什么仍要 spawn：`apply-compression-cycle.mjs` 的 ③ 只产「**残留风险清单**」+ 决策 JSON，**不产 `apply-diff` 可吃的四族清单**（脚本头 `③` 原文：「触发 T5 v(N+1) 段级 diff（自动生成微压缩清单，主控可批准应用）」）⇒ 清单必须由模型出，于是 T5 被 spawn。

**方案（三段，全部复用既有件）**：
1. `apply-compression-cycle.mjs` 在「超阻塞线」分支追加**候选清单输出**（≤1.5 KB 代码），格式取 `apply-diff` 四族：`[P1-n] 定位 / 现况串 / 修改后串 / 两侧汉字`；候选来源**全部是已有判据**——`HARD_TERMS`/`SOFT_TERMS` 命中行、分节超预算段、`CRITERION_RE` 邻近的冗句（**只摘"删冗/等量置换"类，不产出删论证的条目**）。
2. 主控 `node scripts/apply-diff.mjs <draft> <清单> --in-place` 机械应用（`apply-diff` 已具备 `old/new` 最小差异 + `expect` 命中次数断言）。
3. 应用后**复跑**脚本 ④′ 的四类不变量（引用标记 / 图位编号 / 判据句 / 分节最小硬指标）+ `apply-diff` 的三条守恒（`causal_upgrades` / `numeric_drift` / `droppedLines`）。

**质量护栏（定稿质量优先）**：
- 只做**删冗与等量置换**，不新增事实、不改因果强度（`apply-diff` 的 `causal_upgrades` 硬拦）、不动引用与数值（不变量硬拦）；
- 主控**逐条批准**后才 `--in-place`；任一条不变量不通过 → 回退该轮，改走 spawn；
- **论证删减类压缩不进脚本**（必须 T5），本动议**不承诺**覆盖全部压缩轮。

**收益上界（不写预测）**：可脚本化轮占比的上界 = **23.1%**（xingbie 单篇实测，n=1）；全库未测，故**不写"预计省 N%"**。

**影响面**：`scripts/apply-compression-cycle.mjs`（改）；`apply-diff.mjs`（**不改**）；`pipeline-readme.md` L313 段（余 1,452 B，且须同步 `pl[950-1]` 行号锚）；`05-写作-writer.md` L326-351（余 4,691 B）。**零新增脚本。**
