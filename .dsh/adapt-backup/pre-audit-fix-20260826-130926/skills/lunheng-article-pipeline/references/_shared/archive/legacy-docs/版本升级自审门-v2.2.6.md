# 版本升级自审门（Upgrade Self-Audit Gate）v2.2.6

> **背景**：论衡版本升级反复踩「改 A 漏 B」（教训 #36/#58/#60）与「头痛医头」（教训 P1-3）。最典型的两例：
> - v2.2.2 新增 T6 批判伙伴 + v2.1.8 强化 T3 案例检索员时，**SKILL.md 正文三处（流水线全景/项目目录/派发话术）漏同步**，直到 v2.2.6 主人人工发现才补；
> - v2.2.4 改进只修了实战暴露的单点（M-Exist-1 内联空转），未系统排查同类问题（G2/M-Form-1/M-Exist-3/G4-2 全空转），v2.2.5 审计才补全。
>
> **解法**：把「版本升级」本身当作需要机械校验的对象——每次改角色卡/文档/机制，commit 前必须跑一道自审门，**不依赖人（或 LLM）自觉**，用 grep + md5 + ls 三件套机械化验证。
> **设计哲学**：与 M 门同源——「形式合规 ≠ 存在性合规」，版本升级的「改 A 漏 B」本质是「改了真源却漏了下游」。自审门就是版本升级的 M 门。

## 触发条件

以下任一动作发生时，主控必须跑自审门（**commit 前，不是 commit 后**）：

1. 新增/删除/重命名角色卡（`references/agents/0X-*.md`）
2. 修改角色卡机制（铁律/G 项/F 模式/M 门算法）
3. 升级版本号（SKILL.md version / README / 设计文档）
4. 修改真源层任一文档（README/设计文档/SKILL.md/`references/_shared/failure-modes.md`/模板）

> 纯项目产出（run/<项目名>/ 下的稿件）**不触发**自审门——自审门只管论衡机制本身，不管论文成品（论文成品走终稿 M 门）。

## 检查项（7 项，全机械化，exit 0 才 commit）

### 门 A：角色卡完整性（ls）
```bash
ls references/agents/ | grep -E '^0[0-8]-'
# 应有 8 张卡：00主控/01文献/02数据/03分析/04写作/05审计/06案例/08批判
# 无 07 正常——T7 终检是主控职责，无独立角色卡
# 数量 != 8 → FAIL
```

### 门 B：角色清单三处一致性（grep，防 T8/T6 漏同步）
```bash
# 提取 agents/ 目录实际存在的角色编号（01-08 中除 07）
ls references/agents/ | grep -oE '^0[0-9]' | sort -u > /tmp/agents_exist.txt
# 三处文档分别 grep 每个角色编号 T1-T8（含 T7 终检、T0 主控）
for f in "references/pipeline-readme.md" "references/../README.md" "SKILL.md"; do
  # 派发话术段 + 流水线全景段 + 项目目录段 是否覆盖每个角色
  grep -cE 'T[0-8]' "$f"
done
# 判定：README.md + SKILL.md 的「流水线全景」「派发话术」「项目目录」三处，
#       每个实际存在的角色编号都至少出现一次 → PASS；缺任一 → FAIL
```
**核心判据**：新增角色（如 T8）后，`grep -c 'T8' SKILL.md` 必须 ≥3（流水线全景 + 项目目录 + 派发话术三处各一次），否则就是「角色卡加了、正文漏了」。

### 门 C：版本号五处一致性（grep）
```bash
NEW_VER="v2.2.6"  # 本次升级的目标版本
# 五处真源必须都含 NEW_VER：
# ① SKILL.md version 字段（ClawHub 副本）
grep -E "^version:" ~/.DSH/workspace/skills/lunheng-article-pipeline/SKILL.md
# ② references/pipeline-readme.md 版本历史行
grep -c "$NEW_VER" references/pipeline-readme.md
# ③ pipeline/设计文档.md 版本历史段
grep -c "$NEW_VER" pipeline/设计文档.md
# ④ settings.yaml 论衡 agent description
grep -c "$NEW_VER" settings.yaml
# ⑤ `references/_shared/failure-modes.md` / MEMORY.md（如有版本段）
grep -c "$NEW_VER" `references/_shared/failure-modes.md` 2>/dev/null
# 任一为 0 → FAIL（该层漏更版本号）
```

### 门 D：双端 md5 一致性（教训 #57）
```bash
# workspace-paperwriter/pipeline/ ↔ ClawHub skill 副本/references/agents/ 对应文件逐一 md5 对比
SKILL=~/.DSH/workspace/skills/lunheng-article-pipeline
for f in agents/00-主控-coordinator.md agents/01-文献检索-literature-scout.md \
         agents/02-数据检索-data-scout.md agents/03-分析-analyst.md \
         agents/04-写作-writer.md agents/05-审计-auditor.md \
         agents/06-案例检索-case-scout.md agents/08-批判-critical-companion.md; do
  [ "$(md5sum pipeline/$f | cut -d' ' -f1)" = "$(md5sum $SKILL/references/$f | cut -d' ' -f1)" ] \
    || echo "MISMATCH: $f"
done
# 任何 MISMATCH → FAIL（真源改了、副本没同步，或反之）
```

### 门 E：真源五层同步（清单核对）
| 层 | 验证点 | 命令 |
|----|-------|------|
| ① git | commit 存在 + tag 已打 | `git log --oneline -1` + `git tag | grep $NEW_VER` |
| ② 文档/角色卡 | 门 A-D 全过 | - |
| ③ GitHub Web UI | description/topics 已更新 | `gh repo view --json description` |
| ④ settings.yaml | description 含 NEW_VER | 门 C ④ |
| ⑤ DSH 本地记忆 memory | entity memory 已 store | `文件记忆` 已调用 |

### 门 F：新增机制落地检查（防「头痛医头」，教训 P1-3）
```bash
# 本次升级新增/修改的机制，必须在所有「下游文档」都体现，而非只改单点。
# 判据：新增机制的关键词，在「角色卡 + README + 设计文档 + SKILL.md」≥2 处出现。
# 例：v2.2.4 新增「修订轮独立写手」，应 grep 主控卡 + 审计卡 T5.5 + SKILL.md 三处都有。
```

### 门 G：关键词矩阵 grep（教训 #60 SOP）
```bash
# 5 层真源 × N 文件 × 关键词矩阵，全命中才算闭环。
# 例：本次升级关键词「批判伙伴」应 grep：
#   agents/08-批判-critical-companion.md（角色卡）+ references/pipeline-readme.md（派发话术/全景）
#   + SKILL.md（三处）+ 设计文档（版本历史）+ settings.yaml（description）
#   + ClawHub 顶层 README.md（GitHub 根目录精简版，树形结构/项目目录/流水线全景三处）⚠️ v2.2.6 补
# 任一文件漏关键词 → 该文件漏同步 → FAIL
```

> ⚠️ **v2.2.6 补丁（教训：主人发现顶层 README 漏 T8）**：真源清单必须包含 **ClawHub skill 副本顶层 `README.md`**（GitHub 仓库根目录直接显示的精简版，含树形结构 + 项目目录 + 流水线全景）。它是**独立真源**，不是 `references/pipeline-readme.md` 的副本——之前门 G 只 grep 了 references/pipeline-readme.md（完整版），漏了顶层精简版，导致 v2.2.2 加 T8 时顶层 README 三处（树形结构缺 T8 + T6 重复 + 目录缺 08 卡）一直没被发现，直到主人人工指出。

## 判定与失败处理

```
7 门全过（exit 0）→ 允许 commit + tag + push
任一门 FAIL → 禁止 commit，回到对应真源层补同步，重新跑全部门
自审门报告写入 final/版本升级自审-vX.md（或 audits/），随 commit 一并记录
```

**失败处理优先级**：
- 门 B（角色三处一致性）失败 → 补派发话术/全景/目录三处，1 轮内可关
- 门 D（双端 md5）失败 → cp 同步副本，立即关
- 门 C/E（版本号/五层）失败 → 补对应真源层，通常需主人确认（GitHub/DSH 本地记忆 是公开动作）

## 论衡哲学化

- 「**版本升级也需要 M 门**」——终稿有 M 门查成品，版本升级也要有门查机制本身，两层都不能靠自觉。
- 「**改 A 漏 B 是 LLM 的结构性通病，不是偶然失误**」——教训 #36/#58/#60 + v2.2.6 T8 漏同步四次同源，必须用机械化 grep 兜底，不能靠「下次注意」。
- 「**自审门是论衡的「自指」**」——论衡用审别人的标准审自己，这正是「独立角色 + 机械化门 > 自我复核」命题的最高形态。

## 与终稿 M 门的区别

| 维度 | 终稿 M 门 | 版本升级自审门 |
|------|----------|--------------|
| 对象 | 论文成品（final/定稿.md） | 论衡机制本身（角色卡/文档/真源） |
| 触发 | T7 终检 | 每次版本升级 commit 前 |
| 检查 | M-Form 6 + M-Exist 3 | 角色清单一致性 + 双端 md5 + 版本号 + 真源五层 |
| 产出 | M-Gate-Report-v2.2.4.json | 版本升级自审-vX.md |
